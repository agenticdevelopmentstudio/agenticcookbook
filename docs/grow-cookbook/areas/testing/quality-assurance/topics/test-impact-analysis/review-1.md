# Review: test-impact-analysis

## Findings

- `rules.md` `run-the-full-suite-periodically`, `selecting-tests-for-a-change.md` step 9, `rationale.md` paragraph 4: the full-run rule outruns two of the claims it cites, and the text calls things full runs that the research says are not. Every instance: (1) `tap-milestones-batch-commits` says TAP runs, per milestone, the targets affected since the previous milestone (the second check confirms: "milestones run tests selected by reverse dependencies on files changed since the previous milestone"), which is a batched affected-set run, not the full suite; step 9 lists "Google TAP's milestones" as a full run. (2) `android-test-mapping-directory-rules` says TEST_MAPPING has separate postsubmit groups, which are still directory-mapped tests, not the full suite; step 9 lists "Android's postsubmit groups" as a full run. (3) Rationale paragraph 4 opens "A full run stays behind the subset in every source that selects", but most of the selecting sources read (Nx, Bazel, Pants, Turborepo, Target Determinator, bazel-diff, GitHub Actions, GitLab, Gradle) say nothing of a full run; only Microsoft, Launchable, Develocity and Mill do. Fix: reword step 9 so TAP milestones are a batched run of everything affected since the last milestone and Android postsubmit groups are a later, wider mapped group, not full runs; either widen the rule so these two claims support it (for example "the full suite, or every test affected by the changes since the last such run, at some later point ...") or cite them from a rule they do support (both claims come from a `new` verdict, so they must stay cited somewhere); and change "in every source that selects" to name the sources that say it.
- `rationale.md` (with `rules.md`): the rationale for allowing deviation (behavioral-requirements `must-explain-rationale-for-should-requirements`) and the conditions for a MAY (`should-document-conditions-for-may-requirements`) are missing for these rules; the rationale never mentions them and the rule text gives no reason: `diff-against-a-known-good-base` (SHOULD; why a known-good base and when another base is acceptable), `log-each-fallback` (SHOULD; why the fallback is logged, from `bazel-diff-fallback-costs-speed`), and `decide-change-by-content` (MAY; when content hashing is worth using rather than names or commit metadata). Every other SHOULD has its reason in the rationale or inline (`path-skipped-required-checks-resolve` carries its "so a skipped workflow does not block the merge"). Fix: add one sentence each to the rationale from the claims already cited (Nx's latest-successful-commit recommendation and Turborepo's shallow-checkout behaviour; bazel-diff logging which path each run took; bazel-diff hashing content rather than names or metadata).
- `rules.md` `always-select-new-changed-and-failing-tests` ("recently new, recently changed, recently failed or recently flaky") and `retrain-a-learned-selector` ("retrain it regularly"): unanchored relative terms (behavioral-requirements `should-not-use-unanchored-relative-terms`); a reviewer cannot tell PASS from FAIL on "recently" or "regularly". The research gives no threshold (Develocity and Meta use the same words), so a number would be invented. Fix: anchor each to a window the team states and records (for example "recently, within a window the team states" and "on a cadence the team states"), or say in the rationale that the sources give no threshold and the team sets one; the same applies to the matching lines in `a-build-must-establish.md`.
- `rationale.md` paragraph 5 ("The four Verify checks"), `a-build-must-establish.md` and `what-a-reviewer-looks-for.md` (the owner rules' "site", "residue path", "the prose", "commit range"): terms the guideline never defines. "Verify checks" is the author's own wording and names nothing in this guideline. "Site" and "residue path" come from the owner rules, whose wording is exempt, but the surrounding text repeats them (build lines for `each-selection-justified-by-diff`, `every-changed-path-accounted-for`, `fail-closed-is-stated`) without ever saying what a site or a residue path is, while every other part speaks of tests, targets and changed files; a reader cannot apply those MUST rules (behavioral-requirements `must-be-independently-testable`). Fix: in the rationale say "the four rules kept as the owner's text" instead of "Verify checks"; outside the exempt rule text (intro or how-to), say what a site and a residue path are in this guideline's terms (a selected test or test target; a changed path handed to the analysis to attribute), without changing the four rules' wording.
- `examples.md`: the record shows a fallback for `package-lock.json` ("every test that uses an npm dependency is selected") but never names the tests that fallback selected, so the illustration of `record-why-each-test-was-selected` and `every-changed-path-accounted-for` leaves the one unattributable path without its sites; it is also unclear whether `pricing:test`, `checkout:test` and `cart:test` are the npm users or graph-only selections. Fix: list the tests the lockfile fallback selected (for example "Selected by fallback (package-lock.json): pricing:test, checkout:test, cart:test, search:test") so every changed path in the record is attributed to named tests.
