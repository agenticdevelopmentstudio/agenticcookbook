
- **register-handler-at-startup**: On a node that is not in machine mode, the `categorize_and_tag` handler MUST be registered in the job worker's dispatch table at startup, and the job worker's supported-types set MUST include `categorize_and_tag` if and only if that handler is registered.
- **register-step-handlers**: A node that runs Jobs steps MUST also register the `jobs.step.ai` handler at startup, and the `jobs.step.script` handler when **script-steps-machine-only** allows it, and its supported-types set MUST include each job type if and only if a handler for it is registered. A node in machine mode MUST NOT register `categorize_and_tag`: a machine claims only its own environment's step rows, and that type is never one.
- **claim-sends-job-types**: Every claim MUST send `jobTypes`, listing exactly the registered handlers' job types. The backend's legacy rule gives a claim without `jobTypes` only `categorize_and_tag` and never a `jobs.step.*` row, so a node that omits the list MUST NOT expect a step and a node that wants steps MUST name them.
- **machine-mode**: The node MUST accept `AI_NODE_ENVIRONMENT_TOKEN` (a `jenv_` environment token) as an alternative to `AI_NODE_API_TOKEN` and use it as the bearer on the claim, heartbeat, complete and fail calls; startup MUST fail with a configuration error when neither is set or when `AI_NODE_ENVIRONMENT_TOKEN` does not start with `jenv_`, and when both are set the environment token MUST be used. In machine mode the node runs as one owner's Jobs environment and MUST report `capabilities` on every claim as `{ jobTypes, providers, scripts }`: the registered job types, the provider kinds it can run now (with `claude-code` only when the CLI answers `--version`; a yes is remembered for the life of the process, and a no is asked again once 60 seconds have passed, so a CLI installed after the node started is picked up without a restart), and whether `jobs.step.script` is registered. A machine MUST claim for, and report in `capabilities`, only providers it runs itself (`local`, and `claude-code` as above), never a paid provider kind the hub would need to send it a key for. A machine MUST NOT register in the hub's node registry or ship its log lines there; those belong to the hub's operators, and a machine belongs to its owner.
- **no-key-on-machine**: In machine mode the node MUST use its own configured model for an AI step whose model source is `environment` and MUST NOT expect a provider key in the claim; a claimed AI step whose model source is `connection` on a machine MUST fail with `retryable: false`.
- **step-ai-handler**: The `jobs.step.ai` handler MUST read the payload `{ step, inputs, steps }`, where `step` carries `id`, `prompt`, optional `instructions`, `model` and optional `outputSchema`, and `steps` maps each earlier step's id to `{ output }`. A payload that does not parse, or an output schema that cannot be read, MUST fail the job with `retryable: false`. The instructions (or a default) are the system prompt, with the output schema appended when there is one; the user message is the prompt followed by the inputs and the earlier outputs as JSON. A `connection` model MUST run on the target the claim resolved into `llm`; an `environment` model runs on the node's own Ollama (`local`) or on the injected `claude-code` runner. When the step declares an output schema, the handler MUST validate the answer against it before returning (a result that fails validation fails the job as retryable, as **backend-failure-is-job-failure** says); without one the output is the model's text. The handler returns `{ output, toolCalls }`, and the usage of each provider turn rides beside it on complete or fail.
- **step-ai-tool-loop**: When the claim carries an acting token, the `jobs.step.ai` handler MUST run a tool loop against the hub's `/mcp` endpoint with that token as the bearer, offering the model the tools `/mcp` lists and returning each tool result to the model, and MUST stop after at most 20 tool calls in one step. Tool names MUST be offered with every character outside `[a-zA-Z0-9_-]` replaced by `_` (the hub's `<source>.<name>` dot is refused by the OpenAI and Anthropic wires), cut to 64 characters, and mapped back to the hub's name on the call. Two hub tools MUST NOT share an offered name: when a name is already taken, the later tool in `/mcp`'s list MUST be offered as the name with `_2` appended (then `_3`, and so on), the name cut short enough that the result is still at most 64 characters, so each offered name maps back to exactly one hub tool. A tool result longer than 64,000 characters MUST be cut before it goes back to the model. The cap MUST be checked for a whole model turn before any of its calls runs: a turn whose calls would take the step past 20 MUST fail the step with `retryable: false` and an error that names the limit, and MUST run none of its calls. Without an acting token, or on a `claude-code` step, the handler MUST offer no tools. The acting token is valid on `/mcp` only while the queue row is claimed under the lease, so the loop MUST run inside the lease and its heartbeat. The claim's token lasts one lease, and each heartbeat for an acting job answers a fresh `actingToken` for the extended lease: the node MUST use the newest token it holds as the bearer on each later `/mcp` call, MUST keep its current token when a heartbeat answers a null or absent `actingToken`, and MUST NOT log or ship any acting token. A `/mcp` 401 MUST make the node ask the lease with a heartbeat: a heartbeat the hub answers 404 means the lease is gone, and the job MUST be dropped with neither complete nor fail (**lost-lease-abort**); a lease that still holds, or a heartbeat that fails some other way, MUST fail the attempt as retryable, so it is reported rather than left for the reaper.
- **step-script-handler**: The `jobs.step.script` handler MUST run the step's `node` or `python` source (`python` is `AI_NODE_PYTHON`, default `python3`, found on the node's own `PATH`, since the script's `PATH` is fixed) in a new temporary directory that is removed afterwards and is the script's working directory and `HOME`, with a clean environment built from nothing (a fixed `PATH`, `HOME`, `TMPDIR` and `LANG`, and no variable of the node's own, so no token reaches the script), the earlier steps' outputs as one JSON object keyed by step id on stdin, and the step's timeout (default 60 seconds, at most 15 minutes; a larger value is clamped to 15 minutes). It MUST return `{ output, exitCode }`, with stdout as the output, parsed as JSON when it parses and as a string otherwise. The handler MUST cap captured stdout at 4 MiB and stderr at 64 KiB, keeping the last 64 KiB of stderr. A non-zero exit or a timeout MUST fail the step as retryable, with the exit code or the timeout and the tail of stderr in the error; the step's own attempt limit decides whether it runs again. When the script exits, its process group MUST be killed, so a background process it left running neither holds the step open nor outlives it, and when the node stops it MUST kill every script and CLI process still running. Stdout over 4 MiB MUST fail the step with `retryable: false` and an error that names the cap, since the same source on the same inputs overflows the same way.
- **script-steps-machine-only**: The `jobs.step.script` handler MUST be registered only when the node runs in machine mode (`AI_NODE_ENVIRONMENT_TOKEN` set) and `AI_NODE_ALLOW_SCRIPTS=1`; otherwise `jobs.step.script` MUST NOT be in `jobTypes` or `capabilities`. `AI_NODE_ALLOW_SCRIPTS` MUST be `1`, `0` or unset (unset means `0`); any other value MUST fail startup, so a typo cannot turn scripts on or off.
- **claude-code-provider**: On a machine the node MUST offer a provider kind `claude-code` that runs the CLI named by `AI_NODE_CLAUDE_CODE_BIN` (default `claude`) as `claude -p --output-format json --tools "" --strict-mcp-config --safe-mode --permission-mode dontAsk --no-session-persistence --disable-slash-commands`, a subprocess with the prompt on stdin, in a new empty temporary directory that is its working directory and is removed afterwards, whatever authentication the owner set up for Claude Code (a subscription sign-in, or an `ANTHROPIC_API_KEY` the owner keeps in their own environment), and the timeout `AI_NODE_CLAUDE_CODE_TIMEOUT_MS` (default 300,000 ms). The flags are pinned: `--tools ""` removes every built-in tool (`--allowedTools` only pre-approves tools and takes none away), `--strict-mcp-config` with no `--mcp-config` loads no MCP server, `--safe-mode` loads none of the owner's CLAUDE.md, skills, plugins, hooks or custom agents, and `--permission-mode dontAsk` allows nothing that would ask; the only thing a step adds is `--model <name>` when its model names one, and only after the name matches `^[A-Za-z0-9][A-Za-z0-9._:@[\]-]{0,99}$` (so it can never read as another flag; a name that does not match MUST fail the step with `retryable: false`). The node MUST NOT take any other flag from the step, so the CLI runs no tools and reads no project. The CLI MUST start from the node's environment less every `AI_NODE_*` variable and any variable holding the node's token. Provider variables the owner set are kept on purpose: the machine is the owner's, the hub never sends a machine a provider key (**no-key-on-machine**), so any key the CLI finds is one the owner chose for Claude Code. The node MUST parse the CLI's JSON result and report the usage it prints (input and output tokens) with the result; output that does not parse, an error result, a non-zero exit and a timeout MUST fail the step as retryable, the first with an error that says the CLI output did not parse, and a failed run's output MUST NOT be passed onward as text. A hub node has no `claude-code` runner, and a `claude-code` step claimed there MUST fail with `retryable: false`.
- **inject-llm-backend**: The node MUST construct the LLM backend from configuration at startup and inject it into every handler that performs inference, including the `claude-code` provider. A handler MUST NOT select or construct its own backend, so the same handler runs unmodified on the Swift development node and the TypeScript production node.
- **backend-failure-is-job-failure**: When the LLM backend fails or returns output that does not validate against the handler's schema, the handler MUST fail and the job worker MUST report the job as failed with `retryable: true`. A malformed result MUST NOT be passed to the complete call.
- **handler-result-reported-by-worker**: The job worker, not the handler, MUST report the handler's validated result to the backend, and MUST do so only after the handler's schema validation has passed.
- **idempotent-end-to-end**: A job re-claimed after a lease expiry MUST produce the same backend result as the first completion, with no duplicate category or tag entries. The job worker's duplicate-terminal-state tolerance and the handler's idempotent-categorization requirement together satisfy this.
- **stub-backend-testable**: The composition MUST be runnable with a stub LLM backend and a stub job source, so the integration vectors can run without network access to a model or to the `adh` backend.
