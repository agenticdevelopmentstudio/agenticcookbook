
- **SwiftUI / Compose / React/Web**: Not applicable. The node is a background worker with no view layer. The two implementations are a Swift macOS daemon and a TypeScript service.
- **Swift macOS daemon (development node)**: Runs as a launchd-managed background process with a local model server as the default LLM backend. Detailed daemon, heartbeat, structured-output, and logging guidance is in the job-worker and llm-backend ingredients.
- **TypeScript service (production node)**: Runs as a containerized Node.js process using a hosted API as the LLM backend. The backend is selected by the `LLM_BACKEND_KIND` and `LLM_BACKEND_URL` environment variables; see the llm-backend ingredient and the Design Decision on LLM backend selection below.
- **Jobs steps (phase 9)**: the TypeScript node adds `jobSteps.ts` (the step payload schemas), `jobErrors.ts` (`PermanentJobError` for `retryable: false`, `LeaseLostError` for a drop with no report), `mcpClient.ts` (the `/mcp` client under the acting token), `subprocess.ts`, `handlers/jobStepAi.ts`, `handlers/jobStepScript.ts` and `providers/claudeCode.ts`; `config.ts` resolves the mode from the two tokens and `index.ts` registers the handlers and builds the claim's `jobTypes` and `capabilities`. Its `ProviderAdapter` is HTTP-shaped, so `claude-code` needs a subprocess path beside the HTTP adapters. The Swift development node is unchanged: it already sends its handler keys, so it never receives a step. It conforms to the 2.0 requirements only, `register-handler-at-startup` and `apn-009` among them; the Jobs-step requirements (`register-step-handlers`, `claim-sends-job-types`, machine mode, the `jobs.step.*` handlers, `claude-code`) and `apn-010` onward apply to the TypeScript node.
