
This section is informative.

A selection is judged first on safety, selecting every affected test, and then on precision, selecting no unaffected one. Every safe selection tool read falls back to running everything when it cannot map a change: Azure DevOps TIA for commits and file types it cannot understand, which Microsoft calls good from a safety perspective; bazel-diff, whose fallback costs speed but never correctness; Turborepo on a shallow checkout; GitHub Actions when the diff times out; GitLab when there is no push event. That is why unsure and unknown changes select widely. The tools fall back by design, and none words it as a requirement on the user, so the rules are recommendations.

Affected means transitively dependent: Google's TAP treats as affected every test target that directly or indirectly depends on the modified files, and Bazel, Nx, Pants and Turborepo all compute it from the build graph. Path filters select whole workflows by pattern with no knowledge of dependencies, Nx carries a change only through declared inputs, and dependency selection is only as fine as the module graph it walks. Coverage maps have blind spots too: Ekstazi, a JVM-level tracer, collected only 16.99% of the file dependencies an OS-level monitor found on the same projects (Celik et al., ESEC/FSE 2017, the authors comparing their own tool with an earlier one from their group), and in the Testar tool Hammant describes, a resource file the user does not list re-runs all tests. Nx's and Pants' lockfile defaults show how tools treat a shared input they cannot trace; Pants' documentation states it as a limit of its own tool, and the research holds the claim at reduced trust.

A diff is defined only between two revisions, so the base is named. Nx recommends the latest commit on main whose CI run succeeded rather than the plain branch tip, Target Determinator computes changed targets between two Git commits, and Turborepo needs the whole history between base and head and treats every package as changed when the checkout is too shallow. A named branch, as GitLab's `compare_to` gives, is the departure the sources show where a pipeline has no natural base. bazel-diff hashes a source file's content, not its name or the commit metadata, so a file counts as changed only when its content did; that is worth using where names or commit metadata do not show what changed, and it is a MAY because the research shows it in bazel-diff alone. A fallback costs speed but never correctness, so it does not show in the test results; bazel-diff's log says which path each run took, which is how a team sees how often its selection fell back.

Dependency selection over-selects, which is the cost the full run and measurement keep in view. At Meta it marked tests as impacted more often than necessary; at Google only 63K of 5.5 million affected test targets ever failed over 500K changes in a month (Memon et al., ICSE-SEIP 2017). Google's churn rules out running every affected target per change, so TAP batches consecutive commits into milestones, cut as often as compute allows, and runs every target affected since the previous one; batching is an option for a team whose change rate rules out per-change runs, and it is a MAY because the research shows it at Google alone. Ekstazi cut end-to-end test time by 32% on average and 54% on longer suites across 615 revisions of 32 Java projects (Gligoric et al., ISSTA 2015). Meta's predictive selection halved testing infrastructure cost while still reporting over 95% of individual test failures and over 99.9% of faulty changes (Machalica et al., arXiv preprint, owner-reported and not replicated). Leong et al. replayed Google's history and found history-based algorithms performed worse than earlier reports suggested, which is why a team measures and validates on its own history rather than adopting a published figure.

Four of the selecting sources keep a full run behind the subset: Microsoft recommends a periodic full run as the means to regulate selection, Launchable advises a later full run and keeping the nightly one, Develocity concedes that predictive selection trades comprehensiveness for speed and pairs it with a remaining-tests mode, and Mill's author runs a heuristic-free suite after merge. The build-graph tools and path filters read (Nx, Bazel, Pants, Turborepo, Target Determinator, bazel-diff, Gradle, GitHub Actions, GitLab) say nothing of a full run. Hammant mentions a nightly all-tests job only as something teams might choose and criticises it as delaying bad news; the research holds that claim at low trust. Apple's guidance is to run one target's tests while working and the full umbrella scheme before integrating. Android's TEST_MAPPING keeps presubmit and postsubmit groups apart in one mapping, so a mapped test can run after a change is submitted rather than before it; that is an option for tests a team keeps out of its pre-merge check, and it is a MAY because the research shows it in Android alone. Neither TAP's milestones nor Android's postsubmit groups is a full run. Azure TIA and Develocity both add tests selected for reasons outside the diff: previously or recently failing, newly added, recently changed or flaky. Develocity, Nx and Target Determinator record or explain why each test or target was selected; Azure TIA reports its selection in the run's test summary and details, though the research does not establish what fields that report carries. Launchable and Meta retrain their learned models on recent results. No source gives a window or a cadence (Develocity says "recently", Azure TIA "previously" and Meta "regularly", none with a number), so the rules leave the window and the cadence to the team and ask that it state and record them.

The four rules kept as the owner's text are kept at must-hold strength, which the research could not support. Tools record a reason per selection and treat every changed file as an input, which supports recording and completeness at SHOULD, but no source requires a written justification per selection, a written account of every changed path or a statement of each fallback, and tools select tests for reasons outside the diff. No source speaks to judgments resting on commit messages or branch names, and path-based mapping (Nx inputs, GitHub Actions path filters, Android TEST_MAPPING) is the platform norm. Left to the owner: the cadence and place of the full run; whether predictive selection may gate a merge on its own; whether the four checks keep their strength; whether a test selected for a reason outside the diff counts as justified; which file classes a team may declare unable to affect tests, and who approves that list; and which shared inputs select everything.
