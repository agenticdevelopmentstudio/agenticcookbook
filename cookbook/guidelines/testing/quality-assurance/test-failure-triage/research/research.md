# test-failure-triage: research

Researched 2026-11-24 for `cookbook/guidelines/testing/quality-assurance/test-failure-triage`. Every finding names the claim in `research.json` that holds its source and quote. Flaky-test quarantine and its lifecycle are left to testing/flaky-test-quarantine and testing/flaky-test-prevention; this topic covers the triage decision that comes before them.

## Best practices

- **Someone owns every failure.** Mozilla's sheriffs look at all failures on the sheriffed trees and decide for each whether it is a regression or intermittent (bp-sheriffs-review-every-failure). Chromium's gardener keeps new failures out, repairs existing ones, identifies the culprit change and reverts it (bp-gardener-owns-new-failures). This supports **every-failure-gets-one-disposition** and the new rule **named-triage-rotation-owns-failures** (SHOULD).
- **Failures fall into a small fixed set of classes.** Labuschagne et al. classified every CI failure in 61 Java projects as a flaky test, a bug in the system under test, or a broken or obsolete test: 18% of test-suite executions failed, 13% of the failures were flaky, and of the non-flaky failures 74% were bugs and 26% incorrect or obsolete tests (bp-failure-classes-flaky-bug-obsolete). The study, sample, measure and result are named in the claim. With Treeherder's fixed list (ks-treeherder-classification-set) this supports **disposition-from-fixed-set** and **every-failure-gets-one-disposition**.
- **The evidence states what was observed.** Mozilla's bug-writing guidelines require the observed (actual) result and the expected result, with facts kept apart from speculation (bp-bug-report-observed-vs-expected). Chromium and Mozilla both have the triager copy the relevant failure lines from the log into the bug (bp-failure-record-copies-log). ICD 203 makes the same split between information and judgment (bp-separate-information-from-judgment). This supports **evidence-states-what-was-observed**.
- **A bug names the observed misbehavior.** Mozilla requires the observed versus expected result (bp-bug-report-observed-vs-expected). Software Engineering at Google wants a failure to state the desired outcome, the actual outcome and the relevant parameters (bp-failure-message-desired-actual). This supports **bug-names-observed-misbehavior**.
- **A rerun on the same code separates a flake from a deterministic failure, but only one way.** A pass on rerun shows the test is flaky. Continued failure leaves it either a real failure or a flake that did not show (bp-rerun-same-code-separates-flake). This supports **flake-cites-history-or-race** and the new rule **rerun-on-same-revision-before-calling-flake** (SHOULD). It also grounds **never-force-a-verdict**: a failing rerun alone does not settle the class.
- **A stale test is told apart by an intended behavior change.** Existing tests are expected to change only when the system's behavior is meant to change. A test that fails on an unrelated change that adds no bug is brittle, not stale (bp-tests-change-only-on-behavior-change). This is the new rule **stale-test-distinguished-by-intended-behavior-change** (SHOULD). No source requires the stale-test verdict to spell out the new assertion, so **spec-rot-names-new-assertion** is unsupported as a must-hold check. The sources support SHOULD for naming the behavior change that made the test stale. They are silent on whether the verdict must carry the replacement assertion. The prior rule is recorded as spec-rot-names-new-assertion-prior.
- **State confidence with its basis and its gaps.** ICD 203 has an analytic judgment explain the basis for its uncertainty, name the causes of that uncertainty including knowledge gaps, and identify the indicators that would change it (bp-explain-uncertainty-and-gaps). It is a "should" standard from outside software. It supports the new rule **verdict-states-confidence-and-its-basis** at SHOULD. It also supports **uncertain-names-missing-evidence** at SHOULD, not as the must-hold check the rule states (uncertain-names-missing-evidence-prior).
- **No source sets a 1-10 confidence scale or a 9-10 threshold.** Nothing read ties top confidence to an observed reproduction plus a stated mechanism. The sources support only a SHOULD that a verdict states its confidence and the evidence it rests on (bp-explain-uncertainty-and-gaps, ev-get-data-first). **high-confidence-needs-reproduction-and-mechanism** is unsupported (high-confidence-needs-reproduction-and-mechanism-prior).
- **Environment verdicts are unsupported at the rule's strength.** The signals the rule names are real practice: mass failure across many jobs (ks-treeherder-infra-classify-many), retrying stopped when everything fails (pg-gradle-maxfailures-stops-retry), and a platform's inconclusive outcome (pg-firebase-inconclusive-vs-failure). But no source says a single failing test never establishes an environment fault. Gruber et al. classify infrastructure flakiness from one test's pattern across runs (ev-infrastructure-flakiness-share). The sources support SHOULD: an environment verdict should cite a signal across tests or an infrastructure observation. They do not support the "never" clause. **environment-cites-cross-test-signal** is unsupported (environment-cites-cross-test-signal-prior).
- **Triage in practice acts on the verdict.** Chromium's sheriffs disable the failing test and file a bug. Azure DevOps puts bug creation and flaky marking in its resolution step (bp-triage-acts-on-verdict). Gardeners revert culprits (bp-gardener-owns-new-failures). **triage-changes-nothing** is contradicted as general practice (triage-changes-nothing-prior). It may still hold as one team's choice to keep the disposition separate from the action; that is listed as an open question.

## Known solutions

- **Treeherder (Mozilla)** gives each failure one value from a fixed list: not classified, fixed by commit, expected fail, intermittent, infra, and variants (ks-treeherder-classification-set). "Not classified" is itself a value, so the tool never forces a class; this supports **never-force-a-verdict** at SHOULD. Broken infrastructure shows as many jobs failing at once, which sheriffs pin and classify together (ks-treeherder-infra-classify-many).
- **Trunk Flaky Tests** splits consistently failing tests (broken) from intermittently failing ones (flaky) (ks-trunk-broken-vs-flaky). **Meta's probabilistic flakiness score** measures how likely a test is to fail when it could have passed on the same code. A deterministically broken test therefore scores near zero however often it fails (ks-meta-pfs-broken-vs-flaky). Together they ground the new rule **distinguish-broken-from-flaky-by-failure-pattern** (SHOULD).
- **Meta's model** reports a posterior distribution and says when it cannot confidently estimate a test's flakiness (ks-meta-pfs-posterior-uncertainty). This is the in-domain case for **verdict-states-confidence-and-its-basis** and for **never-force-a-verdict**.
- **Datadog Flaky Test Management** sorts flaky tests by cause from execution patterns and error signals, and keeps an Unknown category (ks-datadog-flaky-categories). **Luo et al.** studied 201 flaky-fix commits in 51 projects and found the top causes were Async Wait (45%), Concurrency (20%) and Test Order Dependency (12%) of the 161 classified (ks-luo-flaky-root-causes). Together these support **flake-cites-history-or-race**, since a race visible in the error is a recognised category. They also support the new rule **record-flake-cause-category** (MAY).
- **RootFinder (Microsoft)** logs runtime properties and diffs the logs of passing and failing runs to locate a flake's cause (ks-rootfinder-compares-pass-fail-logs). This supports **gather-failure-artifacts-before-classifying**.
- **git bisect** binary-searches history for the commit that introduced a failure, and can skip untestable commits (ks-git-bisect-finds-culprit). This grounds the new rule **find-the-change-that-introduced-the-failure** (SHOULD).
- **Buildkite Test Engine** can route a flaky test to the team responsible for it (ks-buildkite-notify-responsible-team). This supports **named-triage-rotation-owns-failures**.
- How they compare: Treeherder is a human classification system with a fixed vocabulary. Trunk, Meta PFS, Datadog, Buildkite and the CI vendors below detect flakiness from history automatically. Only Treeherder, Labuschagne et al. and Firebase's outcomes cover classes other than flaky and failed (expected failure, infrastructure, obsolete test).

## Platform guidelines

- **Web (Playwright).** A test that fails and then passes on retry is reported as flaky. One that fails every retry is failed (pg-playwright-flaky-status). Traces should be recorded on the first retry in CI. They hold DOM snapshots per action, network requests and console logs (pg-playwright-trace-on-first-retry). `test.fail` marks an expected failure and complains if the test passes (pg-playwright-test-fail-annotation).
- **Python (pytest).** `xfail` records an expected failure, with a `reason` and a `raises` parameter that reports any other exception as a regular failure (pg-pytest-xfail-strict-reason). Rerunning failures mitigates flakes, and pytest-rerunfailures marks as failed only the tests that fail on every rerun (pg-pytest-rerun-mitigates). With Playwright's annotation this grounds the new rule **known-failure-marked-expected-with-reason** (MAY).
- **JVM (Maven Surefire, Gradle).** Surefire counts a test that passes on a rerun as a flake, reported separately in the summary and the XML report (pg-surefire-flaky-counted). Gradle's test-retry plugin stops retrying once too many tests fail, because mass failure is a different signal (pg-gradle-maxfailures-stops-retry). This supports **separate-infrastructure-outcomes-from-test-failures** (SHOULD).
- **Apple (Xcode).** Xcode repeats a test until it first fails, until it first passes, or a fixed number of times (pg-xcode-repeat-tests). Its test report brings forward failure information and screenshots, and its Insights show failure patterns across configurations and run destinations (pg-xcode-test-report-insights). Apple's page does not use the word "flaky".
- **Android.** Android Test Orchestrator runs each test in its own Instrumentation, so one crash does not hide the rest of the results (pg-android-orchestrator-isolates-crashes). Firebase Test Lab gives each test a report with stack traces, logs and video (pg-firebase-artifacts). It reports "inconclusive", separate from failure, for a likely transient or Test Lab problem, and its infrastructure errors do not trigger flaky reruns (pg-firebase-inconclusive-vs-failure). This supports **separate-infrastructure-outcomes-from-test-failures**.
- **CI systems.** CircleCI, Azure DevOps and Firebase each define a flaky test by mixed outcomes on the same commit or configuration (pg-ci-flaky-same-code-history). This is the main support for **flake-cites-history-or-race**. GitLab shows how often a failing test failed on the default branch in 14 days, which tests newly failed against the target branch, and screenshots (pg-gitlab-failure-history-and-screenshots). GitHub Actions reruns failed jobs on the same SHA with debug logging (pg-github-rerun-same-sha-debug). Together they support **gather-failure-artifacts-before-classifying** (SHOULD) and **rerun-on-same-revision-before-calling-flake**.
- **Snapshot tests (Jest).** A failing snapshot is either a bug to fix or an intended change that needs the snapshot updated, and a bug must be fixed before snapshots are regenerated (pg-jest-snapshot-bug-or-update). This supports **stale-test-distinguished-by-intended-behavior-change**.
- **Windows.** Windows has no bearing on this topic beyond Azure DevOps (covered above under CI systems).

## The expert's view

- **What to do: get data before deciding.** Agans's rules, as Wheeler reviews them, are to make the failure happen and look, not to fix on a guess (ev-get-data-first). Reproduce where it failed: at Microsoft, 86% of flaky tests rerun 100 times locally were flaky only in CI, and 97 of 311 cloud failures never reproduced locally (ev-ci-only-flakiness). A few reruns may miss a low-probability flake, and one study was still finding flakes after 10,000 reruns (ev-reruns-may-not-manifest). This is the new rule **reproduce-in-the-failing-environment** (SHOULD).
- **What to avoid: letting a pass on retry clear a failure.** Ignoring flaky failures is dangerous because they may be real product faults (ev-ignoring-flaky-hides-bugs). In Luo et al.'s sample, 24% of flaky-test fixes changed the code under test, and 94% of those fixed a bug there (ev-flaky-fixes-fix-cut-bugs). Rerunning only delays the root cause (ev-rerun-delays-root-cause). Once failures are ignored, engineers stop reacting to tests at all (ev-flaky-erodes-trust). This is the new rule **pass-on-retry-does-not-clear-a-bug** (SHOULD).
- **What people get wrong: updating the test instead of examining the failure.** Jest names the habit of regenerating snapshots instead of examining the root cause (ev-regenerating-instead-of-examining). This supports **stale-test-distinguished-by-intended-behavior-change**.
- **Expect larger tests and infrastructure to produce non-product failures.** Larger tests are flakier because they use more infrastructure, and left unchecked they become too hard to triage (ev-larger-tests-flakier). In Gruber et al.'s Python study, as reported by Parry et al., 28% of 7,571 flaky tests were infrastructure flakiness, detected as flaky between iterations but not within one (ev-infrastructure-flakiness-share). This supports **separate-infrastructure-outcomes-from-test-failures**. It is also why **environment-cites-cross-test-signal**'s "never from a single test" is unsupported.
- **Treat no verdict as certain.** Meta assumes all real-world tests are flaky to some extent, and Lam et al. note calls to treat every test as potentially flaky (ev-every-test-flaky-to-some-degree). This supports **verdict-states-confidence-and-its-basis**.
- **Flake share at scale.** Luo et al. report, from a personal communication, that 4.56% of Google TAP's daily test failures were caused by flaky tests (ev-google-flaky-failure-share). How those failures were classified is not disclosed. The figure shows only that a fixed flaky-versus-other split is used at scale, and supports **disposition-from-fixed-set** only that far.
