
- **should-prefer-coroutine-first-dao-apis**: You SHOULD prefer coroutine-first DAO APIs — observable reads as `Flow`, one-shot writes as `suspend`, and multi-statement work wrapped in `@Transaction`.
- **should-state-kmp-support-as-2-7-plus**: You SHOULD state KMP support as "2.7.0+" — do not back-port the claim to older versions.
- **should-treat-room-3-as-forecast**: **Room 3.0 is ALPHA** — you SHOULD treat its API and the `androidx.room3:room3-*` artifact rename as a FORECAST, not a shipped default.
- **should-not-migrate-production-to-room-3**: You SHOULD NOT migrate production code to Room 3.0 yet.
- **should-pin-room-version**: You SHOULD pin the Room version explicitly in the version catalog; do not float to `+`.
- **must-use-ksp**: You **MUST** use **KSP** (`androidx.room:room-compiler` via the KSP plugin) for the annotation processor. KAPT is legacy and roughly 2x slower; Room 3.0 removes KAPT support entirely.
- **should-export-schema**: You **SHOULD** enable schema export (`room.schemaLocation`) and commit the generated JSON schema so migrations can be diffed and tested.
- **should-return-flow-for-observable-reads**: Observable reads **SHOULD** return `kotlinx.coroutines.flow.Flow<T>` (or `Flow<List<T>>`). Room re-emits automatically whenever an underlying table changes — no manual invalidation.
- **should-suspend-one-shot-reads-and-writes**: One-shot reads and all writes (`@Insert`, `@Update`, `@Delete`, `@Query` DML) **SHOULD** be `suspend` functions so they run off the main thread on a Room-managed dispatcher.
- **must-not-call-blocking-dao-on-main-thread**: You **MUST NOT** call blocking (non-`suspend`, non-reactive) DAO functions on the main thread; Room throws `IllegalStateException` unless `allowMainThreadQueries()` is set.
- **should-not-allow-main-thread-queries-outside-tests**: `allowMainThreadQueries()` is what stops Room throwing on main-thread queries; you **SHOULD NOT** use it outside tests.
- **must-not-mark-reactive-returns-suspend**: Reactive return types (`Flow`, and `Flowable`/`Observable` via the RxJava artifact) **MUST NOT** be marked `suspend`.
- **must-wrap-atomic-multi-statement-work-in-transaction**: Any operation that issues **more than one statement and must be atomic** (read-modify-write, multi-table insert, batch upsert with dependent rows) **MUST** be wrapped in a single transaction — annotate the DAO method with `@Transaction`, or call `db.withTransaction { ... }` from suspend code.
- **must-use-transaction-on-relation-queries**: `@Transaction` **MUST** also be on `@Query` methods that return a `@Relation`-bearing POJO, so the parent and child reads see a consistent snapshot.
- **should-keep-transactions-short**: You SHOULD keep transactions short; do no network or long CPU work inside `withTransaction`.
- **should-define-one-entity-per-normalized-table**: You SHOULD define one `@Entity` per normalized table.
- **should-declare-relationships-not-denormalize**: You SHOULD declare relationships with `@ForeignKey` and load them via `@Relation`, not by denormalizing.
- **must-index-foreign-key-columns**: Every `@ForeignKey` column **MUST** be indexed (`@Entity(indices = [Index("owner_id")])`).
- **should-treat-unindexed-fk-warning-as-error**: Room emits a build warning for unindexed foreign keys; you SHOULD treat it as an error to fix.
- **should-use-unique-index-for-natural-keys**: You SHOULD add an `@Index(unique = true)` for natural-key uniqueness instead of relying on app-side checks.
- **must-bump-version-and-supply-migration**: On every schema change you **MUST** bump the database `version` and supply a `Migration` (or an `@DeleteColumn`/`@RenameColumn`-driven auto-migration spec).
- **must-not-ship-destructive-migration-fallback**: You **MUST NOT** ship `fallbackToDestructiveMigration()` in a release build — it silently drops user data.
- **should-test-migrations**: You **SHOULD** add a `MigrationTestHelper`-based instrumented test that opens the exported schema at version N and migrates to N+1, asserting data survives.
- **must-not-hold-database-per-screen**: You MUST NOT hold the `RoomDatabase` instance per-screen; build one application-scoped singleton via `Room.databaseBuilder(...)`.
- **must-not-expose-livedata-to-coroutine-consumers**: You MUST NOT expose `LiveData` for new code when the consumer is a coroutine/Compose layer; prefer `Flow`.
- **must-not-split-multi-step-writes-without-transaction**: You MUST NOT perform multi-step writes as separate suspend calls without a transaction — a crash between calls leaves a partial, inconsistent state.
