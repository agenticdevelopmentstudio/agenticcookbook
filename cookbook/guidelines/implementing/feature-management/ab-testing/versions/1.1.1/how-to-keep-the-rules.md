
- **Interface.** Expose one call that evaluates an experiment by key and takes the default at the call site, for example `variant(key, default) -> String`. Wrap any vendor SDK (OpenFeature, LaunchDarkly, GrowthBook, Statsig, Optimizely, Azure App Configuration, Firebase Remote Config) behind it; the vendor-neutral OpenFeature API evaluates by key with a required default and reports the resolved variant name in its evaluation details.
- **Failure.** Catch every error inside the provider, return the default, and log the failure; never let an experiment take a feature down.
- **Control.** Make control the default and the kill switch: disabling an experiment gives everyone control, whatever their bucket or override.
- **Overrides.** In an app, let testers force a user or device into any variant from the debug panel's A/B test variant picker, which [adc.guideline.implementing.feature-management.debug-mode](cookbook:e446ee3e-b8f2-40e7-b93d-3113e6a95e5d) requires, and keep the panel out of release builds. Elsewhere, add such an override where testers need one. If a variant must be forceable in production (a cookie, header or query parameter), authenticate or sign it and document it; otherwise accept no override in production.
- **Assignment.** Hash `userId + experimentId` (MurmurHash is common) into a fixed range and map sub-ranges to variants. Nothing needs to be stored; the bucket is recomputed on every evaluation. When a configuration change would move users, turn on sticky bucketing first.
- **Exposure.** Log exposure in the code path that renders or runs the variant, not where the variant is fetched. If the SDK logs exposure on evaluation, evaluate where the variant is used, or disable automatic exposure and log it manually there. With Firebase, fire the activation event at that point.
- **Before launch.** Write down the hypothesis, the decision metric, the effect to detect, the power, and the resulting minimum sample size and run time.
- **During the run.** Ramp from a small percentage, with automatic shutdown on significant harm; write down the starting percentage, the steps and the shutdown significance level before launch. Do not stop or extend on interim significance.
- **Analysis.** Run the SRM check first; filter bots; compare event loss per variant; segment by day; investigate any surprising result.
- **Validation.** Run A/A tests on the experimentation system, and keep running them alongside real experiments: check that users split by the planned percentages, that the collected data matches the system of record, and that results come out non-significant about 95% of the time.
- **Web.** Apply client-side variant changes synchronously, for example in CSS, before first paint. Serve crawlers exactly what humans see. For alternate URLs, redirect with a 302 and put `rel=canonical` to the original on each alternate. When the test ends, remove its alternate URLs and testing scripts.
- **iOS.** Ship every variant in the reviewed binary and select it by configuration; never download code that adds or changes a feature. Describe each variant with specificity in the Notes for Review in App Store Connect and make each one accessible for review.
- **Store pages.** Test icons, screenshots, previews and descriptions with Apple product page optimization or Google Play store listing experiments, not with an in-app experiment.
