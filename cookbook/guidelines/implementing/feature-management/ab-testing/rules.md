
- **experiment-provider-interface**: Features that may need experimentation SHOULD support variant assignment via an `ExperimentProvider` interface (for example `variant(key, default) -> String`), evaluated by experiment key, with the default variant supplied by the caller at each call site. (claims: openfeature-typed-evaluation-with-default, openfeature-variant-field, azure-variant-flags, sdks-take-call-site-default)
- **local-default-with-debug-override**: Every experiment MUST have a local default variant, and that default SHOULD be control, the variant every user gets when the experiment is off or aborted. Testers MAY be able to force a chosen variant through a debug override; in an app, that override MUST be the A/B test variant picker that [adc.guideline.implementing.feature-management.debug-mode](cookbook:e446ee3e-b8f2-40e7-b93d-3113e6a95e5d)'s `debug-only-config-panel` requires in the debug panel. The debug panel's override MUST NOT be reachable in release builds; any other override reachable in production (a cookie, header or query parameter) SHOULD be authenticated or signed and SHOULD be documented as added attack surface, as that guideline's `production-overrides-are-guarded` asks, and where no such override is needed, production SHOULD accept none. (claims: control-is-the-abort-state, azure-kill-switch-default-variant, forced-variants-for-qa, dev-override-off-in-production)
- **deterministic-hash-assignment**: Variant assignment MUST give a user the same variant on every visit for the length of the experiment, and MUST be independent of the user's assignment in every other experiment; it SHOULD be a deterministic hash of the user identifier together with the experiment identifier, partitioned among the variants. (claims: hash-user-and-experiment-id, consistent-assignment-across-visits, no-correlation-between-experiments, optimizely-murmurhash-bucketing, launchdarkly-recomputes-assignment, growthbook-hash-and-tracking-callback)
- **stable-assignment-when-allocation-changes**: Raising a variant's allocation MAY keep users already assigned in place (monotonic ramp-up); if allocation, seed or targeting must change mid-experiment in a way that reshuffles buckets, assignments MUST be persisted (sticky) first. (claims: monotonic-ramp-up-keeps-assignments, reallocation-reshuffles-users, sticky-bucketing-persists-assignment)
- **evaluation-never-fails-returns-default**: Variant evaluation MUST NOT throw or otherwise fail; on any error it MUST return the caller-supplied default. (claims: evaluation-returns-default-on-error, sdks-take-call-site-default)
- **log-exposure-at-point-of-use**: The exposure event SHOULD be logged at the point where the user first sees the varied experience, not at assignment, and the analysis SHOULD include only exposed users. (claims: log-exposure-when-variant-is-seen, launchdarkly-variation-records-exposure, statsig-disable-exposure-logging, growthbook-hash-and-tracking-callback, firebase-activation-event, assignment-without-exposure-dilutes, openfeature-tracking-api)
- **pre-register-metric-and-sample-size**: Before an experiment starts, its hypothesis, its decision metrics and its minimum sample size (from the chosen power, the effect to detect and the metric's variance) SHOULD be recorded. (claims: pre-register-hypothesis-and-metrics, compute-minimum-sample-size, underpowered-experiments-common-mistake)
- **no-peeking**: An experiment SHOULD NOT be stopped or extended because an interim result reached or missed significance; it SHOULD run to a sample size fixed before it started, unless it uses a sequential or Bayesian design built for interim looks. (claims: peeking-inflates-false-positives, stopping-or-extending-is-common-mistake)
- **check-sample-ratio-mismatch**: Every experiment's analysis SHOULD test the observed split against the configured split (for example, a chi-square test), and MUST NOT report results while a sample ratio mismatch is unexplained. (claims: check-sample-ratio-mismatch, srm-invalidates-results, srm-is-common)
- **validate-with-aa-tests**: The experimentation system SHOULD be validated with A/A tests that confirm the planned split, that the data matches the system of record, and that results are non-significant about 95% of the time. (claim: run-aa-tests)
- **ramp-up-with-auto-abort**: A treatment SHOULD start on a small percentage of users and ramp up in steps, and SHOULD be shut down automatically when it significantly underperforms control; the team chooses the starting percentage, the ramp steps and the significance level that triggers shutdown, and SHOULD record them before launch. (claim: ramp-up-and-auto-abort)
- **guard-data-quality**: The analysis SHOULD filter bots and SHOULD measure client telemetry loss per variant, and a surprising result, positive or negative, SHOULD be investigated as a possible bug before it is acted on. (claims: client-telemetry-loss-biases-results, robots-skew-results, twymans-law)
- **watch-novelty-effects**: The analysis SHOULD segment the effect by day to detect novelty or primacy effects before a lift is trusted. (claim: novelty-and-primacy-effects)
- **avoid-web-flicker**: A client-side web test SHOULD apply its visual changes before first paint (synchronously, for example via CSS) so the original page never flashes before the variant. (claim: web-flicker)
- **web-tests-follow-search-guidance**: A web test MUST NOT serve search crawlers different URLs or content than humans; alternate URLs SHOULD use 302 redirects and `rel=canonical` to the original; and the test SHOULD run only as long as needed, its code removed afterwards. (claims: google-search-no-cloaking, google-search-302-and-canonical, google-search-end-tests-promptly)
- **app-variants-ship-in-reviewed-binary**: In an iOS app, a variant MUST NOT depend on downloaded code that introduces or changes features, and MUST NOT be hidden from App Review or undocumented; every variant MUST be described with specificity in the Notes for Review and be accessible for review, and SHOULD ship in the reviewed binary and be selected by configuration. (claims: apple-review-notes-describe-changes, apple-no-hidden-features, apple-no-downloaded-code)
- **store-page-tests-use-store-tools**: A test of an App Store or Google Play store page SHOULD use the store's own tool, Apple product page optimization or Google Play store listing experiments, not an in-app experiment. (claims: apple-product-page-optimization, google-play-store-listing-experiments)
