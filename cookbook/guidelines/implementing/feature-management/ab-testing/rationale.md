
- `experiment-provider-interface`: OpenFeature, LaunchDarkly and GrowthBook evaluate by key with a default supplied at the call site, and Azure's variant flags expose named variants by key, so one interface of that shape can wrap any of them and keeps vendor code out of features. It is a SHOULD because a feature that will never be experimented on needs no provider; whether the interface returns a variant name or a typed value is open (OpenFeature returns typed values and reports the variant name in evaluation details).
- `local-default-with-debug-override`: The local default is a MUST because `evaluation-never-fails-returns-default` requires every failed evaluation to return the caller-supplied default, which an experiment without one cannot do; the MUST rests on that rule, not on this rule's claims. Control is the SHOULD default because it is the safe state: when a variant misbehaves the experiment is aborted and everyone gets control, as Azure's `DefaultWhenDisabled` does. A default other than control is acceptable only when the team records why. The override is a MAY for experimentation systems in general because the source calls forcing a variant something an experimentation system "may support" to make testing easier. In an app it is a MUST, and that MUST comes from debug-mode's `debug-only-config-panel`, which is cookbook policy requiring a debug panel with an A/B test variant picker, not from this guideline's research; this rule does not relax it. Keeping the debug panel's override out of release builds is a MUST because [adc.guideline.implementing.feature-management.debug-mode](cookbook:e446ee3e-b8f2-40e7-b93d-3113e6a95e5d) requires the panel itself to be compiled out of them. Override tooling in production exposes internal flags and experiments, and the vendor that warns of this recommends disabling it in production "in most cases"; so any other override reachable in production is a SHOULD, authenticated or signed and documented as added attack surface as debug-mode's `production-overrides-are-guarded` asks, and accepted only where it is needed.
- `deterministic-hash-assignment`: Consistent assignment across visits and no correlation between concurrent experiments are required properties of a sound assignment method (Kohavi et al., "must"). Hashing user ID with experiment ID is the standard way to get both with no stored state (Optimizely, LaunchDarkly, GrowthBook), so it is the SHOULD default; another method is acceptable when it provably keeps both MUST properties.
- `stable-assignment-when-allocation-changes`: Monotonic ramp-up, raising a treatment's percentage without changing earlier assignments, is an optional property an assignment method "may support", so it is a MAY; a raise that does move users already assigned is a reshuffling change, and the MUST below applies to it. Reducing and re-raising allocation or changing the seed reshuffles users (Optimizely, LaunchDarkly), and it can cause a sample ratio mismatch that invalidates the results; sticky bucketing is the platforms' mechanism for keeping assignments through such a change. Those claims alone describe harm, which would make a SHOULD; the MUST rests on `deterministic-hash-assignment`, whose MUST that a user gets the same variant on every visit a reshuffle of users already assigned would break. So persisting assignments first is a MUST.
- `evaluation-never-fails-returns-default`: OpenFeature requires that evaluation never throw and always return the default on abnormal execution. An experiment is optional behaviour, so its failure must degrade to the default.
- `log-exposure-at-point-of-use`: Users assigned but never exposed behave like control and dilute the measured effect, and SDKs differ on when exposure is logged (LaunchDarkly and GrowthBook on evaluation, Statsig optionally manual, Firebase on an activation event), so the point of evaluation has to be the point of use. Kohavi presents first-exposure recording as a variance-reduction technique, not a mandate, so the rule is a SHOULD; logging at assignment is acceptable where assignment and exposure are the same moment.
- `pre-register-metric-and-sample-size`: The hypothesis and its metrics are the first step in designing an experiment, and the minimum sample size follows from power, effect and variance; underpowered experiments are a common mistake. The sources recommend rather than require it, so it is a SHOULD; a sequential or Bayesian design that sets its stopping rule in advance instead of a fixed sample size is an acceptable deviation.
- `no-peeking`: Repeated significance testing always raises the false-positive rate, and stopping early or extending are among the most common mistakes experimenters make. The sources describe harm, not a requirement, so the rule is a SHOULD NOT; a sequential or Bayesian design built for interim looks is the allowed deviation.
- `check-sample-ratio-mismatch`: An SRM means something is wrong with the sampling and in most cases invalidates the results, so reporting results over an unexplained SRM is a MUST NOT. SRMs are not rare (about 6% of A/B tests at Microsoft). The chi-square test is what the sources suggest ("can be used"), so running it is a SHOULD; any test of the observed against the configured split serves.
- `validate-with-aa-tests`: A/A tests show whether users are split by the planned percentages, whether the data matches the system of record, and whether results are non-significant about 95% of the time, which validates the system rather than one experiment. It is a SHOULD because a team on a platform already validated this way may rely on that validation.
- `ramp-up-with-auto-abort`: Starting a treatment on a small percentage limits how many users a bad treatment reaches, and a system that analyses data in near-real-time can shut down a treatment that significantly underperforms control. The sources recommend it and set no thresholds, so it is a SHOULD and the team records its own values; a change with no user-facing risk may launch at its full allocation.
- `guard-data-quality`: Bots can skew metrics enough to render assumptions invalid, mobile telemetry loss can differ by variant and bias results, and per Twyman's law a surprising movement, positive or negative, usually means a bug. The sources say these should be done, so each clause is a SHOULD; bot filtering may be skipped where no bot traffic reaches the measured surface, and loss measurement where no client telemetry is used.
- `watch-novelty-effects`: Short-term effects can fade (novelty) or grow (primacy), so a lift seen in the first days may not last; segmenting by day shows the trend. It is a SHOULD because a test whose effect cannot change with familiarity (a one-time flow, for example) gains little from it.
- `avoid-web-flicker`: A client-side test that applies its changes after the page renders shows users the original before the variant, which both harms the experience and contaminates the comparison; applying changes synchronously, for example in CSS, prevents it. It is a SHOULD because the guidance is vendor-specific (Optimizely), and server-side tests do not flicker at all.
- `web-tests-follow-search-guidance`: Google treats serving crawlers different content from humans as cloaking whether or not a test is running, so that is a MUST NOT. 302 redirects, `rel=canonical` on alternates and short tests with their code removed are Google's recommended practices, not requirements, so they are SHOULD; a test with no alternate URLs needs neither redirect nor canonical.
- `app-variants-ship-in-reviewed-binary`: Apple's App Review forbids downloading code that introduces or changes features and forbids hidden, dormant or undocumented features, so both are MUST NOT. Guideline 2.3.1(a) says all new features, functionality and product changes "must be described with specificity in the Notes for Review" and be "accessible for review"; a variant is such a change, so describing it there and keeping it accessible for review is a MUST. Shipping every variant in the binary and selecting it by configuration is the design that satisfies these, but Apple does not prescribe it, so it is a SHOULD; another design that keeps every variant reviewed and downloads no feature code is acceptable.
- `store-page-tests-use-store-tools`: Apple's product page optimization and Google Play's store listing experiments are the stores' sanctioned surfaces for testing store pages, with review of the new metadata built in. It is a SHOULD because a test of something other than the store page itself belongs in the app.
