# Research: debug-mode

The topic's core holds: debug and test features must not be reachable in release builds (Google's Android security guidance, CWE-489, Apple App Review 2.5.19), and compile-time guards (Swift #if with Xcode's DEBUG condition, C# #if DEBUG and [Conditional], Vite import.meta.env.DEV, webpack's DefinePlugin NODE_ENV) remove the code from release. Flag-override, variant-override, event-log and environment-info functions are what existing tools provide (GrowthBook DevTools, Firebase DebugView, Pulse, FLEX). The TypeScript rule's Ctrl+Shift+D shortcut is contradicted: Chrome binds it. The topic is missing: compile code out rather than hide it at runtime (Android: not-exported is no protection); give the panel to internal/staging and TestFlight builds, not only Debug; release builds non-debuggable with debug logging off and redacted; flag-SDK dev modes and developer exception pages off in production; no secrets in client-side debug config; filter debug traffic out of analytics; guard production-time overrides; pick access gestures that do not collide with system gestures (shake is iPhone undo); on Android, BuildConfig is not generated by default since AGP 8, so prefer debug source sets or enable it; on Node servers NODE_ENV is always production.

## Best practices

*Best practices: what is current best practice for this topic?*

- **debug-features-out-of-production**: Test and debug features, hidden menus among them, must not ship reachable in production builds, because they can be used to alter the app's flow or retrieve system information. Quote: "Releasing production builds that include Testing or Debug features can negatively impact the security posture of the application. These functionalities are used to help developers discover and identify bugs within intended application use cases prior to, or after a new version release, and shouldn't be publicly accessible." Source: [Test and debug features (OWASP category: MASVS-CODE: Code Quality)](https://developer.android.com/privacy-and-security/risks/test-debug); [CWE-489: Active Debug Code](https://cwe.mitre.org/data/definitions/489.html). Trust 88 (multi-independent): Platform owner's security guidance (Google, mapped to OWASP MASVS-CODE), independently corroborated by MITRE CWE-489 ('The product is released with debugging code still enabled or active.'); stable principle.
- **hidden-menus-are-debug-features**: The platform owner names hidden menus, debug-log toggles and options that alter application flow as examples of test/debug features. Quote: "Examples of Testing/ Debug features are: Hidden menus Options to enable debug logs Options to alter application flow Options to circumvent payment or subscription processes Options to circumvent authentication Tests for application-specific activities" Source: [Test and debug features (OWASP category: MASVS-CODE: Code Quality)](https://developer.android.com/privacy-and-security/risks/test-debug). Trust 80 (single): Google's own risk catalogue; a definition, single source but authoritative for Android.
- **runtime-hiding-is-not-protection**: Hiding a debug component at runtime (for example marking it not exported) is not a valid protection; debug functionality must not be implemented in production components at all. Quote: "Test or debug functionalities should never be implemented within production application components such as activities, broadcast receivers, services or content providers since, if exported, can be run by any other process on the device. Setting the debug component as not exported ( android:exported="false" ) does not constitute a valid protection for the capabilities since any rooted device can still execute it through the Android Debug Bridge (ADB) tool if the debug option is enabled." Source: [Test and debug features (OWASP category: MASVS-CODE: Code Quality)](https://developer.android.com/privacy-and-security/risks/test-debug). Trust 82 (single): Platform owner's security guidance; consistent with Apple guideline 2.5.19 (claim app-review-no-hidden-features) on hidden features in the binary.
- **dedicated-debug-or-staging-build**: Debug and test features belong in a dedicated debug or staging build given to a restricted set of developers and testers, not in the production build. Quote: "The execution of any test or debug function within applications should be limited only to a restricted set of Staging builds to allow only developers to debug or test application's features in a controlled environment. This can be obtained by creating a dedicated test or debug build of the application and advanced instrumented tests for it in order to ensure that any test or debug feature is run on an isolated version." Source: [Test and debug features (OWASP category: MASVS-CODE: Code Quality)](https://developer.android.com/privacy-and-security/risks/test-debug). Trust 82 (single): Google platform guidance; corroborated in practice by Pulse shipping its console to 'everyone who has your test builds' (claim pulse-console-in-test-builds).
- **debug-only-source-set**: Android source sets let debug-only code (for example logging functionality) be compiled only into variants of the debug build type, which excludes it from release at compile time. Quote: "For example, you can define basic functionality in the main/ source set and use product flavor source sets to change the branding of your app for different clients, or include special permissions and logging functionality only for build variants that use the debug build type." Source: [Configure build variants](https://developer.android.com/build/build-variants). Trust 85 (single): Current Android Developers build documentation (updated 2026-11-13); authoritative for the mechanism.
- **expose-build-and-flag-state**: Expose the build/version metadata and the current feature-flag configuration so a developer, tester or operator can see exactly what is running. Quote: "It's always been a helpful practice to embed build/version numbers into a deployed artifact and expose that metadata somewhere so that a dev, tester or operator can find out what specific code is running in a given environment. The same idea should be applied with feature flags. Any system using feature flags should expose some way for an operator to discover the current state of the toggle configuration." Source: [Feature Toggles (aka Feature Flags)](https://martinfowler.com/articles/feature-toggles.html). Trust 70 (single): Secondary source (Pete Hodgson on martinfowler.com, a widely cited reference) used because no platform owner documents debug-panel contents; corroborated in tooling by GrowthBook DevTools showing flag state and an evaluation debug log (claim growthbook-devtools-overrides).
- **analytics-debug-event-stream**: The analytics vendor's own debug mode shows raw logged events from development devices in near real time to validate instrumentation, enabled per device outside the release configuration. Quote: "DebugView lets you to see the raw event data logged by your app on development devices in near real-time. This is very useful for validation purposes during the instrumentation phase of development and can help you discover errors and mistakes in your Analytics implementation and confirm that all events and user properties are logged correctly." Source: [Monitor collected events and user properties using DebugView](https://firebase.google.com/docs/analytics/debugview). Trust 84 (single): Google Firebase's own documentation, current (updated 2026-11-12).
- **exclude-debug-traffic-from-analytics**: Events logged in analytics debug mode still reach exports, so developer and test traffic should be filtered out of reports. Quote: "Note: Events logged while in debug mode are intended for real-time validation during development. These events are included in your daily BigQuery export by default. To prevent developer and test traffic from being processed and appearing in your reports or BigQuery exports, you should configure a developer traffic data filter within your Analytics property." Source: [Monitor collected events and user properties using DebugView](https://firebase.google.com/docs/analytics/debugview). Trust 82 (single): Vendor's own documentation for its own product; current.

## Known solutions

*Known solutions: what solutions, patterns, libraries and tools already exist, and how do they compare?*

- **flex-in-app-debugger-debug-only**: FLEX is an in-app iOS debugging and state-exploration toolbar that its maintainers say must be excluded from Release builds, gated with #if DEBUG, and opened by a gesture, keyboard shortcut or debug menu item. Quote: "Wrap the places in your code where you integrate FLEX with an `#if DEBUG` statement to ensure the tool is only accessible in your `Debug` builds and to avoid errors in your `Release` builds." Source: [FLEX README](https://raw.githubusercontent.com/FLEXTool/FLEX/master/README.md). Trust 72 (single): Project's own README (authoritative for the tool); its claim that an included FLEX gets an app rejected is the maintainers' statement, not Apple's.
- **flex-excluded-or-rejected**: FLEX's maintainers warn that shipping FLEX in a Release build leads to App Store rejection and give per-package-manager exclusion recipes. Quote: "Manually add the files in `Classes/` to your Xcode project, or just drag in the entire `FLEX/` folder. Be sure to exclude FLEX from `Release` builds or your app will be rejected." Source: [FLEX README](https://raw.githubusercontent.com/FLEXTool/FLEX/master/README.md); [App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/). Trust 66 (single): Tool README; the rejection risk is consistent with Apple guideline 2.5.19 against hidden features (claim app-review-no-hidden-features), but Apple names no tool.
- **pulse-console-in-test-builds**: Pulse is a native Apple-platform logging and network-inspection framework whose in-app console is meant to be available to everyone with the app's test builds, including QA. Quote: "This way Pulse console is available for everyone who has your test builds. You or your QA team can view the logs on the device and easily share them to attach to bug reports." Source: [Pulse README](https://raw.githubusercontent.com/kean/Pulse/main/README.md). Trust 70 (single): Project README, authoritative for what the tool does; single source.
- **chucker-no-op-release-artifact**: Chucker (Android HTTP inspector) ships a no-op library for release builds, wired with debugImplementation/releaseImplementation so release APKs contain no trace of it. Quote: "Please note that you should add both the `library` and the `library-no-op` variant to isolate Chucker from release builds as follows:" Source: [Chucker README](https://raw.githubusercontent.com/ChuckerTeam/chucker/develop/README.md). Trust 74 (single): Project README; the variant-scoped dependency mechanism it uses is documented by Google (claim variant-scoped-dependencies).
- **chucker-data-is-sensitive**: In-app network inspectors capture sensitive data such as Authorization and Cookie headers and bodies, so they are for development only and should redact headers. Quote: "**Warning** The data generated and stored when using Chucker may contain sensitive information such as Authorization or Cookie headers, and the contents of request and response bodies. It is intended for **use during development**, and not in release builds or other production deployments." Source: [Chucker README](https://raw.githubusercontent.com/ChuckerTeam/chucker/develop/README.md); [MASWE-0005: Insertion of Sensitive Data into Logs](https://mas.owasp.org/MASWE/MASVS-STORAGE/MASWE-0005/). Trust 76 (multi-independent): Tool README, corroborated independently by OWASP MASWE-0005 on sensitive data in debug logs.
- **hyperion-shake-plugin-drawer**: Hyperion-Android is a hidden plugin drawer opened by shaking the device, added as a debugImplementation dependency. Quote: "Once Hyperion is integrated into your app, simply shake your phone to activate." Source: [Hyperion-Android README](https://raw.githubusercontent.com/willowtreeapps/Hyperion-Android/develop/README.md). Trust 66 (single): Project README; the project's activity level was not established (see limitations).
- **rn-dev-menu-disabled-in-release**: React Native's Dev Menu, LogBox and DevTools are disabled in release builds; the Dev Menu opens by shaking the device or by keyboard shortcuts in simulators/emulators. Quote: "Debugging features, such as the Dev Menu, LogBox, and React Native DevTools are disabled in release (production) builds." Source: [Debugging Basics](https://raw.githubusercontent.com/facebook/react-native-website/main/docs/debugging.md). Trust 84 (single): Framework owner's documentation (Meta), current docs.
- **flipper-decoupled-from-react-native**: React Native moved away from Flipper as its default debugging tool, deprecating the native Flipper integration in 0.73 for removal, in favour of a new Chrome-DevTools-based debugger. Quote: "We are gradually moving away from Flipper as the default tool for debugging React Native apps. In 0.73, this begins by deprecating the native Flipper integration included with React Native (bootstrap code which wires up Flipper's core plugins). We will be removing this integration and dependency in the next release — meaning parts of Flipper such as the Network plugin will cease to work." Source: [React Native 0.73 - Debugging Improvements, Stable Symlink Support, and more](https://raw.githubusercontent.com/facebook/react-native-website/main/website/blog/2023-12-06-0.73-debugging-improvements-stable-symlinks.mdx). Trust 82 (single): Framework owner's release blog (2023-12-06); a dated, factual announcement.
- **browser-devtools-built-in**: On the web the browser ships its own developer tools, so a web debug panel supplements rather than replaces them. Quote: "Chrome DevTools is a set of web developer tools built directly into the Google Chrome browser." Source: [Chrome DevTools overview](https://developer.chrome.com/docs/devtools/overview). Trust 80 (single): Browser vendor's own documentation; definitional.
- **growthbook-devtools-overrides**: Flag vendors provide developer tools that override flag values and experiment variations and show an evaluation debug log, the same functions a debug panel's flag-override and variant-picker sections provide. Quote: "GrowthBook DevTools provides powerful debugging and testing tools, including: * A real-time view of active **feature flags** and **experiments** * The ability to **override flags and experiment variations** * A detailed **debug log** explaining how and why flags were evaluated" Source: [GrowthBook DevTools (Chrome extension)](https://docs.growthbook.io/tools/chrome-extension.md). Trust 76 (single): Vendor's own documentation for its own tool.
- **sdk-dev-mode-off-in-production**: A flag SDK's developer-tools mode exposes every internal flag and experiment, so the vendor recommends turning it off in production. Quote: "To avoid exposing all of your internal feature flags and experiments to users, we recommend setting this to `false` in production in most cases." Source: [JavaScript SDK](https://docs.growthbook.io/lib/js.md). Trust 78 (single): Vendor's own SDK documentation; consistent with the Microsoft developer-exception-page warning (claim aspnet-dev-page-development-only).

## Platform guidelines

*Platform guidelines: what do the platform owners' own guidelines say, for each platform the topic touches (Apple, Android, Windows, web, the databases and runtimes concerned)?*

- **swift-conditional-compilation**: In Swift, the statements in an #if block are compiled only if the compilation condition (which can be an identifier passed with -D) is true at compile time, so #if DEBUG code is absent from builds that do not define DEBUG. Quote: "Unlike the condition of an `if` statement, the *compilation condition* is evaluated at compile time. As a result, the *statements* are compiled and executed only if the *compilation condition* evaluates to `true` at compile time." Source: [Statements: Conditional Compilation Block (The Swift Programming Language)](https://raw.githubusercontent.com/swiftlang/swift-book/main/TSPL.docc/ReferenceManual/Statements.md). Trust 90 (single): The Swift language reference; stable language semantics.
- **xcode-active-compilation-conditions**: Xcode's SWIFT_ACTIVE_COMPILATION_CONDITIONS build setting supplies the conditions Swift #if tests; the Debug configuration of a new Swift target sets it to DEBUG. Quote: "A list of compilation conditions to enable for conditional compilation expressions." Source: [Build settings reference: Active Compilation Conditions](https://developer.apple.com/documentation/xcode/build-settings-reference); [Conditional Compilation, Part 1: Precise Feature Flags](https://davedelong.com/blog/2018/07/25/conditional-compilation-in-swift-part-1/). Trust 74 (single): Apple's build settings reference defines the setting; that the Debug configuration presets DEBUG rests on a secondary source (Dave DeLong: 'When you create a new Swift target, this build setting has the following value in the debug configuration: SWIFT_ACTIVE_COMPILATION_CONDITIONS = DEBUG') because no fetched Apple page states the default.
- **uikit-motion-ended-shake**: UIKit reports a shake as a motion event to the first responder and up the responder chain via motionEnded(_:with:), the hook a shake-to-open panel uses. Quote: "UIKit informs the responder only when a motion event starts and ends. It doesn’t report intermediate shakes. Motion events are delivered initially to the first responder and are forwarded up the responder chain as appropriate" Source: [motionEnded(_:with:)](https://developer.apple.com/documentation/uikit/uiresponder/motionended(_:with:)). Trust 86 (single): Apple's own API reference.
- **hig-shake-is-system-undo**: On iPhone, shaking is a standard system gesture for undo, and Apple warns that redefining standard gestures confuses people. Quote: "For example, people can use a three-finger swipe to initiate an undo or redo, or shake their iPhone. As with all standard gestures, redefining them in your interface runs the risk of confusing people and making your experience unpredictable." Source: [Undo and redo (Human Interface Guidelines)](https://developer.apple.com/design/human-interface-guidelines/undo-and-redo). Trust 84 (single): Apple Human Interface Guidelines; authoritative for Apple platforms.
- **app-review-no-hidden-features**: Apple's App Review Guidelines forbid hidden, dormant or undocumented features in a shipped app. Quote: "2.5.19 Don’t include any hidden, dormant, or undocumented features in your app; your app’s functionality should be clear to end users and App Review. Attempting to hide undocumented features in your app binary, such as through code obfuscation or other methods, is grounds for removal of your app from the App Store and termination of your developer account." Source: [App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/). Trust 92 (single): Apple's binding store policy, current page; corroborated in effect by the FLEX maintainers' rejection warning.
- **app-review-betas-use-testflight**: Apple routes pre-release and test builds through TestFlight rather than the App Store. Quote: "Demos, betas, and trial versions of your app don’t belong on the App Store – use TestFlight instead." Source: [App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/). Trust 88 (single): Apple's store policy.
- **android-release-not-debuggable**: Android release build types must be configured non-debuggable (isDebuggable = false), the debug build type being debuggable. Quote: "To configure whether the APK is debuggable, use the debuggable flag for Groovy or the isDebuggable flag for Kotlin script:" Source: [Prepare your app for release](https://developer.android.com/studio/publish/preparing); [MASTG-TEST-0039: Testing whether the App is Debuggable (deprecated v1 test)](https://mas.owasp.org/MASTG/tests/android/MASVS-RESILIENCE/MASTG-TEST-0039/). Trust 88 (multi-independent): Android's release checklist (updated 2026-11-13); corroborated by OWASP MASTG ('For a release build, this attribute should always be set to "false" (the default value).').
- **android-release-turn-off-logging**: Before release, Android apps should remove Log calls and Debug tracing calls, and disable WebView debugging. Quote: "Deactivate logging before you build your app for release. You can deactivate logging by removing calls to Log methods in your source files. Also, remove any log files or static test files that were created in your project." Source: [Prepare your app for release](https://developer.android.com/studio/publish/preparing). Trust 86 (single): Android platform release checklist, current.
- **android-debug-build-type-defaults**: Android Studio creates debug and release build types; the debug type is debuggable and signed with a generic debug keystore. Quote: "When you create a new module, Android Studio automatically creates the debug and release build types. Although the debug build type doesn't appear in the build configuration file, Android Studio configures it with debuggable true. This lets you debug the app on secure Android devices and configures app signing with a generic debug keystore." Source: [Configure build variants](https://developer.android.com/build/build-variants). Trust 86 (single): Current Android build documentation.
- **variant-scoped-dependencies**: Gradle dependency configurations can be scoped to a build variant by prefixing the configuration name (e.g. debugImplementation), keeping debug-only libraries out of release. Quote: "If you instead want to declare a dependency for only a specific build variant source set or for a testing source set, you must capitalize the configuration name and prefix it with the name of the build variant or testing source set." Source: [Add build dependencies](https://developer.android.com/build/dependencies); [Chucker README](https://raw.githubusercontent.com/ChuckerTeam/chucker/develop/README.md); [Hyperion-Android README](https://raw.githubusercontent.com/willowtreeapps/Hyperion-Android/develop/README.md). Trust 86 (multi-independent): Android build documentation, corroborated by independent tools that use debugImplementation (Chucker, Hyperion).
- **agp8-buildconfig-not-generated**: Since Android Gradle Plugin 8.0, BuildConfig (and so BuildConfig.DEBUG) is not generated by default; a module must opt in with buildFeatures.buildConfig. Quote: "AGP 8.0 doesn't generate BuildConfig by default. You need to specify this option using the DSL in the projects where you need it." Source: [Android Gradle plugin 8.0.0 release notes](https://developer.android.com/build/releases/past-releases/agp-8-0-0-release-notes). Trust 88 (single): Android Gradle plugin release notes, platform owner.
- **android-shake-needs-sensors**: Android has no shake-gesture API; shake detection is built on the motion sensors (accelerometer). Quote: "Motion sensors are useful for monitoring device movement, such as tilt, shake, rotation, or swing." Source: [Motion sensors](https://developer.android.com/develop/sensors-and-location/sensors/sensors_motion). Trust 70 (single): Android sensor documentation; that no higher-level shake API exists is inferred from its absence on this page.
- **dotnet-if-debug**: In C#, the DEBUG symbol is set by the Debug/Release build configuration and #if DEBUG code is compiled only when it is defined. Quote: "Other predefined symbols include the `DEBUG` and `TRACE` constants. Use `#define` to override the values set for the project. The `DEBUG` symbol, for example, is automatically set depending on your build configuration properties ("Debug" or "Release" mode)." Source: [C# preprocessor directives](https://raw.githubusercontent.com/dotnet/docs/main/docs/csharp/language-reference/preprocessor-directives.md). Trust 90 (single): Microsoft's C# language reference (2026-01-16).
- **dotnet-conditional-attribute**: C#'s [Conditional("DEBUG")] removes calls to a void method when DEBUG is undefined, and Microsoft calls it less error-prone than #if blocks. Quote: "When a method marked conditional is called, the presence or absence of the specified preprocessing symbol determines whether the compiler includes or omits calls to the method. If the symbol is defined, the call is included; otherwise, the call is omitted. A conditional method must be a method in a class or struct declaration and must have a `void` return type. Using `Conditional` is cleaner, more elegant, and less error-prone than enclosing methods inside `#if…#endif` blocks." Source: [Attributes interpreted by the C# compiler: Conditional](https://raw.githubusercontent.com/dotnet/docs/main/docs/csharp/language-reference/attributes/general.md). Trust 90 (single): Microsoft's C# language reference (2026-02-17).
- **aspnet-dev-page-development-only**: Microsoft says to enable ASP.NET Core's developer exception page only in the Development environment and never to share detailed exception information in production. Quote: "Don't enable the Developer Exception Page **unless the app is running in the `Development` environment**. Don't share detailed exception information publicly when the app runs in production." Source: [Handle errors in ASP.NET Core: Developer exception page](https://raw.githubusercontent.com/dotnet/AspNetCore.Docs/main/aspnetcore/includes/developer-exception-page.md). Trust 86 (single): Microsoft's own documentation.
- **vite-dev-flag-tree-shaken**: Vite statically replaces import.meta.env.DEV at build time, so code inside if (import.meta.env.DEV) is removed from production builds. Quote: "Vite exposes certain constants under the special `import.meta.env` object. These constants are defined as global variables during dev and statically replaced at build time to make tree-shaking effective." Source: [Env Variables and Modes](https://raw.githubusercontent.com/vitejs/vite/main/docs/guide/env-and-mode.md). Trust 86 (single): Vite's own documentation; current.
- **webpack-mode-defines-node-env**: webpack's mode sets process.env.NODE_ENV through DefinePlugin, so client-side NODE_ENV checks are compile-time constants in a webpack bundle. Quote: "| `production`  | Sets `process.env.NODE_ENV` on `DefinePlugin` to value `production`. Enables deterministic mangled names for modules and chunks, `FlagDependencyUsagePlugin`, `FlagIncludedChunksPlugin`, `ModuleConcatenationPlugin`, `NoEmitOnErrorsPlugin` and `MinimizerPlugin`. |" Source: [Mode](https://raw.githubusercontent.com/webpack/webpack.js.org/main/src/content/configuration/mode.mdx). Trust 84 (single): webpack's own configuration documentation.
- **node-env-only-production-on-servers**: Node.js says setting NODE_ENV to anything but production is an antipattern because it makes environments behave differently; servers should always run with NODE_ENV=production. Quote: "While this might look harmless, it makes the production and staging environments different, thus making reliable testing impossible. For example a test and thus a functionality of your product could pass when `NODE_ENV` is set to `development` but fail when setting `NODE_ENV` to `production`. Therefore, setting `NODE_ENV` to anything but `production` is considered an _antipattern_." Source: [Node.js, the difference between development and production](https://nodejs.org/en/learn/getting-started/nodejs-the-difference-between-development-and-production). Trust 84 (single): Node.js project's own documentation.
- **chrome-binds-ctrl-shift-d**: Chrome binds Ctrl+Shift+D to saving all open tabs as bookmarks, so a web app's Ctrl+Shift+D shortcut collides with a browser command. Quote: "Save all open tabs as bookmarks in a new folder | Ctrl + Shift + d" Source: [Chrome keyboard shortcuts](https://support.google.com/chrome/answer/157179?hl=en&co=GENIE.Platform%3DDesktop). Trust 84 (single): Google's own Chrome Help page (Windows/Linux table; quote is the table row's two cells).
- **typescript-debug-access-prior**: Access via `/debug` route or keyboard shortcut (`Ctrl+Shift+D`), guarded by `process.env.NODE_ENV === 'development'`. Quote: "Access via `/debug` route or keyboard shortcut (`Ctrl+Shift+D`), guarded by `process.env.NODE_ENV === 'development'`." Source: [debug-mode (typescript.md)](git:2071c94e51a8c517e11178fdee54e0ec033064c2:cookbook/guidelines/implementing/feature-management/debug-mode/typescript.md). Trust 0 (uncorroborated): contradicted by chrome-binds-ctrl-shift-d (the named shortcut is a Chrome browser command); the NODE_ENV guard itself is supported for bundled client code by webpack-mode-defines-node-env

## The expert's view

*The expert's view: if we hired an expert consultant in this topic, what would they tell us: what to do, what to avoid, and what people usually get wrong?*

- **remove-debug-code-before-deploy**: Security catalogues classify releasing a product with debugging code still enabled as a weakness, mitigated by removing debug code before deployment. Quote: "Remove debug code before deploying the application." Source: [CWE-489: Active Debug Code](https://cwe.mitre.org/data/definitions/489.html); [Test and debug features (OWASP category: MASVS-CODE: Code Quality)](https://developer.android.com/privacy-and-security/risks/test-debug). Trust 86 (multi-independent): MITRE CWE (standards catalogue), independently corroborated by Google's Android guidance.
- **debug-feature-impact**: A debug feature reachable in production can bypass paywalls and protections or leak system and user information, with impact proportional to the feature's permissions. Quote: "Such functionalities within an application can be used to circumvent a number of protections, bypass paywalls, retrieve system or user related information, or trigger testing activities." Source: [Test and debug features (OWASP category: MASVS-CODE: Code Quality)](https://developer.android.com/privacy-and-security/risks/test-debug). Trust 80 (single): Platform owner's security guidance.
- **debug-statements-never-in-release**: Security testers check that debug statements and debug views are guarded so they are never present in the release build. Quote: "As a developer, incorporating debug statements into your application's debug version should not be a problem as long as you make sure that the debug statements are never present in the application's release version." Source: [MASTG-TEST-0084: Testing for Debugging Code and Verbose Error Logging (deprecated v1 test)](https://mas.owasp.org/MASTG/tests/ios/MASVS-RESILIENCE/MASTG-TEST-0084/). Trust 74 (single): OWASP MASTG; the test is a deprecated v1 test superseded by v2 logging tests, so currency is reduced.
- **debug-logs-hold-sensitive-data**: Verbose debug logging shipped in release leaks sensitive data; disable debug log levels in production builds and redact sensitive values. Quote: "Use Log Levels Properly: Assign debug-only details to debug or verbose levels and ensure those levels are disabled in production releases." Source: [MASWE-0005: Insertion of Sensitive Data into Logs](https://mas.owasp.org/MASWE/MASVS-STORAGE/MASWE-0005/); [Prepare your app for release](https://developer.android.com/studio/publish/preparing). Trust 84 (multi-independent): OWASP MASWE-0005, corroborated independently by Android's release checklist ('Deactivate logging before you build your app for release.').
- **no-secrets-in-client-bundle**: Values compiled into a client bundle (for example a debug panel's environment config) are public; API keys and secrets must not be put there. Quote: "`VITE_*` variables should _not_ contain sensitive information such as API keys. The values of these variables are bundled into your source code at build time. For production deployments, consider a backend server or serverless/edge functions to properly secure secrets." Source: [Env Variables and Modes](https://raw.githubusercontent.com/vitejs/vite/main/docs/guide/env-and-mode.md). Trust 80 (single): Vite's own documentation; general principle consistent with OWASP MASWE storage guidance but only this source quoted.
- **production-overrides-widen-attack-surface**: Overriding flags in production (per-request cookie, header or query parameter) lets testers check unreleased features but lets curious or malicious users flip them too; signing the override reduces but does not remove the risk. Quote: "The downside of this per-request approach is that it introduces a risk that curious or malicious end-users may modify feature toggle state themselves. Some organizations may be uncomfortable with the idea that some unreleased features may be publicly accessible to a sufficiently determined party. Cryptographically signing your override configuration is one option to alleviate this concern, but regardless this approach will increase the complexity - and attack surface - of your feature toggling system." Source: [Feature Toggles (aka Feature Flags)](https://martinfowler.com/articles/feature-toggles.html). ### Open questions

- Whether the panel should be Debug-only or also present in internal/staging/TestFlight builds: Google recommends a dedicated staging build and Pulse targets test builds, while `#if DEBUG` alone removes it from TestFlight (Release-configuration) builds; the owner decides which configuration the rule names.
- No source mandates that every app MUST include a debug panel; the requirement is a cookbook policy choice, supported here only in that its contents and its exclusion from release match platform and vendor practice.
- Whether to keep shake as the iOS access gesture given Apple's HIG reserves shake for undo; in a Debug-only build the collision affects only developers.
