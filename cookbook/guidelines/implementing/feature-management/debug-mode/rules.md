
- **debug-only-config-panel**: Apps MUST include a debug-only configuration panel (not in release builds) with feature flag overrides, an analytics event log, an A/B test variant picker, and environment info (version, build, OS, device). (claims: debug-features-out-of-production, hidden-menus-are-debug-features, growthbook-devtools-overrides, analytics-debug-event-stream, expose-build-and-flag-state, rn-dev-menu-disabled-in-release)
- **platform-access-methods**: The panel SHOULD be reached, and guarded, per platform by these access methods: on Apple iOS by a shake gesture (UIKit's `motionEnded(_:with:)`), guarded by `#if DEBUG`; on Apple macOS by a Debug menu item, guarded by `#if DEBUG`; on Android by a shake gesture, its code in the debug source set (`src/debug/`); on the web by a client-side `/debug` route in the bundled code, guarded by `NODE_ENV === 'development'`, which the bundler replaces at build time; on Windows by a debug-only settings page, guarded by `#if DEBUG`. (claims: uikit-motion-ended-shake, swift-conditional-compilation, xcode-active-compilation-conditions, flex-in-app-debugger-debug-only, hyperion-shake-plugin-drawer, rn-dev-menu-disabled-in-release, android-debug-build-type-defaults, debug-only-source-set, dotnet-if-debug, webpack-mode-defines-node-env)
- **typescript-debug-access**: In TypeScript, the panel SHOULD be reached this way: Access via `/debug` route or keyboard shortcut (`Ctrl+Shift+D`), guarded by `process.env.NODE_ENV === 'development'`. (claim: typescript-debug-access-prior)
- **windows-debug-settings-page**: On Windows, the panel SHOULD be a dev-only settings page guarded by `#if DEBUG` (a `void` helper that code outside the guard calls MAY be marked `[Conditional("DEBUG")]` so the compiler omits the calls to it in Release, provided the helper's body keeps every panel reference inside `#if DEBUG`, since the attribute removes the calls, not the method), holding at least feature flag overrides, an analytics event log and environment info (app version, OS version, device), and reached through a navigation menu item visible only in debug builds. (claims: dotnet-if-debug, dotnet-conditional-attribute)
- **release-exclusion-guard**: Every debug-panel code path MUST sit behind a compile-time guard that removes it from release builds: Swift `#if DEBUG` with `DEBUG` set only in the Debug configuration's Active Compilation Conditions; C# `#if DEBUG`; Android's debug source set (`src/debug/`) for the panel's code and `debugImplementation` for its libraries; Vite `import.meta.env.DEV`; webpack's `process.env.NODE_ENV`, which the mode sets through DefinePlugin; never a runtime check whose code stays in the release build. (claims: swift-conditional-compilation, xcode-active-compilation-conditions, dotnet-if-debug, debug-only-source-set, variant-scoped-dependencies, vite-dev-flag-tree-shaken, webpack-mode-defines-node-env, remove-debug-code-before-deploy)
- **compile-out-not-hide**: Debug and test code, the panel and the debug libraries it uses (FLEX, Chucker, Hyperion and the like) MUST be absent from the release binary, not present and hidden: hiding at runtime (an Android component marked `android:exported="false"`, an unlinked route, an obfuscated or dormant feature) MUST NOT be relied on as protection; on Android the panel's code goes in the debug source set and its libraries in `debugImplementation`. (claims: runtime-hiding-is-not-protection, app-review-no-hidden-features, flex-excluded-or-rejected, debug-only-source-set, variant-scoped-dependencies, debug-statements-never-in-release, remove-debug-code-before-deploy)
- **release-no-op-artifact**: On Android, where a debug library ships a no-op artifact for release (Chucker's `library-no-op`), the app SHOULD declare it under `releaseImplementation` beside the real library under `debugImplementation`, so release code compiles with no trace of the library. (claim: chucker-no-op-release-artifact)
- **panel-in-internal-builds**: Beyond the Debug configuration, the panel MAY be compiled into a dedicated internal or staging build given only to developers and testers, not the production build. (claims: dedicated-debug-or-staging-build, pulse-console-in-test-builds)
- **internal-build-not-on-the-store**: On Apple platforms, a test or internal build that carries the panel MUST go to testers through TestFlight and MUST NOT be submitted to the App Store. (claim: app-review-betas-use-testflight)
- **release-build-not-debuggable**: On Android, the release build type SHOULD be non-debuggable (`isDebuggable = false`, its default), WebView debugging SHOULD be off in it, and `Log` and `Debug` tracing calls SHOULD be removed from it. (claims: android-release-not-debuggable, android-release-turn-off-logging)
- **debug-logging-off-and-redacted**: Debug and verbose logging, the panel's event log and in-app network inspectors among it, MUST be disabled in release builds, and sensitive values (Authorization and Cookie headers, tokens, request and response bodies) MUST be redacted from what the panel records, shows or shares. (claim: debug-logs-hold-sensitive-data)
- **network-inspector-redacts-headers**: An in-app network inspector (Chucker and the like) SHOULD be used during development only, not in release builds or production deployments, and SHOULD redact Authorization and Cookie headers from what it captures. (claim: chucker-data-is-sensitive)
- **sdk-dev-modes-off-in-production**: Developer modes of SDKs and frameworks (a flag SDK's developer-tools mode, ASP.NET Core's Developer Exception Page, React Native's Dev Menu) SHOULD be off in production builds and environments. (claims: sdk-dev-mode-off-in-production, aspnet-dev-page-development-only, rn-dev-menu-disabled-in-release)
- **no-secrets-in-debug-panel**: API keys, credentials and other secrets MUST NOT be compiled into client-side debug configuration, the panel's environment section included, because every value bundled into a client build is public. (claim: no-secrets-in-client-bundle)
- **exclude-debug-traffic-from-analytics**: Events logged from development and test devices, including in an analytics vendor's debug mode, SHOULD be filtered out of analytics reports and exports, for example by a developer-traffic data filter. (claims: exclude-debug-traffic-from-analytics, analytics-debug-event-stream)
- **production-overrides-are-guarded**: A flag or variant override reachable in a production build (a per-request cookie, header or query parameter) SHOULD be cryptographically signed or authenticated, and SHOULD be recorded as added attack surface. (claims: production-overrides-widen-attack-surface, sdk-dev-mode-off-in-production)
- **access-gesture-avoids-system-gestures**: An access gesture or shortcut chosen beyond those `platform-access-methods` and `typescript-debug-access` name SHOULD NOT redefine a standard system or browser gesture or command (shake is undo on iPhone; Chrome binds Ctrl+Shift+D); on Android, shake detection SHOULD be built on the accelerometer through the motion sensors. (claims: hig-shake-is-system-undo, chrome-binds-ctrl-shift-d, android-shake-needs-sensors)
- **android-guard-needs-buildconfig**: The panel's code stays in the debug source set; a `BuildConfig.DEBUG` check in `src/main/` MAY gate only the call into the panel's entry point, never hold panel code, and on Android Gradle Plugin 8.0 or later a module whose code reads `BuildConfig.DEBUG` MUST enable `buildFeatures { buildConfig = true }`. (claims: agp8-buildconfig-not-generated, debug-only-source-set)
- **node-env-production-on-servers**: A Node.js server SHOULD run with `NODE_ENV=production` in every deployed environment, staging included, so a `NODE_ENV === 'development'` check SHOULD guard only bundled client code that the bundler replaces at build time, never server-side debug features; server-side debug endpoints SHOULD be left out of the production deploy, not switched off at runtime. (claims: node-env-only-production-on-servers, webpack-mode-defines-node-env, remove-debug-code-before-deploy)
- **debug-impact-scales-with-permissions**: A debug feature SHOULD have no more capability than testing needs; one that can circumvent payment, subscription or authentication, or retrieve system or user data, SHOULD exist only where a test requires it. (claim: debug-feature-impact)
- **complement-platform-devtools**: The panel SHOULD show app-specific state that the platform's own developer tools do not (on the web, what Chrome DevTools cannot show), and a React Native panel SHOULD NOT build on Flipper's native integration, which React Native deprecated in 0.73 for removal. (claims: browser-devtools-built-in, flipper-decoupled-from-react-native)
