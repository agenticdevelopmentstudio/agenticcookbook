
- `flag-only-when-needed`, `remove-flags-when-done`: flags are inventory with a carrying cost; savvy teams keep that inventory low, and a release flag is the last choice once breaking a feature down has failed. Release flags are temporary, and a flag left in the code after its rollout is technical debt.
- `evaluation-takes-a-default-and-never-throws`, `no-dependency-on-flag-service`, `off-means-existing-behaviour`: OpenFeature's evaluation API never throws and returns the default on abnormal execution, and LaunchDarkly, ConfigCat and Flagsmith serve the caller's default when the service is unreachable or evaluation fails. A default that is the existing behaviour keeps the app running when the flag service is not there.
- `fail-at-setup-not-at-evaluation`: OpenFeature keeps abnormal execution for provider registration; Unleash separates flags, short-lived and favouring availability, from configuration, consistent and loaded at startup.
- `feature-flag-provider-interface`, `prefer-a-standard-flag-api`: OpenFeature's provider is the translator between evaluation calls and the flag system, set at startup, and may wrap a vendor SDK or read a local file; with no provider it returns the default. Microsoft.FeatureManagement has the same injected shape, from appsettings.json to Azure App Configuration. The `FeatureFlagProvider` interface and the local default implementations named in the platform rules are therefore not the flag infrastructure `prefer-a-standard-flag-api` warns against building: the interface is the seam, and the local default is the stand-in until a standard API or an existing platform is adopted behind it. Microsoft recommends adopting a platform over building one, and OpenFeature offers one vendor-agnostic evaluation API across flag tools.
- `decouple-toggle-points`: coupling the toggle point to the toggle router is a common mistake; injecting the decision leaves the code with no knowledge of flags. Hodgson advises against point conditionals wherever a feature needs several toggle points or the toggle point is expected to be long-lived, which a permanent flag is.
- `typed-flag-evaluation`: the OpenFeature specification requires its client to provide typed evaluation for boolean, numeric, string and structure values, so a value that is more than on or off keeps its own type instead of being spread across booleans.
- `name-and-describe-flags`: LaunchDarkly calls a shared naming convention an effective way to eliminate flag debt and recommends a description for context on each flag; Unleash asks that flag names be unique across the whole system.
- `test-release-and-fallback-configurations`: Fowler finds no need to test every combination of flags; Hodgson names the configuration expected to go live, production plus the flags to be released turned on, as the most important to test, and the fallback with those flags off as wise to test too.
- `no-mid-session-ui-flip`: Firebase Remote Config advises against updating or switching UI while the user is viewing or interacting with it, and can keep fetched values until they are activated the next time the app starts.
- `prefer-static-flag-configuration`: Hodgson holds static configuration preferable, with a more dynamic approach required for cases such as operational toggles. His "static" means toggle configuration kept in source control rather than changed at runtime. That is a different thing from the static application configuration of `fail-at-setup-not-at-evaluation`, which Unleash describes as consistent, long-lived and loaded at startup, and which flags must not carry: a flag can have static, source-controlled configuration and still be short-lived.
- `unique-never-reused-flag-names`: Knight Capital repurposed an old flag; on the server still carrying the dead code it triggered that code, and the firm lost $460 million.
- `flag-has-a-type-and-lifetime`: release, experiment, operational and permission toggles differ in how long they live and how dynamic they are, and vendors set an expected lifetime per type.
- `flags-never-hide-features-from-review`, `flags-switch-only-shipped-code`: App Review Guideline 2.5.19 bars hidden, dormant or undocumented features, 2.3.1(a) requires new features to be described and accessible for review, and Apple and Google Play both bar downloading code that changes app features (Google exempts interpreted code such as JavaScript in a webview).
- `kotlin-datastore-default`, `swift-userdefaults-default`, `typescript-localstorage-default`, `local-flag-store-is-untrusted`: the Android team strongly recommends against SharedPreferences for new storage and names feature flags as DataStore content; Apple describes UserDefaults as unencrypted storage for nonsensitive configuration; localStorage is per-origin, string-only and can throw when storage is blocked; client-side overrides let users change flag state.
- Left to the owner: `gate-all-features` stands against `flag-only-when-needed`, `kotlin-sharedpreferences-default` against `kotlin-datastore-default`, and `fail-fast-on-missing-config` against `evaluation-takes-a-default-and-never-throws`. Also open: whether the provider interface keeps `isEnabled(key) -> Bool` or takes a call-site default and typed values; whether the spec convention stays; whether App Review treats a feature in the binary but switched off during review as hidden; whether fail-fast is scoped to deploy configuration; and which backend Swift names and which DataStore Kotlin names.
