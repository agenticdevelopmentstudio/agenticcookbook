
Reads every flag check in the change and follows it to the provider: whether it goes through the injected interface or reaches a vendor SDK or storage directly, whether flags are evaluated through a standard API such as OpenFeature or an adopted flag platform rather than home-built flag infrastructure, and whether deep code queries flags instead of receiving the decision. Checks each new feature against the owner's `gate-all-features` rule as written, and each new flag against `flag-only-when-needed`: whether the change could have shipped in safe increments without it, and whether the team's recorded limit on live flags, or the flag's expiration date, holds the count down. Checks each new flag for an in-code default that is today's behaviour (restrictive for security-sensitive flags), a name that follows the shared naming convention and is unique in the system and never used before, a description, a type with its lifetime, and a planned removal, and checks each spec the change touches for a **Feature Flags** section listing its flag keys (`spec-lists-flag-keys`, the owner's rule as written). Looks for evaluation paths that can throw or block on the flag service, for provider setup failures that surface only when a flag is evaluated instead of at registration, for flags carrying static application configuration, for per-deploy configuration that is not read from the environment into a typed object at startup and halted on when missing or malformed (`fail-fast-on-missing-config`, the owner's rule as written), for non-boolean values encoded in booleans instead of evaluated as their own type, for flag configuration changed at runtime where a static, source-controlled value would serve, and for runtime flag changes that swap UI mid-session. Checks the platform store: UserDefaults with nonsensitive values on Apple platforms; on Android, whether SharedPreferences or DataStore is used (both rules stand for the owner); on the web, string values and a blocked-storage path; in .NET, Microsoft.FeatureManagement with appsettings.json. Looks for personal or sensitive data in the local flag store and for code that trusts a flag value from the local store, or from a client-side or per-request override, that the user could have changed. Looks for tests of both states and of the release and fallback configurations, for a rollout that widens exposure with no usage or system-health metrics to watch, for flags whose rollout is done but whose code remains, for features a flag keeps hidden from App Review, and, in an app distributed through the App Store or Google Play, for code fetched at runtime that a flag turns on.
