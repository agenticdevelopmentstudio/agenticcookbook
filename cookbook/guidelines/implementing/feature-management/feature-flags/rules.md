
- **gate-all-features**: All features MUST be gated behind feature flags from initial implementation. (claim: gate-all-features-prior)
- **flag-only-when-needed**: A change SHOULD first be broken down so its parts can be introduced into the product safely, with a release flag as the last choice rather than the default, and the number of live flags SHOULD be held down, either by a limit, set and recorded by the team, on how many flags may be live at once, or by an expiration date on each flag, because each one carries a cost. (claims: not-every-change-needs-a-flag, toggles-are-inventory)
- **spec-lists-flag-keys**: Each spec SHOULD list flag keys in a **Feature Flags** section. (claim: spec-lists-flag-keys-prior)
- **feature-flag-provider-interface**: Code SHOULD read flags as follows. Define a `FeatureFlagProvider` interface (`isEnabled(key) -> Bool`), provide a local default implementation, swap in a backend implementation later via DI. Until a backend is swapped in, the local default implementation serves each flag's in-code default, and tests MAY swap in a provider of their own. (claims: openfeature-provider-abstraction, openfeature-noop-provider, ms-json-to-app-configuration, decouple-decision-point-from-logic)
- **prefer-a-standard-flag-api**: Flags SHOULD be evaluated through a vendor-agnostic standard API such as OpenFeature, and an existing flag platform SHOULD be adopted rather than building flag infrastructure of your own. (claims: openfeature-vendor-agnostic, build-vs-buy)
- **swift-userdefaults-default**: In Swift, the local default implementation SHOULD be as follows. Protocol + `UserDefaults`-backed implementation as the default. It SHOULD hold only nonsensitive flag values, since UserDefaults stores them on disk unencrypted. (claims: apple-userdefaults-for-config, apple-userdefaults-not-sensitive)
- **kotlin-sharedpreferences-default**: In Kotlin, the local default implementation SHOULD be as follows. Interface + `SharedPreferences`-backed implementation as the default. (claim: kotlin-sharedpreferences-default-prior)
- **kotlin-datastore-default**: In Kotlin on Android, the local flag store SHOULD be Jetpack DataStore rather than `SharedPreferences`, with flags kept in a DataStore file separate from any sensitive data. (claims: android-sharedpreferences-not-for-new, android-datastore-holds-feature-flags)
- **typescript-localstorage-default**: In TypeScript, the local default implementation SHOULD be as follows. TypeScript interface + `localStorage`-backed implementation as the default. It SHOULD store each value as a string, since `localStorage` holds only strings per origin across sessions, and SHOULD handle the `SecurityError` thrown when the user has blocked storage. (claims: sdks-cache-in-local-storage, web-localstorage-semantics)
- **csharp-feature-management**: In C#, flags SHOULD be read as follows. `IFeatureManager` interface + local JSON config as the default. Use the `Microsoft.FeatureManagement` NuGet package. Swap in Azure App Configuration for server-side flag evaluation later. The package is registered through .NET dependency injection; `IVariantFeatureManager`, which its documentation now leads with, MAY be used in place of `IFeatureManager`, and ASP.NET Core controllers, actions and Razor pages MAY be gated on a flag with `FeatureGateAttribute`. (claims: ms-featuremanager-interface, ms-json-to-app-configuration, ms-feature-gate)
- **evaluation-takes-a-default-and-never-throws**: Every flag SHOULD have an in-code default value, and evaluating a flag SHOULD NOT throw: when the flag service is unreachable, the key is missing or evaluation fails, the read SHOULD return that default, so the app behaves as expected without the flag service. (claims: openfeature-default-required-no-throw, vendor-sdks-default-on-error, default-at-every-evaluation)
- **fail-fast-on-missing-config**: The app MUST do the following. Read every value that varies per deploy from the environment, coerce all required config into a typed object once at startup, and halt on a missing or malformed value rather than falling back to a silent default (fail-fast). (claim: fail-fast-on-missing-config-prior)
- **fail-at-setup-not-at-evaluation**: A failure in the flag system SHOULD surface at setup, when the provider is registered, rather than when a flag is evaluated, and flags SHOULD NOT be used for static application configuration, which is long-lived and loaded at startup. (claims: setup-may-fail-evaluation-may-not, flags-are-not-config)
- **typed-flag-evaluation**: A flag whose value is more than on or off SHOULD be evaluated as its own type, number, string or structure, rather than encoded in booleans. (claim: openfeature-typed-evaluation)
- **off-means-existing-behaviour**: A flag's off state and its default value SHOULD be the existing, known-working behaviour, with on the new behaviour; for a security- or compliance-sensitive flag, the default SHOULD instead be the more restrictive behaviour. (claims: off-is-existing-behaviour, restrictive-fallback-for-security)
- **no-dependency-on-flag-service**: The app SHOULD keep working when the flag service is unavailable, using the last-known flag values cached locally or the in-code defaults. (claims: no-dependency-on-flag-service, sdks-cache-in-local-storage)
- **local-flag-store-is-untrusted**: The local flag store SHOULD NOT hold personal or sensitive information, and a flag value read from it, or set by a client-side or per-request override, SHOULD be treated as a value the user may have changed. (claims: apple-userdefaults-not-sensitive, client-side-override-risk)
- **prefer-static-flag-configuration**: Flag configuration SHOULD be static and source-controlled, with dynamic configuration changed at runtime used only where it is needed, such as for operational toggles. (claim: static-config-preferred)
- **flag-has-a-type-and-lifetime**: Each flag SHOULD be given a type, temporary (release, experiment, operational) or permanent (kill switch, permission), and managed by its type's expected lifetime, and a flag that outlives that lifetime SHOULD be marked stale. (claims: categories-managed-differently, flag-types-and-lifetimes, stale-flag-detection)
- **unique-never-reused-flag-names**: A flag's name MUST be unique and MUST NOT be reused: an old flag MUST NOT be repurposed to switch new code. (claim: never-repurpose-a-flag)
- **name-and-describe-flags**: Flags SHOULD follow one shared naming convention, with names unique across the whole system, and each flag SHOULD carry a description. (claim: naming-and-descriptions)
- **decouple-toggle-points**: The code at a toggle point SHOULD have the flag decision injected into it, for example at construction, rather than query the flag system itself, and a toggle expected to outlive a release flag's lifetime, such as a permanent flag (kill switch, permission), or needed at several points SHOULD select its code path through a strategy rather than scattered conditionals. (claims: decouple-decision-point-from-logic, strategy-over-conditionals, flag-types-and-lifetimes)
- **test-both-flag-states**: Code behind a flag MUST be tested with the flag on and with it off, and the off path of a permanent flag (kill switch, permission), which stays switchable after its release, MUST keep being tested for as long as the flag can be switched. (claims: test-both-states, flag-types-and-lifetimes)
- **test-release-and-fallback-configurations**: Tests SHOULD cover the flag configuration expected to go live, the current production configuration plus the flags to be released turned on, and the fallback with those flags turned off, rather than every combination of flags. (claim: test-the-release-combinations)
- **no-mid-session-ui-flip**: A flag value fetched while the app runs SHOULD NOT update or switch UI the user is viewing or interacting with; it MAY be activated the next time the app starts. (claim: firebase-activate-next-start)
- **monitor-flag-rollout**: While a flag widens a feature's exposure, usage and system-health metrics SHOULD be monitored to judge readiness for broader exposure. (claim: monitor-flag-rollout)
- **remove-flags-when-done**: Once a release flag's rollout is complete, the flag and its old code path SHOULD be removed from the code; its removal SHOULD be planned when it is created, with a removal pull request or an expiration date; a flag SHOULD be removed from the code before it is archived in the flag service; and the live flags SHOULD be reviewed on a regular cadence, such as each sprint, to keep their number low. (claims: flags-short-lived-removed, removal-planned-at-creation, remove-code-before-archive, regular-flag-review, toggles-are-inventory)
- **flags-never-hide-features-from-review**: Every new feature in a build submitted to App Review MUST be described in the Notes for Review and accessible for review, and the app MUST NOT include hidden, dormant or undocumented features. (claims: apple-features-accessible-for-review, apple-no-hidden-features)
- **flags-switch-only-shipped-code**: In an app distributed through the App Store or Google Play, a flag SHOULD switch only code already in the binary the store reviewed, and SHOULD NOT turn on code downloaded after release that introduces or changes the app's features. (claim: store-no-downloaded-code)
