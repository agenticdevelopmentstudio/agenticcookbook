# Research: feature flags

Researched and accessed 2026-11-16 against base commit `2071c94e51a8c517e11178fdee54e0ec033064c2`. Every finding below names its claim id in `research.json`; quotes there are verbatim from the fetched pages.

Four of the eight rules hold: the injected provider interface (OpenFeature's provider model and Microsoft.FeatureManagement's DI both have this shape), UserDefaults on Apple, localStorage on web (vendor SDKs cache flags there; it is per-origin, string-only and can throw) and Microsoft.FeatureManagement with appsettings.json then Azure App Configuration (IFeatureManager still ships, though the docs now lead with IVariantFeatureManager). Three are contradicted: gating every feature (Microsoft says not every change needs a flag; Fowler calls release flags the last choice), SharedPreferences on Android (the Android team strongly recommends against it for new storage; DataStore instead), and fail-fast applied to flag evaluation (OpenFeature and every vendor SDK return the caller's default and never throw; failure belongs at setup, and flags are not config). 'Each spec lists flag keys' is unsupported: no source covers specs; the nearest practice is naming conventions, descriptions and a planned removal. The topic misses: a call-site default and no-throw evaluation, typed values, off means existing behaviour, no runtime dependency on the flag service, flag types with lifetimes, removing flags when done, unique never-reused names (Knight Capital), testing both states, decoupled toggle points, App Store 2.5.19/2.3.1 and the store bans on downloaded code, the local store as untrusted, no mid-session UI flips, monitoring rollouts, static config preferred, and a standard API (OpenFeature).

**Open questions**

- Whether the provider interface should keep `isEnabled(key) -> Bool` or take a call-site default and typed values as OpenFeature does; the owner decides the rule's signature.
- Whether to keep a 'spec lists flag keys' rule as a house convention; no external source supports or contradicts it.
- Whether Apple App Review treats a feature already in the binary but switched off during review as 'hidden' under 2.5.19; no Apple text addresses feature flags directly.
- Whether the fail-fast rule should be scoped to deploy configuration (where Unleash's config/flag split supports it) with flags explicitly excluded, or whether flag provider setup should fail fast as OpenFeature allows.
- Whether the Swift guidance should name OpenFeature's iOS SDK or a vendor SDK as the 'backend later', and whether Kotlin should name Preferences DataStore or Proto DataStore.

**Limitations**

- The brief's 'App Store guideline 2.3.1 on hidden features' is out of date: the current hidden-features rule is 2.5.19; 2.3.1 now covers describing new features for review.
- No Windows desktop (Microsoft Store) guidance on feature flags was found; Microsoft coverage is Microsoft.FeatureManagement, Azure App Configuration and Azure DevOps guidance.
- No primary source speaks to documenting flag keys in a specification; the naming and description practice comes from vendors.
- The web platform claim cites MDN rather than the WHATWG HTML standard.
- Several Microsoft DevOps claims come from a 2022 page; currency was scored down.
- The Unleash unique-names topic page returned 404; its point was taken from the Unleash best-practices page instead.

## Best practices

- **off-is-existing-behaviour** (trust 80, multi-independent). A flag's off state (and its fallback value) should be the existing, known-working behaviour; on is the new behaviour. Sources: [Feature Toggles (aka Feature Flags)](https://martinfowler.com/articles/feature-toggles.html); [Resilient architecture patterns for LaunchDarkly SDKs](https://launchdarkly.com/docs/guides/sdk/resilience).
- **restrictive-fallback-for-security** (trust 62, single). For security- or compliance-sensitive flags, the fallback should be the more restrictive behaviour rather than the current one. Sources: [Resilient architecture patterns for LaunchDarkly SDKs](https://launchdarkly.com/docs/guides/sdk/resilience).
- **default-at-every-evaluation** (trust 86, multi-independent). Every flag read should carry an in-code default so the app behaves correctly without the flag service. Sources: [Firebase Remote Config loading strategies](https://firebase.google.com/docs/remote-config/loading); [Defensive Coding and Designing for Failure](https://docs.flagsmith.com/best-practices/defensive-coding); [Flag variation evaluation](https://launchdarkly.com/docs/sdk/features/evaluating).
- **no-dependency-on-flag-service** (trust 78, multi-independent). The application must keep working when the flag service is unavailable, using cached last-known values or in-code defaults. Sources: [11 feature flag best practices for scale](https://docs.getunleash.io/topics/feature-flags/feature-flag-best-practices); [Defensive Coding and Designing for Failure](https://docs.flagsmith.com/best-practices/defensive-coding).
- **flags-short-lived-removed** (trust 88, multi-independent). Release flags are temporary: once the rollout is complete, remove the flag and its old code path from the codebase. Sources: [11 feature flag best practices for scale](https://docs.getunleash.io/topics/feature-flags/feature-flag-best-practices); [Reducing technical debt from feature flags](https://launchdarkly.com/docs/guides/flags/technical-debt); [Progressive experimentation with feature flags](https://learn.microsoft.com/en-us/devops/operate/progressive-experimentation-feature-flags).
- **remove-code-before-archive** (trust 64, single). Remove a flag from code before retiring it in the flag service, because a retired flag serves the in-code fallback. Sources: [Archiving and restoring flags](https://launchdarkly.com/docs/home/flags/archive).
- **removal-planned-at-creation** (trust 76, multi-independent). Plan a flag's removal when it is created: a removal pull request, a backlog item or an expiration date. Sources: [Reducing technical debt from feature flags](https://launchdarkly.com/docs/guides/flags/technical-debt); [Feature Toggles (aka Feature Flags)](https://martinfowler.com/articles/feature-toggles.html).
- **regular-flag-review** (trust 58, single). Review the set of live flags on a regular cadence, such as every sprint. Sources: [Progressive experimentation with feature flags](https://learn.microsoft.com/en-us/devops/operate/progressive-experimentation-feature-flags).
- **naming-and-descriptions** (trust 72, multi-independent). Use a shared naming convention, unique names across the whole system, and a description for each flag. Sources: [Reducing technical debt from feature flags](https://launchdarkly.com/docs/guides/flags/technical-debt); [11 feature flag best practices for scale](https://docs.getunleash.io/topics/feature-flags/feature-flag-best-practices).
- **test-both-states** (trust 82, multi-independent). Test both states of each flag, and keep testing a long-lived flag's off path while it can still be switched. Sources: [Feature Toggles (aka Feature Flags)](https://martinfowler.com/articles/feature-toggles.html); [Progressive experimentation with feature flags](https://learn.microsoft.com/en-us/devops/operate/progressive-experimentation-feature-flags); [Resilient architecture patterns for LaunchDarkly SDKs](https://launchdarkly.com/docs/guides/sdk/resilience).
- **not-every-change-needs-a-flag** (trust 80, multi-independent). Not every change needs a flag; splitting a feature into safe increments is preferred, with a release flag as the last resort. Sources: [Progressive experimentation with feature flags](https://learn.microsoft.com/en-us/devops/operate/progressive-experimentation-feature-flags); [FeatureFlag (bliki)](https://martinfowler.com/bliki/FeatureFlag.html).
- **monitor-flag-rollout** (trust 60, single). Watch usage and system-health metrics while a flag widens exposure. Sources: [Progressive experimentation with feature flags](https://learn.microsoft.com/en-us/devops/operate/progressive-experimentation-feature-flags).
- **flags-are-not-config** (trust 66, single). Feature flags are not application configuration: configuration is static and loaded at startup, flags are short-lived, change at runtime and favour availability. Sources: [11 feature flag best practices for scale](https://docs.getunleash.io/topics/feature-flags/feature-flag-best-practices).
- **gate-all-features-prior** (trust 0, uncorroborated). All features MUST be gated behind feature flags from initial implementation. Sources: feature-flags (intro.md) (`git:2071c94e51a8c517e11178fdee54e0ec033064c2:cookbook/guidelines/implementing/feature-management/feature-flags/intro.md`).
- **spec-lists-flag-keys-prior** (trust 0, uncorroborated). Each spec SHOULD list flag keys in a **Feature Flags** section. Sources: feature-flags (intro.md) (`git:2071c94e51a8c517e11178fdee54e0ec033064c2:cookbook/guidelines/implementing/feature-management/feature-flags/intro.md`).
- **fail-fast-on-missing-config-prior** (trust 0, uncorroborated). Read every value that varies per deploy from the environment, coerce all required config into a typed object once at startup, and halt on a missing or malformed value rather than falling back to a silent default (fail-fast). Sources: feature-flags (reference/building--devops-observability.txt) (`git:2071c94e51a8c517e11178fdee54e0ec033064c2:reference/building--devops-observability.txt`).

## Known solutions

- **openfeature-vendor-agnostic** (trust 82, single). OpenFeature is a CNCF open specification giving one vendor-agnostic flag evaluation API, with client SDKs for iOS, Kotlin and Web and a server SDK for .NET. Sources: [Introduction | OpenFeature](https://openfeature.dev/docs/reference/intro).
- **openfeature-provider-abstraction** (trust 88, multi-independent). OpenFeature separates the evaluation API from a swappable provider set at startup; a provider may wrap a vendor SDK or read flags from a local file. Sources: [OpenFeature Specification, 2. Provider](https://openfeature.dev/specification/sections/providers); [OpenFeature Specification, 02-providers.md (source)](https://raw.githubusercontent.com/open-feature/spec/main/specification/sections/02-providers.md); [OpenFeature Specification, 01-flag-evaluation.md (source)](https://raw.githubusercontent.com/open-feature/spec/main/specification/sections/01-flag-evaluation.md).
- **openfeature-noop-provider** (trust 84, single). With no provider set, OpenFeature uses a no-op provider that returns the caller's default, and the API can be reset to it for testing. Sources: [OpenFeature Specification, 01-flag-evaluation.md (source)](https://raw.githubusercontent.com/open-feature/spec/main/specification/sections/01-flag-evaluation.md).
- **openfeature-default-required-no-throw** (trust 92, multi-independent). OpenFeature evaluation takes a required default value and must never throw; on any abnormal execution it returns the default with an error code. Sources: [OpenFeature Specification, 1. Flag Evaluation API](https://openfeature.dev/specification/sections/flag-evaluation); [OpenFeature Specification, 01-flag-evaluation.md (source)](https://raw.githubusercontent.com/open-feature/spec/main/specification/sections/01-flag-evaluation.md).
- **openfeature-typed-evaluation** (trust 84, single). The standard evaluation API is typed (boolean, number, string, structure), not boolean-only. Sources: [OpenFeature Specification, 1. Flag Evaluation API](https://openfeature.dev/specification/sections/flag-evaluation).
- **setup-may-fail-evaluation-may-not** (trust 80, multi-independent). OpenFeature puts failure at setup (provider registration) and keeps evaluation non-failing; Microsoft.FeatureManagement treats a missing flag as off by default but can be set to throw. Sources: [OpenFeature Specification, 01-flag-evaluation.md (source)](https://raw.githubusercontent.com/open-feature/spec/main/specification/sections/01-flag-evaluation.md); [FeatureManagementOptions.cs (FeatureManagement-Dotnet, main)](https://raw.githubusercontent.com/microsoft/FeatureManagement-Dotnet/main/src/Microsoft.FeatureManagement/FeatureManagementOptions.cs).
- **vendor-sdks-default-on-error** (trust 88, multi-independent). LaunchDarkly, ConfigCat and Flagsmith all return the caller-supplied default when the service is unreachable, the key is missing, or evaluation errors. Sources: [Flag variation evaluation](https://launchdarkly.com/docs/sdk/features/evaluating); [Feature Flag Evaluation](https://configcat.com/docs/targeting/feature-flag-evaluation/); [Defensive Coding and Designing for Failure](https://docs.flagsmith.com/best-practices/defensive-coding).
- **ms-featuremanager-interface** (trust 86, single). Microsoft.FeatureManagement still ships IFeatureManager with IsEnabledAsync(string); its docs now lead with IVariantFeatureManager. Sources: [IFeatureManager.cs (FeatureManagement-Dotnet, main)](https://raw.githubusercontent.com/microsoft/FeatureManagement-Dotnet/main/src/Microsoft.FeatureManagement/IFeatureManager.cs); [.NET Feature Flag Management - Azure App Configuration](https://learn.microsoft.com/en-us/azure/azure-app-configuration/feature-management-dotnet-reference).
- **ms-json-to-app-configuration** (trust 88, single). Microsoft.FeatureManagement reads flags through IConfiguration, from appsettings.json up to Azure App Configuration, and is registered through .NET dependency injection. Sources: [.NET Feature Flag Management - Azure App Configuration](https://learn.microsoft.com/en-us/azure/azure-app-configuration/feature-management-dotnet-reference); [Feature Management Overview - Azure App Configuration](https://learn.microsoft.com/en-us/azure/azure-app-configuration/feature-management-overview).
- **ms-feature-gate** (trust 80, single). ASP.NET Core can gate whole controllers, actions and Razor pages on a flag with FeatureGateAttribute. Sources: [.NET Feature Flag Management - Azure App Configuration](https://learn.microsoft.com/en-us/azure/azure-app-configuration/feature-management-dotnet-reference).
- **flag-types-and-lifetimes** (trust 82, multi-independent). Vendors classify flags by type with expected lifetimes: temporary (release, experiment, operational) versus permanent (kill switch, permission/entitlement). Sources: [Feature flags](https://docs.getunleash.io/concepts/feature-flags); [Reducing technical debt from feature flags](https://launchdarkly.com/docs/guides/flags/technical-debt).
- **stale-flag-detection** (trust 72, single). Tools flag stale flags automatically once a flag outlives its type's expected lifetime. Sources: [Technical debt](https://docs.getunleash.io/reference/technical-debt).
- **sdks-cache-in-local-storage** (trust 74, multi-independent). Vendor client SDKs persist flag values locally (localStorage on web, SharedPreferences on Android) and read them on launch before the network. Sources: [Caching contexts to local storage](https://launchdarkly.com/docs/sdk/features/local-storage); [Defensive Coding and Designing for Failure](https://docs.flagsmith.com/best-practices/defensive-coding).
- **firebase-activate-next-start** (trust 70, single). Firebase Remote Config advises not switching UI while the user is using it, and can activate fetched values on the next app start. Sources: [Firebase Remote Config loading strategies](https://firebase.google.com/docs/remote-config/loading).
- **build-vs-buy** (trust 55, single). Microsoft recommends adopting an existing flag platform over building one. Sources: [Progressive experimentation with feature flags](https://learn.microsoft.com/en-us/devops/operate/progressive-experimentation-feature-flags).

## Platform guidelines

- **apple-no-hidden-features** (trust 90, single). Apple forbids hidden, dormant or undocumented features (guideline 2.5.19); the hidden-features rule is not 2.3.1. Sources: [App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/).
- **apple-features-accessible-for-review** (trust 90, single). Apple requires every new feature to be described in Notes for Review and accessible for review (2.3.1(a)). Sources: [App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/).
- **store-no-downloaded-code** (trust 90, multi-independent). Apple and Google Play both forbid downloading code that changes app features, so a flag may only switch code already in the reviewed binary. Sources: [App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/); [Device and Network Abuse - Play Console Help](https://support.google.com/googleplay/android-developer/answer/16273414).
- **apple-userdefaults-for-config** (trust 84, single). Apple describes UserDefaults as the store for nonsensitive app configuration, including temporary overrides to test a feature. Sources: [UserDefaults](https://developer.apple.com/documentation/foundation/userdefaults).
- **apple-userdefaults-not-sensitive** (trust 88, single). UserDefaults is unencrypted on disk, so nothing sensitive belongs in it. Sources: [UserDefaults](https://developer.apple.com/documentation/foundation/userdefaults).
- **android-sharedpreferences-not-for-new** (trust 93, single). The Android team strongly recommends against SharedPreferences for new storage and points to Jetpack DataStore. Sources: [SharedPreferences (API reference)](https://developer.android.com/reference/android/content/SharedPreferences); [DataStore (App Architecture: Data Layer)](https://developer.android.com/topic/libraries/architecture/datastore).
- **android-datastore-holds-feature-flags** (trust 82, single). Android's DataStore guide names feature flags as non-sensitive preferences to keep in their own DataStore file. Sources: [DataStore (App Architecture: Data Layer)](https://developer.android.com/topic/libraries/architecture/datastore).
- **web-localstorage-semantics** (trust 78, single). localStorage is per-origin, persists across sessions, stores only strings, and can throw SecurityError when storage is blocked. Sources: [Window: localStorage property](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage).
- **kotlin-sharedpreferences-default-prior** (trust 0, uncorroborated). Interface + `SharedPreferences`-backed implementation as the default. Sources: feature-flags (kotlin.md) (`git:2071c94e51a8c517e11178fdee54e0ec033064c2:cookbook/guidelines/implementing/feature-management/feature-flags/kotlin.md`).

## The expert's view

- **categories-managed-differently** (trust 80, multi-independent). Toggle categories (release, experiment, ops, permissioning) differ in longevity and dynamism and must be implemented and managed differently. Sources: [Feature Toggles (aka Feature Flags)](https://martinfowler.com/articles/feature-toggles.html).
- **decouple-decision-point-from-logic** (trust 76, single). Keep the toggle point apart from the decision logic: inject the decision into the code rather than having it query the flag system. Sources: [Feature Toggles (aka Feature Flags)](https://martinfowler.com/articles/feature-toggles.html).
- **strategy-over-conditionals** (trust 70, single). Avoid scattered if-statements for long-lived or multi-point toggles; select alternative code paths through a Strategy. Sources: [Feature Toggles (aka Feature Flags)](https://martinfowler.com/articles/feature-toggles.html).
- **toggles-are-inventory** (trust 80, multi-independent). Flags carry a carrying cost; keep the count low with expiration dates or a hard limit on live flags. Sources: [Feature Toggles (aka Feature Flags)](https://martinfowler.com/articles/feature-toggles.html); [Reducing technical debt from feature flags](https://launchdarkly.com/docs/guides/flags/technical-debt).
- **test-the-release-combinations** (trust 74, single). Do not test every flag combination; test the configuration going live and the fallback with the new flags off. Sources: [FeatureFlag (bliki)](https://martinfowler.com/bliki/FeatureFlag.html); [Feature Toggles (aka Feature Flags)](https://martinfowler.com/articles/feature-toggles.html).
- **static-config-preferred** (trust 68, single). Prefer static, source-controlled toggle configuration; reach for dynamic configuration only where needed (ops toggles). Sources: [Feature Toggles (aka Feature Flags)](https://martinfowler.com/articles/feature-toggles.html).
- **client-side-override-risk** (trust 70, multi-independent). Client-side or per-request flag overrides let users change flag state, and flag systems should not hold PII. Sources: [Feature Toggles (aka Feature Flags)](https://martinfowler.com/articles/feature-toggles.html); [11 feature flag best practices for scale](https://docs.getunleash.io/topics/feature-flags/feature-flag-best-practices).
- **never-repurpose-a-flag** (trust 90, multi-independent). Reusing an old flag for new code, with the dead code still deployed, caused Knight Capital's $460 million loss; flag names must never be reused. Sources: [In the Matter of Knight Capital Americas LLC, Release No. 34-70694 (Order Instituting Administrative and Cease-and-Desist Proceedings)](https://www.sec.gov/files/litigation/admin/2013/34-70694.pdf); [11 feature flag best practices for scale](https://docs.getunleash.io/topics/feature-flags/feature-flag-best-practices).
