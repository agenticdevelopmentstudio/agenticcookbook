
- **must-use-single-activity**: The app **MUST** use a single-activity architecture: one `Activity` hosts the Compose UI; screens are composables, not separate activities.
- **should-hoist-navcontroller-to-top**: Navigation state (the `NavHostController`) **SHOULD** be created once at the top of the UI tree via `rememberNavController()` and passed down, or wrapped in narrow callbacks (`onNavigateToProfile: (id) -> Unit`) so leaf composables stay navigation-agnostic and testable.
- **must-not-touch-back-stack-from-screens**: Screen composables **MUST NOT** read or mutate the back stack directly; they emit navigation events upward. This follows unidirectional data flow — see [adc.guideline.implementing.ui.compose-state-and-udf](cookbook:736fac9a-56e0-449d-8dc0-b95cbfba7884).
- **should-use-stable-type-safe-navigation-apis**: Apps SHOULD use the stable type-safe APIs in `androidx.navigation:navigation-compose` (type-safe routes are stable as of 2.8.0; pin a current `2.9.x` build and apply the `kotlinx-serialization` Gradle plugin).
- **must-use-serializable-route-types**: Routes **MUST** be `@Serializable` Kotlin types, not raw strings: an `object` for argument-free destinations, a `data class` for destinations with arguments.
- **should-build-graph-with-type-safe-builders**: Apps SHOULD build the graph with the type-safe builders and navigate by passing a route instance.
- **must-pass-arguments-through-route-type**: Arguments **MUST** be passed through the route type and read with `toRoute()`; do **NOT** concatenate path strings or hand-parse `NavBackStackEntry.arguments`.
- **should-read-route-arguments-from-savedstatehandle**: ViewModels **SHOULD** receive route arguments via `SavedStateHandle.toRoute<Route>()` rather than being handed a `NavController`.
- **should-declare-deep-links-per-destination**: Deep links **SHOULD** be declared per destination (`deepLinks = listOf(navDeepLink<Profile>(...))`) so the same type-safe route drives both in-app and external entry.
- **should-pin-nav3-and-recheck-release-notes**: Apps SHOULD pin a current `1.x` release of `androidx.navigation3` before relying on it; its APIs and supporting libraries (e.g. `material3-adaptive-navigation3`) are still maturing, so apps SHOULD treat specific surface details as evolving (FORECAST) and re-check the release notes.
- **should-choose-nav3-deliberately**: Nav3 SHOULD be chosen as a **deliberate decision** when you need full control over the back stack, multi-pane/adaptive layouts, or custom transitions — not as a blanket mandate.
- **should-not-mix-nav2-and-nav3-in-a-flow**: Apps SHOULD **NOT** mix Nav2 `NavHost` and Nav3 `NavDisplay` for the same flow; pick one model per navigation graph and migrate a flow at a time.
- **must-handle-process-death**: Surviving process death **MUST** be handled: route types are saved automatically because they are serializable; additional UI state goes in `SavedStateHandle` or `rememberSaveable`.
- **should-scope-viewmodels-to-back-stack-entry**: Back-stack-scoped state **SHOULD** use `viewModel()` scoped to the `NavBackStackEntry` so a ViewModel is cleared when its destination leaves the stack.
- **should-use-single-start-destination**: Apps SHOULD use a single `startDestination` and SHOULD avoid clearing and rebuilding the entire graph to navigate — prefer `popUpTo`/`launchSingleTop` (Nav2) or list operations (Nav3).
