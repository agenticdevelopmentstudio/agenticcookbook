
- **should-configure-tsconfig-to-catch-errors**: You SHOULD configure `tsconfig.json` so the compiler catches the errors it is capable of catching.
- **should-adopt-stricter-flags-deliberately**: You SHOULD adopt the stricter flags deliberately rather than all at once.
- **must-set-strict**: New TypeScript projects MUST set `"strict": true` in `tsconfig.json` `compilerOptions`.
  - This enables the strict family as a unit (`strictNullChecks`, `noImplicitAny`, `strictFunctionTypes`, `strictBindCallApply`, `useUnknownInCatchVariables`, and others).
- **must-not-silence-checker**: Code MUST NOT silence the checker with project-wide `// @ts-nocheck`, blanket `any`, or `skipLibCheck` used to hide first-party errors.
- **should-use-scoped-ts-expect-error**: You SHOULD use a narrowly-scoped `// @ts-expect-error` (with a reason) for the rare unavoidable case so the suppression fails loudly if the underlying type later changes.
- **should-treat-disabled-strict-flags-as-temporary**: Disabling individual strict-family flags (e.g. `"strictNullChecks": false`) SHOULD be treated as a temporary migration state, recorded in code with a tracking reference — not a permanent posture.
- **should-enable-recommended-near-defaults**: New projects SHOULD enable `noUncheckedIndexedAccess` and `verbatimModuleSyntax`: enable these on greenfield projects; they close gaps `strict` alone leaves open.
- **must-use-import-type-with-verbatim-module-syntax**: With `verbatimModuleSyntax`, type-only imports MUST use `import type` / `export type` (or inline `type` modifiers), since the compiler no longer elides them automatically.
- **should-enable-exact-optional-property-types-when-absent-differs**: You SHOULD enable `exactOptionalPropertyTypes` (TS 4.4) when modeling APIs where "absent" and "present but undefined" differ; it adds real friction with loosely-typed third-party shapes, so it is opt-in, not a baseline.
  - `exactOptionalPropertyTypes` (TS 4.4) distinguishes a missing property from one explicitly set to `undefined`.
- **should-enable-erasable-syntax-only-for-type-stripping**: You SHOULD enable `erasableSyntaxOnly` (TS 5.8) when files are run via native type-stripping (Node.js `--experimental-strip-types`/stable type stripping, Bun, Deno, or in-browser transforms) so the source contains no non-erasable syntax.
  - `erasableSyntaxOnly` (TS 5.8) errors on TypeScript constructs that emit runtime code (`enum`, `namespace` with runtime members, parameter properties).
- **should-pair-erasable-syntax-only-with-verbatim-module-syntax**: You SHOULD pair `erasableSyntaxOnly` with `verbatimModuleSyntax`.
- **should-turn-on-strict-first**: On existing code, you SHOULD turn on `strict` first, and land that as its own change.
- **should-enable-one-stricter-flag-at-a-time**: You SHOULD enable one stricter flag at a time (`noUncheckedIndexedAccess`, then `exactOptionalPropertyTypes`, etc.), fixing the fallout before moving on.
- **should-not-enable-every-flag-in-one-sweep**: Agents SHOULD NOT enable every flag in a single sweep on an established codebase — small, reviewable diffs keep each step reversible.
- **should-not-assume-forecast-behavior-is-current**: You SHOULD treat the forecast behavior below as roadmap/proposed behavior, and SHOULD NOT write configs or guidance that assume it as current.
  - The native Go compiler ("tsgo", "Project Corsa") and the TypeScript 7.0 line are a proposed reimplementation targeting large build speedups.
  - "strict by default" and the removal of legacy module/target modes (e.g. dropping `node10` resolution, raising the minimum target) are PLANNED breaking changes discussed for the 6.0/7.0 line.
- **should-confirm-native-compiler-release-state**: As of this writing, you SHOULD confirm the actual release state of the native Go compiler and the TypeScript 7.0 line against the official [TypeScript blog](https://devblogs.microsoft.com/typescript/) and [microsoft/typescript-go](https://github.com/microsoft/typescript-go) before depending on it.
- **must-keep-setting-strict-explicitly**: Until you have verified "strict by default" and the removal of legacy modes in shipped release notes, you MUST keep setting `"strict": true` explicitly rather than relying on an implicit default.
