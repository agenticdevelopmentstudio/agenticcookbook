
- `should-have-single-responsibility`: Rule addresses one coherent concern — not a grab-bag of unrelated instructions (C01)
- `should-give-actionable-specific-instructions`: Every instruction tells the LLM what to do concretely, not vague directives like "handle errors appropriately" (C07)
- `must-not-conflict-with-itself`: Rule does not contradict itself (e.g., "always do X" then later "never do X") (C08)
- `should-use-well-structured-markdown`: Uses headings, lists, code blocks; not a wall of unstructured text (C09)
- `should-not-replicate-native-capabilities`: Rule doesn't teach Claude things it already knows (basic git, standard coding, etc.) (B02)
- `must-not-be-kitchen-sink`: Rule doesn't try to govern everything — stays focused on its stated concern (B06)
- `should-not-be-claude-md-dump`: Content is rule-appropriate, not project configuration that belongs in CLAUDE.md (B08)
- `should-have-clear-title-heading`: File starts with a heading that identifies the rule's purpose (R01)
- `should-use-imperative-tone`: Uses RFC 2119 keywords (MUST, MUST NOT, SHOULD, MAY); not advisory or suggestive (R02)
- `should-number-or-separate-steps`: If procedural, steps are in a clear sequence with headings or numbered list (R03)
- `must-not-use-vague-directives`: Every instruction is concrete and actionable; no "handle appropriately" or "write good code" (R04)
- `must-list-file-references-explicitly`: If the rule says to read files, every file path is listed explicitly — no "read the principles" without paths (R05)
- `must-not-give-contradictory-instructions`: Rule does not say "always do X" then later "never do X" or otherwise conflict with itself (R06)
- `should-address-single-concern`: Rule addresses one coherent concern (planning, implementing, reviewing) — not a grab-bag (R07)
- `should-include-enforcement-mechanism`: Rule includes steps to verify compliance — not just "do X" but "verify X was done" (R08)
- `should-not-be-claude-md-dump-rule-specific`: Content is rule-appropriate, not project configuration that belongs in CLAUDE.md (R09)
- `should-have-reasonable-length`: Rule is long enough to be complete but not so long it gets ignored; under ~300 lines for a single rule file (R10)
- `should-have-must-not-section`: Rule explicitly states what the LLM must NOT do — common mistakes and anti-patterns (R11)
- `should-be-deterministic`: An LLM following the rule would produce consistent behavior across sessions; no room for interpretation on critical steps (R12)
- `should-use-lowercase-kebab-case-filename`: Filename matches `^[a-z][a-z0-9-]*\.md$` (e.g., `testing.md`, `api-design.md`); UPPERCASE stems are reserved for identity files like `SKILL.md` and `CLAUDE.md` (R13)
- `should-stay-under-200-lines-8kb`: Count lines and bytes; larger rules should move content to on-demand skills or external references (O01)
- `should-not-duplicate-another-rule`: Compare against other `.md` files in the same `.claude/rules/` directory; overlapping instructions are processed twice per turn (O02)
- `should-have-globs-when-scoped`: If the rule only applies to specific file patterns (e.g., `.claude/**`, `site/**`), it should have `globs` frontmatter to prevent loading on unrelated work (O03)
- `should-keep-must-not-items-unique`: Each MUST NOT adds a constraint not already expressed imperatively in the body text; restating "You MUST NOT skip this phase" from line 50 in the MUST NOT section wastes per-turn context (O04)
- `may-inline-low-ratio-external-refs`: If an external file reference points to a file where frontmatter exceeds 50% of total lines, suggest inlining the useful content instead (O05)
- `should-limit-unconditional-external-reads`: Rules that mandate reading 6+ external files before any work create high entry cost; consider summaries, on-demand reads, or iterative approaches (O06)
