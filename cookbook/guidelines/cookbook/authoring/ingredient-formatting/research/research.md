# Research: ingredient-formatting

Specification style guides (RFC 7322, the W3C QA framework, the ACT Rules Format) and design-system templates (PatternFly, GOV.UK) support a fixed section order with named headings, but only at recommended strength inside the body, with a short required core and the rest labelled optional. None supports a 22-section MUST order. They agree on a conformance clause, testable requirements and test vectors with expected outcomes, and the W3C outcome vocabularies include "inapplicable", which the draft's passed/failed/partial lacks. Where a section does not apply, IETF and W3C keep it with an explicit "none" statement in the source, while publishers may hide it in the rendered form. Platform owners contradict three template defaults: a single 44x44pt tap target (Apple's minimum varies by platform, Android uses 48dp, Windows 40px, WCAG AA 24px), a custom URL scheme for Apple deep links (Apple strongly recommends universal links) and dotted analytics event names (Firebase allows only letters, digits and underscores). Section structure can be machine-checked with markdownlint MD043 or a custom rule, Vale, or a JSON Schema over the parsed sections; MD043 alone cannot name an optional heading.

**Strength the sources support, for each rule judged unsupported.** A rule judged unsupported here is stated at a strength (mostly MUST) above what any source gives; the note says what the sources do support.

- **if-applicability**: the sources give only the mechanism (a pinned value, conditional checks: json-schema-const, json-schema-if-then). Which files are ingredients is cookbook policy; optional as a researched practice.
- **if-section-order**: a fixed order is recommended, strongly so per RFC 7322 inside the body (rfc-order-strongly-recommended-in-body). PatternFly lets sections be omitted but fixes their headings (patternfly-template-omit-but-fixed-headings). An expert warns against rigid templates (ubl-form-fits-project, ubl-template-clarity). No source requires 22 sections at MUST.
- **if-frontmatter-complete**: the sources give the mechanism (front matter first, required properties: jekyll-front-matter-first, json-schema-required-properties); the field list is cookbook policy. Optional as a researched practice.
- **if-type-field**: mechanism only (json-schema-const); optional.
- **if-title-heading**: an H1 title is recommended (md041-first-line-h1). Exact equality with the front-matter title is policy, and markdownlint's default treats a front-matter title as the H1 and flags a second one (md025-front-matter-title-is-h1); a custom rule can check equality (markdownlint-custom-rules).
- **if-appearance**: an attribute table with defaults is optional (material-attribute-table); no source requires the listed properties.
- **if-states**: recommended. Apple requires a press state for custom buttons (apple-press-state). "Loading" appears in no platform's state list (material-states-list, flutter-interactive-states).
- **if-edge-cases**: recommended. The sources require stated assumptions, limitations and out-of-scope cases (act-assumptions-listed, rfc3552-out-of-scope-stated) rather than an "Edge Cases" heading.
- **if-configuration**: recommended. Keeping the section with a "no configurable options" note is recommended (rfc-empty-iana-section-kept, w3c-qa-label-optional-features).
- **if-logging**: optional, and Apple-only. On Apple's Logger the subsystem and category are optional (apple-logger-optional, apple-logger-subsystem-category).
- **if-platform-notes**: recommended (apple-platform-considerations-none, apple-min-control-size-per-platform). The SwiftUI/Compose/React minimum is policy.
- **if-reference-implementations**: an implementations item is optional in ACT (act-optional-items); deriving it from `index.json` is cookr tool policy with no external source.
- **if-design-decisions**: recommended, on practitioner authority (nygard-adr-status, nygard-consequences-listed).
- **if-change-history**: recommended, on practitioner authority (kac-guiding-principles); versions stay immutable once released (semver-released-immutable). Placing it last is policy.
- **tmpl-approval-fields**: no source. Decision records carry a status rather than approver fields (nygard-adr-status).
- **component-recipe-sections-in-order**: recommended at most (rfc-order-strongly-recommended-in-body, rfc-some-sections-required, patternfly-template-omit-but-fixed-headings); conditional sections fit a schema's if/then (json-schema-if-then).

**The 22 section-order entries (brief question 5): rationale and MAY-omit status.** The research supports a fixed order at recommended strength, with a short required core and every other section labelled optional (short-required-core-labelled-optional-rest). A section that does not apply is kept with a one-line statement in the source rather than silently omitted (inapplicable-section-stated-not-omitted).

1. YAML frontmatter: required first by every front-matter tool (jekyll-front-matter-first). Required.
2. `# Title`: a top-level title is recommended (md041-first-line-h1). Required in practice; whether it repeats the front-matter title is open (md025-front-matter-title-is-h1).
3. `## Overview`: what the component is and when to use it (govuk-description-required, govuk-when-to-use, patternfly-usage-when-to-use), plus when not to (govuk-when-not-to-use). Required core.
4. `## Behavioral Requirements`: the conformance clause, with levels stated (w3c-qa-conformance-clause, w3c-qa-indicate-levels). Required core.
5. `## Appearance`: attribute table with defaults (material-attribute-table), contrast in all states (fluent-contrast-in-all-states). UI-only; may be marked not applicable for infrastructure.
6. `## States`: the interactive states (material-states-list, flutter-interactive-states, apple-press-state). UI-only; may be marked not applicable.
7. `## Accessibility`: name, role, value and target size (wcag-name-role-value, wcag-target-size-minimum-24), keyboard interaction (apg-keyboard-interaction-section). Required core for UI.
8. `## Conformance Test Vectors`: passed, failed and inapplicable examples (act-examples-pass-fail-inapplicable). Required core.
9. `## Edge Cases`: assumptions, limitations and out-of-scope cases (act-assumptions-listed, rfc3552-out-of-scope-stated). Required core.
10. `## Configuration`: options with defaults, or a "none" statement (rfc-empty-iana-section-kept, openfeature-flag-key-and-default). Kept with a note when empty.
11. `## Deep Linking`: verified https links (apple-universal-links-recommended, android-app-links-recommended). MAY omit, supported.
12. `## Localization`: string context for translators (android-string-context). MAY omit, supported.
13. `## Accessibility Options`: reduce motion, contrast, color, text size (apple-reduce-motion, apple-increase-contrast, wcag-use-of-color, wcag-resize-text). MAY omit is weak: text resize is WCAG AA (accessibility-options-include-text-size).
14. `## Feature Flags`: flag key and default (openfeature-flag-key-and-default). MAY omit, supported.
15. `## Analytics`: event names that fit platform limits (firebase-event-name-charset). MAY omit, supported.
16. `## Privacy`: collection, retention, encryption in transit (apple-collect-definition, play-ephemeral-processing, play-encryption-in-transit). Platforms require a statement even when nothing is collected (play-form-even-if-no-data), so MAY omit is weaker than the sources.
17. `## Logging`: subsystem and category, Apple-only and optional there (apple-logger-optional). Its MUST presence is unsupported.
18. `## Platform Notes`: per-platform considerations with an explicit "none" for a platform (apple-platform-considerations-none). Recommended.
19. `## Reference Implementations`: an optional implementations item (act-optional-items); derived, never authored, is policy.
20. `## Design Decisions`: decision, status and consequences (nygard-adr-status, nygard-consequences-listed). Recommended.
21. `## Compliance`: check results that include inapplicable (earl-outcome-values, act-outcome-types). Recommended, with the vocabulary contradicted.
22. `## Change History`: an entry per version, ISO dates (kac-guiding-principles, kac-iso-dates). Recommended.

**Reconciling the component-recipe list (brief question 6).** C's 7-section list (Overview, Behavioral Requirements, Appearance, States, Accessibility, Conformance Test Vectors, Edge Cases) is a strict prefix-order subset of D's sections 3–9: the same seven, in the same order. It adds nothing and can only drift from D, so `template-conformance` drops the list when it is next written and points to ingredient-formatting's section order instead.

## Best practices

- **rfc-order-strongly-recommended-in-body**: The RFC Style Guide gives a fixed element order but only strongly recommends it inside the document body; the order is required only outside the body (front and back matter). Quote: "Within the body of the memo, the order shown above is strongly recommended. Exceptions may be questioned. Outside the body of the memo, the order above is required." Source: [RFC 7322: RFC Style Guide](https://www.rfc-editor.org/rfc/rfc7322).
- **rfc-some-sections-required**: In the RFC series only some of the listed sections are required; the rest appear when they apply. Quote: "A published RFC will largely contain the elements in the following list. Some of these sections are required, as noted." Source: [RFC 7322: RFC Style Guide](https://www.rfc-editor.org/rfc/rfc7322).
- **rfc-security-considerations-required**: A long-lived specification template keeps a short list of always-required sections; for RFCs, Security Considerations is one of them. Quote: "All RFCs must contain a section that discusses the security considerations relevant to the specification" Source: [RFC 7322: RFC Style Guide](https://www.rfc-editor.org/rfc/rfc7322).
- **rfc-empty-iana-section-kept**: IANA prefers that an IANA Considerations section with nothing to say be kept, saying so, rather than omitted, so a reader can tell a deliberate 'none' from an omission. Quote: "IANA prefers that these "empty" IANA Considerations sections be left in the document for the record: it makes it clear later on that the document explicitly said that no IANA actions were needed (and that it wasn't just omitted)." Source: [RFC 8126: Guidelines for Writing an IANA Considerations Section in RFCs](https://www.rfc-editor.org/rfc/rfc8126).
- **rfc-no-actions-statement**: A document with nothing for a mandated section should, once the authors confirm it, still include the section with an explicit 'no actions' statement. Quote: "In order to make it clear to IANA that it has no actions to perform (and that the author has consciously made such a determination), such documents should, after the authors confirm that this is the case, include an IANA Considerations section that states:" Source: [RFC 8126: Guidelines for Writing an IANA Considerations Section in RFCs](https://www.rfc-editor.org/rfc/rfc8126).
- **rfc-editor-removes-empty-iana**: The kept-but-empty section is a drafting-stage convention: the RFC Editor removes an empty IANA Considerations section at publication, though the Internet-Draft must carry it. Quote: "The RFC Editor will remove an IANA Considerations section that says there are no IANA considerations (although such a section is required in the Internet-Draft preceding the RFC)." Source: [RFC 7322: RFC Style Guide](https://www.rfc-editor.org/rfc/rfc7322).
- **rfc3552-out-of-scope-stated**: A specification's required security section must say what is out of scope and why, not only what is covered. Quote: "Authors MUST describe 1. which attacks are out of scope (and why!)" Source: [RFC 3552: Guidelines for Writing RFC Text on Security Considerations](https://www.rfc-editor.org/rfc/rfc3552).
- **rfc3552-security-section-required**: Every RFC is required to carry a Security Considerations section. Quote: "All RFCs are required by RFC 2223 to contain a Security Considerations section." Source: [RFC 3552: Guidelines for Writing RFC Text on Security Considerations](https://www.rfc-editor.org/rfc/rfc3552).
- **w3c-qa-conformance-clause**: W3C's specification guidelines require a specification to include a conformance clause. Quote: "Include a conformance clause." Source: [QA Framework: Specification Guidelines](https://www.w3.org/TR/qaframe-spec/).
- **w3c-qa-consistent-requirement-style**: Conformance requirements must be written in one consistent style, and the specification must explain how to tell them apart from other text. Quote: "Use a consistent style for conformance requirements and explain how to distinguish them." Source: [QA Framework: Specification Guidelines](https://www.w3.org/TR/qaframe-spec/).
- **w3c-qa-indicate-levels**: A specification must indicate which of its requirements are mandatory, which recommended and which optional. Quote: "Indicate which conformance requirements are mandatory, which are recommended, and which are optional." Source: [QA Framework: Specification Guidelines](https://www.w3.org/TR/qaframe-spec/).
- **w3c-qa-test-assertions**: A test assertion is a testable statement derived from a specification's requirements, from which test cases are built; W3C advises providing them. Quote: "A test assertion is a measurable or testable statement of behavior, action, or condition. It is contained within or derived from the specification's requirements and provides a normative foundation from which one or more test cases can be built." Source: [QA Framework: Specification Guidelines](https://www.w3.org/TR/qaframe-spec/).
- **w3c-qa-template-test-assertion-section**: W3C suggests that the template for new feature proposals include a section for test assertions. Quote: "Create a template for new feature proposals that includes a section for adding test assertions." Source: [QA Framework: Specification Guidelines](https://www.w3.org/TR/qaframe-spec/).
- **w3c-qa-label-optional-features**: Optional features should be labelled so they can all be found, and when there are none the conformance section should say so rather than stay silent. Quote: "When introducing an optional feature in the specification, label it as such, so that it is easy to find all the optional features defined in the specification. If there are no optional features, state that in the conformance section." Source: [QA Framework: Specification Guidelines](https://www.w3.org/TR/qaframe-spec/).
- **act-required-items**: W3C's ACT Rules Format fixes a minimum set of items every rule document must contain. Quote: "An ACT Rule must consist of at least the following items: Descriptive Title Rule Identifier Rule Description Rule Type Accessibility Requirements Mapping" Source: [Accessibility Conformance Testing (ACT) Rules Format 1.1](https://www.w3.org/TR/act-rules-format/).
- **act-optional-items**: The ACT Rules Format separates its required items from a short list of items it labels optional, implementations among them. Quote: "An ACT Rule MAY also contain: Related Rules (optional) under Background Other Resources (optional) under Background Issues List (optional) Implementations (optional) Acknowledgments (optional)" Source: [Accessibility Conformance Testing (ACT) Rules Format 1.1](https://www.w3.org/TR/act-rules-format/).
- **act-examples-pass-fail-inapplicable**: Each ACT rule must carry examples for passed, failed and inapplicable outcomes, each pairing an input snippet with its expected outcome. Quote: "Each rule must have one or more examples for passed, failed, and inapplicable outcomes. An example consists of two pieces of data, a snippet of each input aspect for a rule, and the expected outcome for that rule." Source: [Accessibility Conformance Testing (ACT) Rules Format 1.1](https://www.w3.org/TR/act-rules-format/).
- **act-outcome-types**: ACT outcomes include 'inapplicable' alongside passed and failed. Quote: "An outcome can be one of the five following types: inapplicable: No part of the test subject matches the applicability passed: A test target meets all expectations failed: A test target does not meet all expectations" Source: [Accessibility Conformance Testing (ACT) Rules Format 1.1](https://www.w3.org/TR/act-rules-format/).
- **act-assumptions-listed**: An ACT rule must list its known assumptions, limitations and exceptions. Quote: "An ACT Rule must list any known assumptions, limitations or any exceptions for the evaluation, the test environment, technologies being used or the subject being tested." Source: [Accessibility Conformance Testing (ACT) Rules Format 1.1](https://www.w3.org/TR/act-rules-format/).
- **earl-outcome-values**: W3C's EARL recommends five outcome values for a test result: passed, failed, cantTell, inapplicable and untested. It has no 'partial'. Quote: "Where applicable it is recommended to use one of the following instances of earl:OutcomeValue, to categorize the outcome of carrying out the test: earl:passed Passed - the subject passed the test. earl:failed Failed - the subject failed the test. earl:cantTell Cannot tell - it is unclear if the subject passed or failed the test. earl:inapplicable Inapplicable - the test is not applicable to the subject. earl:untested Untested - the test has not been carried out." Source: [Evaluation and Report Language (EARL) 1.0 Schema](https://www.w3.org/TR/EARL10-Schema/).
- **oasis-ta-identifier**: A test assertion carries a unique identifier that maps it to the specification statement it tests; universal uniqueness is recommended. Quote: "Identifier A unique identifier of the test assertion. It facilitates the mapping of assertions to specification statements. It is recommended that the identifier be made universally unique." Source: [Test Assertions Guidelines Version 1.0 (Committee Note 02)](http://docs.oasis-open.org/tag/guidelines/v1.0/cn02/guidelines-v1.0-cn02.html).
- **oasis-ta-normative-source**: A test assertion names the precise normative statement it tests. Quote: "Normative Source The part of the test assertion that identifies the precise specification requirements or normative statements that the test assertion is addressing." Source: [Test Assertions Guidelines Version 1.0 (Committee Note 02)](http://docs.oasis-open.org/tag/guidelines/v1.0/cn02/guidelines-v1.0-cn02.html).
- **semver-released-immutable**: Under Semantic Versioning, a released version's contents must not change; any change is a new version. Quote: "Once a versioned package has been released, the contents of that version MUST NOT be modified. Any modifications MUST be released as a new version." Source: [Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html).
- **uuid-unique-identifier**: A UUID is designed to be unique across space and time, which suits it as a stable link target for a check or an artifact. Quote: "A UUID is 128 bits long and is intended to guarantee uniqueness across space and time." Source: [RFC 9562: Universally Unique IDentifiers (UUIDs)](https://www.rfc-editor.org/rfc/rfc9562).
- **if-section-order-prior**: The cookbook rule under verification, as it stood at the base commit. Quote: "Ingredients MUST follow this section order. Optional sections (marked MAY) can be omitted entirely but MUST NOT appear out of order. 1. YAML frontmatter 2. `# Title` 3. `## Overview` 4. `## Behavioral Requirements` 5. `## Appearance` 6. `## States` 7. `## Accessibility` 8. `## Conformance Test Vectors` 9. `## Edge Cases` 10. `## Configuration` 11. `## Deep Linking` (MAY omit) 12. `## Localization` (MAY omit) 13. `## Accessibility Options` (MAY omit) 14. `## Feature Flags` (MAY omit) 15. `## Analytics` (MAY omit) 16. `## Privacy` (MAY omit) 17. `## Logging` 18. `## Platform Notes` 19. `## Reference Implementations` (MAY: derived from `index.json` when compiled; never authored) 20. `## Design Decisions` 21. `## Compliance` 22. `## Change History`" Source: [ingredient-formatting (ingredient-formatting.md)](git:071e52f9572bf4b7c534cfcf95fb111282abc423:tbd/compliance/artifact-formatting/ingredient-formatting.md).

## Known solutions

- **md043-enforces-heading-structure**: markdownlint's MD043 checks a file's headings against a configured list, enforcing one heading structure across a set of files. Quote: "This rule is triggered when the headings in a file do not match the array of headings passed to the rule. It can be used to enforce a standard heading structure for a set of files." Source: [MD043 - Required heading structure](https://github.com/DavidAnson/markdownlint/blob/main/doc/md043.md).
- **md043-wildcards-only**: MD043 expresses optional sections only through wildcards (zero or more, one or more, or exactly one unspecified heading). It cannot name a specific heading as optional, so a long order with named optional sections needs a custom rule. Quote: "Use the special value `*` meaning "zero or more unspecified headings", the special value `+` meaning "one or more unspecified headings", or the special value `?` meaning "exactly one unspecified heading"" Source: [MD043 - Required heading structure](https://github.com/DavidAnson/markdownlint/blob/main/doc/md043.md).
- **md025-front-matter-title-is-h1**: markdownlint treats a front-matter `title` as the document's top-level heading, so by default a following `# Title` H1 is reported as a second top-level heading. Quote: "If [YAML](https://wikipedia.org/wiki/YAML) front matter is present and contains a `title` property (commonly used with blog posts), this rule treats that as a top level heading and will report a violation for any subsequent top-level headings." Source: [MD025 - Multiple top-level headings in the same document](https://github.com/DavidAnson/markdownlint/blob/main/doc/md025.md).
- **md041-first-line-h1**: markdownlint's MD041 checks that a document has a title by requiring its first line to be a top-level heading. No built-in rule checks that the H1 equals the front-matter title. Quote: "This rule is intended to ensure documents have a title and is triggered when the first line in a document is not a top-level ([HTML][HTML] `h1`) heading" Source: [MD041 - First line in a file should be a top-level heading](https://github.com/DavidAnson/markdownlint/blob/main/doc/md041.md).
- **markdownlint-custom-rules**: markdownlint custom rules can do anything the built-in rules can, so title equality or a section order with named optional sections can be checked by a custom rule. Quote: "Custom rules can do everything the built-in rules can and are defined inline or imported from another package" Source: [Custom Rules](https://github.com/DavidAnson/markdownlint/blob/main/doc/CustomRules.md).
- **vale-occurrence-min-flags-absence**: Vale's occurrence check can make the absence of a token in a scope a violation, for example a required heading. Quote: "`min` makes absence a violation: a scope with fewer than `min` matches is flagged." Source: [occurrence](https://docs.vale.sh/checks/occurrence.md).
- **vale-script-arbitrary-rules**: Vale's script check runs arbitrary logic in Tengo, enough to check a section order with named optional sections. Quote: "`script` allows for the creation of arbitrary logic-based rules using [Tengo](https://tengolang.com/), a Go-like scripting language." Source: [script](https://docs.vale.sh/checks/script.md).
- **json-schema-required-properties**: JSON Schema's `required` keyword checks that every named property is present, which fits a frontmatter field list. Quote: "An object instance is valid against this keyword if every item in the array is the name of a property in the instance." Source: [JSON Schema Validation: A Vocabulary for Structural Validation of JSON (draft 2020-12)](https://json-schema.org/draft/2020-12/json-schema-validation).
- **json-schema-const**: JSON Schema's `const` pins a value, such as `type: ingredient`. Quote: "An instance validates successfully against this keyword if its value is equal to the value of the keyword." Source: [JSON Schema Validation: A Vocabulary for Structural Validation of JSON (draft 2020-12)](https://json-schema.org/draft/2020-12/json-schema-validation).
- **json-schema-prefixitems-positional**: JSON Schema's `prefixItems` validates array elements by position, so a section order can be checked only if the sections are modelled as an ordered array. Quote: "Validation succeeds if each element of the instance validates against the schema at the same position, if any." Source: [JSON Schema: A Media Type for Describing JSON Documents (draft 2020-12)](https://json-schema.org/draft/2020-12/json-schema-core).
- **json-schema-objects-unordered**: In JSON Schema's data model objects are unordered, so the order of frontmatter keys cannot be checked; only arrays carry order. ## Platform guidelines

- **apple-min-control-size-per-platform**: Apple gives a default and a smaller minimum control size for each platform: iOS and iPadOS 44x44 pt default, 28x28 pt minimum; macOS 28 and 20; tvOS 66 and 56; visionOS 60 and 28; watchOS 44 and 28. Quote: "Platform Default control size Minimum control size iOS, iPadOS 44x44 pt 28x28 pt macOS 28x28 pt 20x20 pt tvOS 66x66 pt 56x56 pt visionOS 60x60 pt 28x28 pt watchOS 44x44 pt 28x28 pt" Source: [Accessibility - Human Interface Guidelines](https://developer.apple.com/design/human-interface-guidelines/accessibility).
- **apple-strive-min-control-size**: Apple asks for the recommended minimum control size of each platform, not one value. Quote: "Strive to meet the recommended minimum control size for each platform to ensure controls and menus are comfortable for all when tapping and clicking." Source: [Accessibility - Human Interface Guidelines](https://developer.apple.com/design/human-interface-guidelines/accessibility).
- **apple-button-hit-region-44**: Apple's Buttons page sets a general 44x44 pt hit region, 60x60 pt in visionOS. Quote: "As a general rule, a button needs a hit region of at least 44x44 pt — in visionOS, 60x60 pt — to ensure that people can select it easily, whether they use a fingertip, a pointer, their eyes, or a remote." Source: [Buttons - Human Interface Guidelines](https://developer.apple.com/design/human-interface-guidelines/buttons).
- **apple-press-state**: Apple requires a press state for a custom button. Quote: "Always include a press state for a custom button. Without a press state, a button can feel unresponsive, making people wonder if it’s accepting their input." Source: [Buttons - Human Interface Guidelines](https://developer.apple.com/design/human-interface-guidelines/buttons).
- **apple-platform-considerations-none**: Apple's per-platform section names each platform and says so explicitly when a platform has nothing extra. Quote: "No additional considerations for tvOS." Source: [Buttons - Human Interface Guidelines](https://developer.apple.com/design/human-interface-guidelines/buttons).
- **apple-reduce-motion**: Apple asks apps to respond to the Reduce Motion setting. Quote: "People who are prone to these effects can turn on the Reduce Motion accessibility setting. When this setting is active, ensure your app or game responds by reducing automatic and repetitive animations, including zooming, scaling, and peripheral motion." Source: [Accessibility - Human Interface Guidelines](https://developer.apple.com/design/human-interface-guidelines/accessibility).
- **apple-increase-contrast**: Apple asks for a higher-contrast scheme when Increase Contrast is on. Quote: "If your app doesn’t provide this minimum contrast by default, ensure it at least provides a higher contrast color scheme when the system setting Increase Contrast is turned on." Source: [Accessibility - Human Interface Guidelines](https://developer.apple.com/design/human-interface-guidelines/accessibility).
- **apple-more-than-color**: Apple asks that information not be conveyed by color alone. Quote: "Convey information with more than color alone. Source: [Accessibility - Human Interface Guidelines](https://developer.apple.com/design/human-interface-guidelines/accessibility).
- **apple-dynamic-type**: Dynamic Type lets people resize text on most Apple platforms: a display option next to Reduce Motion and Increase Contrast. Quote: "Dynamic Type is a system-level feature in iOS, iPadOS, tvOS, visionOS, and watchOS that lets people adjust the size of visible text on their device to ensure readability and comfort." Source: [Typography - Human Interface Guidelines](https://developer.apple.com/design/human-interface-guidelines/typography).

- **apple-logger-subsystem-category**: On Apple platforms a logger's subsystem is a large functional area of the app, and its category a specific area within that subsystem. ## The expert's view

- **ubl-form-fits-project**: An experienced design-doc author at Google says such documents should take whatever form suits the project, not follow a strict guideline. Quote: "Design docs are informal documents and thus don’t follow a strict guideline for their content. Rule #1 is: Write them in whatever form makes the most sense for the particular project." Source: [Design Docs at Google](https://www.industrialempathy.com/posts/design-docs-at-google/).
- **ubl-template-clarity**: The same author: a template does no harm, but clarity is what matters. Quote: "It doesn’t hurt using a template, but the clarity is the important part." Source: [Design Docs at Google](https://www.industrialempathy.com/posts/design-docs-at-google/).
- **nygard-adr-status**: A decision record carries a status: proposed until the stakeholders agree, accepted after. Quote: "A decision may be "proposed" if the project stakeholders haven't agreed with it yet, or "accepted" once it is agreed." Source: [Documenting Architecture Decisions](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions).
- **nygard-consequences-listed**: A decision record lists all of the decision's consequences. Quote: "This section describes the resulting context, after applying the decision. All consequences should be listed here" Source: [Documenting Architecture Decisions](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions).
- **kac-guiding-principles**: A change history has an entry for every version, newest first, each with its release date. Quote: "Guiding Principles Changelogs are for humans, not machines. There should be an entry for every single version. The same types of changes should be grouped. Versions and sections should be linkable. The latest version comes first. The release date of each version is displayed. Mention whether you follow Semantic Versioning." Source: [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/).
- **kac-iso-dates**: Change-history dates should be ISO 8601. Quote: "These reasons, and the fact this date format is an ISO standard, are why it is the recommended date format for changelog entries." Source: [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/).
