# Research: principle-formatting

Outside practice supports the shape of a principle. It supports required metadata that a schema checks, one title per document, the main point first, specific guidance in bullets, and a dated, newest-first entry for each version. Four draft rules are not supported at the strength they state:

- No source requires the H1 to equal the frontmatter title.
- The statement-first practice is a recommendation, not a requirement.
- The change-history practice is a recommendation, not a requirement.
- No source supports a ~50-line cap.

The length evidence sets budgets, not a per-principle number. Agent hosts bound the always-loaded total and the size of on-demand skill bodies. Studies show that adherence and recall fall as context and instruction density grow, and that models favor earlier content. The Standard's role-separated parts fit Anthropic's progressive disclosure and its evaluator-optimizer pattern. The internal mechanics (the role vocabulary, every part roled, skill names, routing) are cookbook design that no outside source can confirm.

## Best practices

*Best practices: what is current best practice for this topic?*

- **lead-with-main-point**: Start with the most important information, so a reader who stops early still gets the main point. Quote: "Start content with the most important piece of information so readers can get the main point, regardless of how much they read." Source: [Inverted Pyramid: Writing for Comprehension](https://www.nngroup.com/articles/inverted-pyramid/).
- **pep-preamble-required**: A standards-process document type can require a metadata preamble with fixed, required headers. Quote: "Each PEP must begin with an :rfc:`2822` style header preamble." Source: [PEP 1](https://raw.githubusercontent.com/python/peps/main/peps/pep-0001.rst).
- **pep-abstract-short**: A structured document opens with a short abstract, and PEP 1 states this as a "should". Quote: "Abstract -- a short (~200 word) description of the technical issue being addressed." Source: [PEP 1](https://raw.githubusercontent.com/python/peps/main/peps/pep-0001.rst).
- **adr-short-record**: An architecture decision record, a close analogue of a principle, is one or two pages long. Quote: "The whole document should be one or two pages long." Source: [Documenting Architecture Decisions](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions).
- **adr-motivation-lost**: Record the motivation behind a decision, because it is the hardest part to recover later. Quote: "One of the hardest things to track during the life of a project is the motivation behind certain decisions." Source: [Documenting Architecture Decisions](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions).
- **changelog-entry-per-version**: Give the change history an entry for every version. Quote: "There should be an entry for every single version." Source: [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).
- **changelog-latest-first**: List the latest version first. Quote: "The latest version comes first." Source: [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).
- **changelog-dated**: Show each version's date. Quote: "The release date of each version is displayed." Source: [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).
- **docs-as-code**: Write documentation with the same tools as code, including review and automated tests. Quote: "Documentation as Code (Docs as Code) refers to a philosophy that you should be writing documentation with the same tools as code:" Source: [Docs as code](https://www.writethedocs.org/guide/docs-as-code/).
- **pf-title-heading-prior**, **pf-statement-prior**, **pf-change-history-prior**: These are the draft's own rules. No outside source supports them at MUST. Source: the base-commit draft `tbd/compliance/artifact-formatting/principle-formatting.md`.

## Known solutions

*Known solutions: what solutions, patterns, libraries and tools already exist, and how do they compare?*

Tools can decide the structural checks. They can confirm that required fields exist and that the type is `principle` (JSON Schema `required`, `const`; Astro schemas), that a single title heading comes first (markdownlint MD025, MD041), that an H1 matches the front-matter title (a markdownlint custom rule reading `frontMatterLines`), and that a final `## Change History` heading exists (MD043). They can also confirm a statement paragraph's sentence count and a body's word or line count (Vale `metric`, a custom rule), and that a guidance list exists (Vale's `list` variable). A reviewer must judge whether the statement holds the core idea, whether the guidance is actionable, and whether the principle is an anchor rather than a guide.

- **md041-title-heading**: markdownlint MD041 treats a document's first top-level heading as its title. Quote: "Rationale: The top-level heading often acts as the title of a document." Source: [MD041](https://raw.githubusercontent.com/DavidAnson/markdownlint/main/doc/md041.md).
- **md041-frontmatter-title-satisfies**: By default MD041 accepts a front-matter title in place of an H1. It does not check that the two match. Quote: "If [YAML][YAML] front matter is present and contains a `title` property (commonly used with blog posts), this rule will not report a violation." Source: [MD041](https://raw.githubusercontent.com/DavidAnson/markdownlint/main/doc/md041.md).
- **md025-single-title**: MD025 enforces a single H1 that serves as the title. Quote: "To fix, structure your document so there is a single h1 heading that is the title for the document." Source: [MD025](https://raw.githubusercontent.com/DavidAnson/markdownlint/main/doc/md025.md).
- **md025-frontmatter-title-counts**: With default settings, MD025 counts a front-matter title as the H1 and flags any later `# Title`. Quote: "this rule treats that as a top level heading and will report a violation for any subsequent top-level headings." Source: [MD025](https://raw.githubusercontent.com/DavidAnson/markdownlint/main/doc/md025.md).
- **md043-required-headings**: MD043 enforces a required heading structure across a set of files. Quote: "It can be used to enforce a standard heading structure for a set of files." Source: [MD043](https://raw.githubusercontent.com/DavidAnson/markdownlint/main/doc/md043.md).
- **md013-measures-line-width**: MD013 measures the width of each line, not the length of a document. Quote: "This rule is triggered when there are lines that are longer than the configured `line_length` (default: 80 characters)." Source: [MD013](https://raw.githubusercontent.com/DavidAnson/markdownlint/main/doc/md013.md).
- **markdownlint-custom-rules-frontmatter**: A custom rule receives the front-matter lines separately from the body lines. Quote: "`frontMatterLines` is an `Array` of `String` values corresponding to any lines of front matter (not present in the `lines` `Array`)." Source: [Custom Rules](https://raw.githubusercontent.com/DavidAnson/markdownlint/main/doc/CustomRules.md).
- **vale-metric-formulas**: Vale's metric check evaluates formulas over word, sentence, paragraph, list and heading counts. Quote: "metric enforces arbitrary formulas based on pre-defined, built-in variables." Source: [metric](https://vale.sh/docs/checks/metric).
- **vale-occurrence**: Vale's occurrence check bounds how often a token appears in a scope. Quote: "occurrence enforces the maximum or minimum number of times a particular token can appear in a given scope." Source: [occurrence](https://vale.sh/docs/checks/occurrence).
- **vale-script**: Vale's script check runs arbitrary logic for structural checks. Quote: "script allows for the creation of arbitrary logic-based rules using Tengo, a Go-like scripting language." Source: [script](https://vale.sh/docs/checks/script).
- **json-schema-required**: JSON Schema `required` lists the properties a document must have. Quote: "one can provide a list of required properties using the required keyword." Source: [JSON Schema object](https://json-schema.org/understanding-json-schema/reference/object).
- **json-schema-const**: JSON Schema `const` fixes a property to a single value. Quote: "The const keyword is used to restrict a value to a single value." Source: [JSON Schema const](https://json-schema.org/understanding-json-schema/reference/const).
- **astro-frontmatter-schema**: Astro validates every Markdown file's frontmatter against a collection schema. Quote: "Schemas enforce consistent frontmatter or entry data within a collection through Zod validation." Source: [Content collections](https://docs.astro.build/en/guides/content-collections/).
- **evaluator-optimizer**: Anthropic's evaluator-optimizer pattern has one call generate and another evaluate, which is the pattern behind pairing each builder with a verifier. Quote: "In the evaluator-optimizer workflow, one LLM call generates a response while another provides evaluation and feedback in a loop." Source: [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents).
- **agentsmd-any-headings**: The AGENTS.md format imposes no heading structure, so a required structure serves authors and tools rather than the agent. Quote: "Use any headings you like; the agent simply parses the text you provide." Source: [AGENTS.md](https://agents.md/).
- **roles-vocabulary-prior**, **roles-every-part-roled-prior**, **roles-principle-skill-names-prior**, **roles-principle-routing-prior**: These are the cookbook's own role mechanics, defined in conventions.md. No outside source bears on them. Source: the base-commit `guide/introduction/conventions.md`.

## Platform guidelines

*Platform guidelines: what do the platform owners' own guidelines say, for each platform the topic touches (Apple, Android, Windows, web, the databases and runtimes concerned)?*

A principle is a Markdown file that agents read, so the relevant platforms are the agent hosts (Claude Code, Agent Skills, Codex, Copilot, Cursor) and the owners of documentation style (Google, Microsoft, Diátaxis). Apple, Android and the database owners publish nothing that bears on the topic.

- **claude-md-200-lines**: Claude Code targets under 200 lines per always-loaded file. Quote: "target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence." Source: [How Claude remembers your project](https://code.claude.com/docs/en/memory).
- **claude-md-specific-concise**: Claude follows specific, concise instructions more consistently. Quote: "The more specific and concise your instructions, the more consistently Claude follows them." Source: [How Claude remembers your project](https://code.claude.com/docs/en/memory).
- **claude-md-headers-and-bullets**: Group instructions under headers and bullets. Quote: "Organized sections are easier for Claude to follow than dense paragraphs." Source: [How Claude remembers your project](https://code.claude.com/docs/en/memory).
- **claude-md-conflicts**: When two instructions contradict, Claude may pick either one. Quote: "if two instructions contradict each other, Claude may pick one arbitrarily." Source: [How Claude remembers your project](https://code.claude.com/docs/en/memory).
- **claude-md-every-line-costs**: Every always-loaded line costs some attention on every task. Quote: "every line in it takes a little of Claude's attention on *every* task, whether it's relevant or not." Source: [Best practices for Claude Code](https://code.claude.com/docs/en/best-practices).
- **claude-md-only-what-agent-lacks**: Hold only what the agent could not work out for itself. Quote: "the file works best when it only holds what Claude couldn't work out from the code itself:" Source: [Best practices for Claude Code](https://code.claude.com/docs/en/best-practices).
- **skills-lighter-than-always-loaded**: Only a skill's name and description are seen every session. The body loads when a task needs it. Quote: "Skills are also lighter on context than `CLAUDE.md` for this kind of thing." Source: [Best practices for Claude Code](https://code.claude.com/docs/en/best-practices).
- **skill-only-new-context**: Add only context the model does not already have. Quote: "Only add context Claude doesn’t already have." Source: [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices).
- **skill-body-500-lines**: Keep an on-demand skill body under 500 lines. Quote: "Keep the `SKILL.md` body under 500 lines for optimal performance." Source: [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices).
- **skill-frontmatter-required**: Skill frontmatter has required fields with validation rules. Quote: "The `SKILL.md` frontmatter requires `name` and `description` fields with specific validation rules:" Source: [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices).
- **skill-description-what-and-when**: The description should say what the skill does and when to use it. Quote: "should include both what the Skill does and when to use it." Source: [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices).
- **agentskills-progressive-disclosure**: The body loads on activation, is recommended under 5000 tokens, and moves detailed reference material to separate files. Quote: "Instructions (< 5000 tokens recommended): The full SKILL.md body is loaded when the skill is activated" Source: [Agent Skills specification](https://agentskills.io/specification).
- **agentskills-metadata-always-loaded**: Only the name and description load at startup. Quote: "Metadata (~100 tokens): The name and description fields are loaded at startup for all skills" Source: [Agent Skills specification](https://agentskills.io/specification).
- **cursor-rules-500-lines**: Cursor keeps each rule under 500 lines and splits large rules into composable ones. Quote: "Keep rules under 500 lines" Source: [Cursor Rules](https://cursor.com/docs/context/rules).
- **cursor-focused-actionable**: Good rules are focused, actionable and scoped. Quote: "Good rules are focused, actionable, and scoped." Source: [Cursor Rules](https://cursor.com/docs/context/rules).
- **cursor-reference-not-copy**: Reference a file instead of copying it into a rule. Quote: "Reference files instead of copying their contents." Source: [Cursor Rules](https://cursor.com/docs/context/rules).
- **codex-32kib-combined**: Codex caps the combined size of instruction files at 32 KiB by default. Quote: "stops adding files once the combined size reaches the limit defined by project_doc_max_bytes (32 KiB by default)." Source: [Custom instructions with AGENTS.md](https://developers.openai.com/codex/guides/agents-md).
- **codex-lint-in-ci**: Keep rules concise and leave formatting and lint checks to CI. Quote: "reserve formatting and lint checks for CI." Source: [Custom instructions with AGENTS.md](https://developers.openai.com/codex/guides/agents-md).
- **copilot-two-pages**: GitHub's sample prompt for generating Copilot instructions limits them to two pages. Quote: "Instructions must be no longer than 2 pages." Source: [Adding repository custom instructions for GitHub Copilot](https://docs.github.com/en/copilot/how-tos/configure-custom-instructions/add-repository-instructions).
- **diataxis-explain-why**: An explanation page gives the why: design decisions, constraints and implications. Quote: "explain why things are so - design decisions, historical reasons, technical constraints" Source: [Explanation - Diátaxis](https://diataxis.fr/explanation/).
- **diataxis-keep-bounded**: Keep instruction out of explanation, because it belongs in its own place. Quote: "documentation already has other places for these, and allowing them to creep in interferes with the explanation itself" Source: [Explanation - Diátaxis](https://diataxis.fr/explanation/).
- **google-single-h1**: Use one unique H1 per page. Quote: "only use a level-1 heading once on a page." Source: [Headings and titles](https://developers.google.com/style/headings).
- **google-opening-sentence**: The opening sentence matters most, because busy readers may skip the rest. Quote: "The opening sentence is the most important sentence of any paragraph." Source: [Paragraphs](https://developers.google.com/tech-writing/one/paragraphs).
- **google-paragraph-length**: Readers welcome paragraphs of three to five sentences. Quote: "Readers generally welcome paragraphs containing three to five sentences" Source: [Paragraphs](https://developers.google.com/tech-writing/one/paragraphs).
- **ms-lead-with-most-important**: Lead with what matters most. Quote: "Lead with what's most important. Front-load keywords for scanning." Source: [Top 10 tips for Microsoft style and voice](https://learn.microsoft.com/en-us/style-guide/top-10-tips-style-voice).
- **ms-be-brief**: Be brief. Quote: "Give customers just enough information to make decisions confidently. Prune every excess word." Source: [Top 10 tips for Microsoft style and voice](https://learn.microsoft.com/en-us/style-guide/top-10-tips-style-voice).
- **ms-first-screen**: Content on the first screen is the most likely to be read. Quote: "Content on the first screen (also called above the fold) is the most likely to be read." Source: [Scannable content](https://learn.microsoft.com/en-us/style-guide/scannable-content/).
- **ms-lists-short**: A list has two to seven short items that share one structure. Quote: "A list should have at least two items but (if possible) no more than seven items." Source: [Lists](https://learn.microsoft.com/en-us/style-guide/scannable-content/lists).
- **prompting-explain-why**: Explaining an instruction's motivation produces better-targeted behavior. Quote: "Providing context or motivation behind your instructions ... can give Claude more information about your goals and help it deliver more targeted responses." Source: [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices).

## The expert's view

*The expert's view: if we hired an expert consultant in this topic, what would they tell us: what to do, what to avoid, and what people usually get wrong?*

An expert would tell us to budget the total an agent always loads, to put the key guidance first, and to keep each principle as small as its job allows. They would also say that a fixed line count is the wrong lever, that minimal does not mean short, that emphasis does not rescue a lost line, and that checks a script can decide belong in a linter, not in the agent's prose.

- **context-finite-resource**: Treat context as a finite resource with diminishing returns. Quote: "Context, therefore, must be treated as a finite resource with diminishing marginal returns." Source: [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents).
- **smallest-high-signal-set**: Look for the smallest set of high-signal tokens that produces the desired outcome. Quote: "finding the smallest possible set of high-signal tokens that maximize the likelihood of some desired outcome." Source: [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents).
- **minimal-not-short**: Minimal is not the same as short. Give the agent enough information to adhere. Quote: "(Note that minimal does not necessarily mean short; you still need to give the agent sufficient information up front to ensure it adheres to the desired behavior.)" Source: [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents).
- **right-altitude**: Write instructions specific enough to guide behavior yet flexible enough to work as heuristics. Quote: "The optimal altitude strikes a balance: specific enough to guide behavior effectively, yet flexible enough to provide the model with strong heuristics to guide behavior." Source: [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents).
- **ifscale-density-degrades**: Instruction-following accuracy falls as the number of instructions grows. Quote: "even the best frontier models only achieve 68% accuracy at the max density of 500 instructions." Source: [How Many Instructions Can LLMs Follow at Once?](https://arxiv.org/abs/2507.11538).
- **ifscale-earlier-instructions**: Models favor earlier instructions. Quote: "bias towards earlier instructions" Source: [How Many Instructions Can LLMs Follow at Once?](https://arxiv.org/abs/2507.11538).
- **lost-in-the-middle**: Models use information at the start and end of a context best and lose what sits in the middle. Quote: "performance is often highest when relevant information occurs at the beginning or end of the input context, and significantly degrades when models must access relevant information in the middle of long contexts" Source: [Lost in the Middle](https://arxiv.org/abs/2307.03172).
- **chroma-context-rot**: Model performance becomes less reliable as input grows longer. Quote: "their performance grows increasingly unreliable as input length grows." Source: [Context Rot](https://research.trychroma.com/context-rot).
- **claude-md-line-gets-lost**: Shouting does not rescue an ignored line. Either the file is too long or the rule needs enforcement. Quote: "adding IMPORTANT probably won't fix it. Either the file has grown long enough that the line gets lost" Source: [Best practices for Claude Code](https://code.claude.com/docs/en/best-practices).
- **claude-md-hooks-for-absolutes**: What must happen every time belongs in a hook or setting, not in prose. Quote: "If something has to happen every time, make it a hook, a deny rule, or a managed setting." Source: [Best practices for Claude Code](https://code.claude.com/docs/en/best-practices).
- **cursor-use-a-linter**: Do not copy style guides into agent rules. Use a linter instead. Quote: "Copying entire style guides: Use a linter instead. Agent already knows common style conventions." Source: [Cursor Rules](https://cursor.com/docs/context/rules).
- **cursor-start-simple**: Add a rule only when the agent repeats a mistake. Quote: "Add rules only when you notice Agent making the same mistake repeatedly." Source: [Cursor Rules](https://cursor.com/docs/context/rules).
- **nygard-bullets-not-fragments**: Bullets are for visual style, not an excuse for sentence fragments. Quote: "Bullets are acceptable only for visual style, not as an excuse for writing sentence fragments." Source: [Documenting Architecture Decisions](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions).
- **changelog-for-humans**: A change history is written for people, which supports keeping it out of what an agent loads. Quote: "Changelogs are for humans, not machines." Source: [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).
- **pf-brevity-prior**: The draft's ~50-line cap. No source supports the number. Source: the base-commit draft `tbd/compliance/artifact-formatting/principle-formatting.md`.
