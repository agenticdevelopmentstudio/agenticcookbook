# Research: activity-triggers

The trigger design matches what agent hosts do now. Claude Code loads path-scoped rules and skills on demand. Cursor has four rule activation modes. Copilot has `applyTo`. OpenAI file search and Pinecone filter by metadata. The evaluations that exist (Lost in the Middle, IFScale, Chroma's context-rot report, RAG-MCP) all find that more context and more simultaneous instructions make models perform worse, which is the direction the guide assumes. Z39.19 and SKOS prescribe a closed vocabulary with one meaning per value, a scope note and examples. Outside practice also supports a union query, declaring scope in frontmatter, a cap of 5 tags per item, and nominating a new value before using it.

No source supports any number in the guide (240, 10-20, ~12, 27, ~10). No study measures tag-filtered guideline loading for coding agents. No study backs "most effective" for graduated checkpoints, and no source states the proportional-cost rule. The index location, the regeneration step, the hand-edit ban, specific-to-general ordering, the guideline-only scope and the empty-list default are internal choices that no outside source addresses. The research adds practices the guide lacks:

- Vocabulary governance: scope notes, history notes, renames that keep the old value as an alias, retirement with an impact check and migration, and periodic review of overused and unused values.
- Mechanical validation of trigger values.
- A fallback for when tags miss.
- Evaluation against a labelled task set that reports recall and precision.

Apple, Android and Windows have no bearing on this topic.

- **trigger-values-carry-key-terms**: SHOULD. Each value's description names the task language an agent will use (pg-skills-description-key-terms, bp-warrant).

- **retire-assesses-impact-and-migrates**: MUST consider the impact on tagged guidelines, and MAY migrate one-for-one replacements automatically (bp-retire-consider-impact, bp-one-for-one-auto-migrate, bp-delete-without-replacement-loses-access).

- **validate-trigger-values-mechanically**: SHOULD. Tooling rejects values outside the table, because neither SKOS nor the hosts will (pg-skos-open-boundary, pg-unknown-fields-ignored-silently).
- **measure-trigger-selection-with-labelled-tasks**: SHOULD. Evaluate selection against a labelled task set with a held-out split (ev-test-collection-three-parts, ev-fifty-information-needs, ks-skill-trigger-eval-set, pg-skills-evaluations-first).

## Best practices

*Best practices: what is current best practice for this topic?*

- **bp-smallest-high-signal-set**: Put the smallest set of high-signal tokens in context, not everything that might apply. Quote: "good context engineering means finding the smallest possible set of high-signal tokens that maximize the likelihood of some desired outcome." Source: [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents).
- **bp-context-rot-recall-falls**: A model's recall of what is in its context falls as the context grows. Quote: "as the number of tokens in the context window increases, the model's ability to accurately recall information from that context decreases." Source: [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents).
- **bp-no-laundry-list-of-rules**: Select rules; do not pile every rule into the prompt. Quote: "teams will often stuff a laundry list of edge cases into a prompt in an attempt to articulate every possible rule the LLM should follow for a particular task. We do not recommend this." Source: [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents).
- **bp-hybrid-upfront-plus-on-demand**: Load a small set up front and retrieve the rest on demand. Quote: "the most effective agents might employ a hybrid strategy, retrieving some data up front for speed, and pursuing further autonomous exploration at its discretion." Source: [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents).
- **bp-controlled-vocab-improves-precision-recall**: Controlled vocabularies improve both precision and recall. The standard cites no study for this. Quote: "controlled vocabularies improve both precision and recall in searching." Source: [ANSI/NISO Z39.19](https://groups.niso.org/higherlogic/ws/public/download/6484/Guidelines%20for%20the%20Construction,%20Format,%20and%20Management%20of%20Monolingual%20Controlled%20Vocabularies.pdf).
- **bp-vocab-control-three-methods**: A vocabulary is controlled by defining each term's scope, linking synonyms to one preferred term, and telling homographs apart. Quote: "defining the scope, or meaning, of terms; using the equivalence relationship to link synonymous and nearly synonymous terms; and distinguishing among homographs." Source: [ANSI/NISO Z39.19](https://groups.niso.org/higherlogic/ws/public/download/6484/Guidelines%20for%20the%20Construction,%20Format,%20and%20Management%20of%20Monolingual%20Controlled%20Vocabularies.pdf).
- **bp-controlled-vocabulary-defined**: A controlled vocabulary is an explicit list kept by an authority, and every term in it has a definition. Quote: "All terms in a controlled vocabulary must have an unambiguous, non-redundant definition." Source: [ANSI/NISO Z39.19](https://groups.niso.org/higherlogic/ws/public/download/6484/Guidelines%20for%20the%20Construction,%20Format,%20and%20Management%20of%20Monolingual%20Controlled%20Vocabularies.pdf).
- **bp-one-meaning-per-term**: Each term has exactly one meaning. Quote: "ensuring that each term has one and only one meaning." Source: [ANSI/NISO Z39.19](https://groups.niso.org/higherlogic/ws/public/download/6484/Guidelines%20for%20the%20Construction,%20Format,%20and%20Management%20of%20Monolingual%20Controlled%20Vocabularies.pdf).
- **bp-scope-note-states-meaning**: A scope note states the meaning chosen for a term and separates terms that overlap. Quote: "A scope note should state the chosen meaning of a term." Source: [ANSI/NISO Z39.19](https://groups.niso.org/higherlogic/ws/public/download/6484/Guidelines%20for%20the%20Construction,%20Format,%20and%20Management%20of%20Monolingual%20Controlled%20Vocabularies.pdf).
- **bp-vocabulary-needs-maintenance**: A vocabulary is never finished and needs continuing maintenance. Quote: "there is a continuing need to maintain the controlled vocabulary once it has been constructed." Source: [ANSI/NISO Z39.19](https://groups.niso.org/higherlogic/ws/public/download/6484/Guidelines%20for%20the%20Construction,%20Format,%20and%20Management%20of%20Monolingual%20Controlled%20Vocabularies.pdf).
- **bp-maintenance-policies**: Have a policy for periodic review, for adding terms and for replacing obsolete ones. Quote: "Policies and procedures should be established for periodic review of terminology, establishment of new terms, and replacement of obsolete terms". Source: [ANSI/NISO Z39.19](https://groups.niso.org/higherlogic/ws/public/download/6484/Guidelines%20for%20the%20Construction,%20Format,%20and%20Management%20of%20Monolingual%20Controlled%20Vocabularies.pdf).
- **bp-nominate-candidate-term**: When no term fits, nominate a candidate term instead of using an unlisted one. Quote: "the indexer or searcher should nominate a new term as a candidate term". Source: [ANSI/NISO Z39.19](https://groups.niso.org/higherlogic/ws/public/download/6484/Guidelines%20for%20the%20Construction,%20Format,%20and%20Management%20of%20Monolingual%20Controlled%20Vocabularies.pdf).
- **bp-editor-reviews-new-terms**: The vocabulary's editor, preferably a board, reviews candidate terms before they are admitted. Quote: "New terms and those nominated for reconsideration should be reviewed by the editor of the controlled vocabulary, and preferably by an editorial board". Source: [ANSI/NISO Z39.19](https://groups.niso.org/higherlogic/ws/public/download/6484/Guidelines%20for%20the%20Construction,%20Format,%20and%20Management%20of%20Monolingual%20Controlled%20Vocabularies.pdf).
- **bp-rename-use-reference**: A rename is dated and keeps a reference from the old form to the new one. Quote: "a USE reference should be made from the old form to the new form." Source: [ANSI/NISO Z39.19](https://groups.niso.org/higherlogic/ws/public/download/6484/Guidelines%20for%20the%20Construction,%20Format,%20and%20Management%20of%20Monolingual%20Controlled%20Vocabularies.pdf).
- **bp-retire-consider-impact**: Before changing or deleting a term, consider how the change affects finding items already tagged with it. Quote: "the impact of the change on the ability to search previously indexed database records must be considered". Source: [ANSI/NISO Z39.19](https://groups.niso.org/higherlogic/ws/public/download/6484/Guidelines%20for%20the%20Construction,%20Format,%20and%20Management%20of%20Monolingual%20Controlled%20Vocabularies.pdf).
- **bp-retained-term-marked**: A retired term that is kept is marked as kept for retrieval only and points to its successor. Quote: "If it is retained, it must be marked, e.g., \"for retrieval purposes only,\"". Source: [ANSI/NISO Z39.19](https://groups.niso.org/higherlogic/ws/public/download/6484/Guidelines%20for%20the%20Construction,%20Format,%20and%20Management%20of%20Monolingual%20Controlled%20Vocabularies.pdf).
- **bp-one-for-one-auto-migrate**: A one-for-one replacement can be applied to tagged items automatically. Quote: "One-for-one term changes, where one term simply replaces another, may be implemented in the database automatically if resources permit." Source: [ANSI/NISO Z39.19](https://groups.niso.org/higherlogic/ws/public/download/6484/Guidelines%20for%20the%20Construction,%20Format,%20and%20Management%20of%20Monolingual%20Controlled%20Vocabularies.pdf).
- **bp-delete-without-replacement-loses-access**: Deleting a term without retagging its items under a replacement loses those items over time. Quote: "Deleting a term in the database without replacing it with another term could, over time, seriously reduce access to content objects". Source: [ANSI/NISO Z39.19](https://groups.niso.org/higherlogic/ws/public/download/6484/Guidelines%20for%20the%20Construction,%20Format,%20and%20Management%20of%20Monolingual%20Controlled%20Vocabularies.pdf).
- **bp-history-note-records-entry**: Each term records the date it was added. Quote: "Each term should have a history note recording its date of entry". Source: [ANSI/NISO Z39.19](https://groups.niso.org/higherlogic/ws/public/download/6484/Guidelines%20for%20the%20Construction,%20Format,%20and%20Management%20of%20Monolingual%20Controlled%20Vocabularies.pdf).
- **bp-history-note-succession**: A history note can record when a term was discontinued and which term came before or after it. Quote: "the history note may also include the date discontinued, the term that succeeded the term, and/or the term that preceded it." Source: [ANSI/NISO Z39.19](https://groups.niso.org/higherlogic/ws/public/download/6484/Guidelines%20for%20the%20Construction,%20Format,%20and%20Management%20of%20Monolingual%20Controlled%20Vocabularies.pdf).
- **bp-change-record-dated**: Record every change with its date and the person responsible. Quote: "The term record should note the date of each change and identify the individual responsible for it." Source: [ANSI/NISO Z39.19](https://groups.niso.org/higherlogic/ws/public/download/6484/Guidelines%20for%20the%20Construction,%20Format,%20and%20Management%20of%20Monolingual%20Controlled%20Vocabularies.pdf).
- **bp-prune-overused-and-rare-terms**: Terms that are overused and terms that are rarely used are both candidates for change or removal. Quote: "Overused terms and terms that have been assigned very infrequently in indexing should be considered candidates for modification or deletion". Source: [ANSI/NISO Z39.19](https://groups.niso.org/higherlogic/ws/public/download/6484/Guidelines%20for%20the%20Construction,%20Format,%20and%20Management%20of%20Monolingual%20Controlled%20Vocabularies.pdf).
- **bp-periodic-evaluation**: Test and evaluate the vocabulary periodically. Quote: "it is vital to conduct periodic tests with follow-on evaluation to ensure that the controlled vocabulary is as useful as possible." Source: [ANSI/NISO Z39.19](https://groups.niso.org/higherlogic/ws/public/download/6484/Guidelines%20for%20the%20Construction,%20Format,%20and%20Management%20of%20Monolingual%20Controlled%20Vocabularies.pdf).
- **bp-warrant**: Choose terms on warrant: the language of the content, the language of its users, and the organisation's needs. Quote: "the language of users (user warrant), and • the needs and priorities of the organization (organizational warrant)." Source: [ANSI/NISO Z39.19](https://groups.niso.org/higherlogic/ws/public/download/6484/Guidelines%20for%20the%20Construction,%20Format,%20and%20Management%20of%20Monolingual%20Controlled%20Vocabularies.pdf).
- **bp-commit-build-fast**: The check that runs on every commit is kept fast, and it catches fewer bugs as a result. Quote: "The trick is to balance the needs of bug finding and speed". Source: [Continuous Integration](https://martinfowler.com/articles/continuousIntegration.html).
- **bp-ten-minute-build**: The commit stage is bounded by time, not by a count of rules. Quote: "the XP guideline of a ten minute build is perfectly within reason." Source: [Continuous Integration](https://martinfowler.com/articles/continuousIntegration.html).
- **bp-second-stage-build**: A slower, broader second stage runs after the commit stage. Quote: "The second stage build runs a different suite of tests that do hit a real database and involve more end-to-end behavior." Source: [Continuous Integration](https://martinfowler.com/articles/continuousIntegration.html).

## Known solutions

*Known solutions: what solutions, patterns, libraries and tools already exist, and how do they compare?*

- **ks-claude-path-scoped-rules**: Claude Code rules declare their scope in a `paths` frontmatter field and load only for matching files. The scope is keyed on files, not activities. Quote: "These conditional rules only apply when Claude is working with files matching the specified patterns." Source: [Manage Claude's memory](https://code.claude.com/docs/en/memory).
- **ks-path-rules-save-context**: The stated aim of scoped rules is less noise and less context used. Quote: "reducing noise and saving context space." Source: [Manage Claude's memory](https://code.claude.com/docs/en/memory).
- **ks-rules-without-paths-load-at-launch**: A rule with no scope loads at launch, which makes it an always-loaded tier. Quote: "are loaded at launch with the same priority as `.claude/CLAUDE.md`." Source: [Manage Claude's memory](https://code.claude.com/docs/en/memory).
- **ks-skill-body-loads-on-use**: A skill's body loads only when the skill is used. Quote: "a skill's body loads only when it's used, so long reference material costs almost nothing until you need it." Source: [Extend Claude with skills](https://code.claude.com/docs/en/skills).
- **ks-skill-description-decides-loading**: Claude Code picks skills by matching the task against each skill's free-text description, not against a closed vocabulary. Quote: "Claude uses this to decide when to apply the skill." Source: [Extend Claude with skills](https://code.claude.com/docs/en/skills).
- **ks-skill-listing-budget-drops-descriptions**: When there are many skills, Claude Code drops some descriptions from the listing, and with them the keywords used for matching. Quote: "Claude Code drops some descriptions to fit the listing's character budget, which removes the keywords Claude needs to match your request." Source: [Extend Claude with skills](https://code.claude.com/docs/en/skills).
- **ks-skill-listing-costs-every-turn**: Anything that is always listed costs context on every turn. Quote: "Every skill in the [skill listing](#skill-descriptions-are-cut-short) adds to your context on every turn, whether or not Claude ever uses it." Source: [Extend Claude with skills](https://code.claude.com/docs/en/skills).
- **ks-cursor-rule-types**: Cursor rules have four activation modes: always, chosen by the agent from the description, by file pattern, and by manual mention. Quote: "Apply Intelligently When Agent decides it's relevant based on description". Source: [Cursor Rules](https://cursor.com/docs/context/rules).
- **ks-cursor-always-apply**: An `alwaysApply` rule is included in every session. Quote: "alwaysApply true — Always included. Globs and description are ignored." Source: [Cursor Rules](https://cursor.com/docs/context/rules).
- **ks-copilot-path-instructions**: Copilot applies path-specific instruction files only to requests about matching files. Quote: "apply to requests made in the context of files that match a specified path." Source: [Adding repository custom instructions](https://docs.github.com/en/copilot/how-tos/configure-custom-instructions/add-repository-instructions).
- **ks-copilot-applyto-frontmatter**: Copilot instruction files declare their scope in a frontmatter block. Quote: "At the start of the file, create a frontmatter block containing the `applyTo` keyword." Source: [Adding repository custom instructions](https://docs.github.com/en/copilot/how-tos/configure-custom-instructions/add-repository-instructions).
- **ks-copilot-instructions-combined**: When several Copilot instruction files apply, all of them are used, so the result is a union. Quote: "then the instructions from both files are used." Source: [Adding repository custom instructions](https://docs.github.com/en/copilot/how-tos/configure-custom-instructions/add-repository-instructions).
- **ks-agents-md-nearest-file**: AGENTS.md scopes instructions by directory. Quote: "Agents automatically read the nearest file in the directory tree". Source: [AGENTS.md](https://agents.md/).
- **ks-codex-concatenates-root-down**: Codex joins every AGENTS.md from the root down into one static, always-loaded layer. Quote: "Codex concatenates files from the root down, joining them with blank lines." Source: [Custom instructions with AGENTS.md](https://developers.openai.com/codex/guides/agents-md).
- **ks-codex-size-limit**: Codex caps the always-loaded layer at 32 KiB by default. Quote: "stops adding files once the combined size reaches the limit defined by project_doc_max_bytes (32 KiB by default)." Source: [Custom instructions with AGENTS.md](https://developers.openai.com/codex/guides/agents-md).
- **ks-openai-metadata-filter**: OpenAI file search filters results by file metadata. Quote: "You can filter the search results based on the metadata of the files." Source: [File search](https://platform.openai.com/docs/guides/tools-file-search).
- **ks-pinecone-metadata-filter**: Vector databases limit a search to documents whose metadata matches a filter. Quote: "When you search, add a metadata filter to limit results to the documents that match it." Source: [Filter by metadata](https://docs.pinecone.io/guides/search/filter-by-metadata).
- **ks-pinecone-in-operator**: One query can match any of several values, which is the same operation as a union over triggers. Quote: "$in Matches records or documents with metadata values that are in a specified array." Source: [Filter by metadata](https://docs.pinecone.io/guides/search/filter-by-metadata).
- **ks-tool-search-accuracy-degrades**: Anthropic says tool selection gets worse past 30-50 tools. It discloses no study for this figure. Quote: "Claude's ability to pick the right tool degrades once you exceed 30–50 available tools." Source: [Tool search tool](https://docs.claude.com/en/docs/agents-and-tools/tool-use/tool-search-tool).
- **ks-keep-few-tools-non-deferred**: Keep a small core of tools always loaded and defer the rest. Quote: "Keep your 3–5 most frequently used tools non-deferred". Source: [Tool search tool](https://docs.claude.com/en/docs/agents-and-tools/tool-use/tool-search-tool).
- **ks-pre-commit-simple-issues**: Commit hooks catch simple issues on every commit, which frees reviewers to look at architecture. Quote: "Git hook scripts are useful for identifying simple issues before submission to code review." Source: [pre-commit](https://pre-commit.com/).
- **ks-pre-commit-stages**: The pre-commit framework assigns each check to a stage, so heavier checks can run at a later checkpoint. Quote: "default_stages : [ pre-commit , pre-push ]". Source: [pre-commit](https://pre-commit.com/).
- **ks-skill-trigger-eval-set**: skill-creator tests whether a skill triggers using 20 labelled queries. Quote: "Create 20 eval queries — a mix of should-trigger and should-not-trigger." Source: [skill-creator SKILL.md](https://raw.githubusercontent.com/anthropics/skills/main/skills/skill-creator/SKILL.md).
- **ks-skill-trigger-train-test-split**: skill-creator holds out a test set and runs each query several times to get a trigger rate. Quote: "It splits the eval set into 60% train and 40% held-out test". Source: [skill-creator SKILL.md](https://raw.githubusercontent.com/anthropics/skills/main/skills/skill-creator/SKILL.md).
- **ks-skill-undertrigger**: The common failure of description-based selection is under-triggering. Quote: "currently Claude has a tendency to \"undertrigger\" skills -- to not use them when they'd be useful." Source: [skill-creator SKILL.md](https://raw.githubusercontent.com/anthropics/skills/main/skills/skill-creator/SKILL.md).
- **ks-plugin-eval-trigger-rate**: Claude Code can measure how often a skill triggers across a set of prompts. Quote: "you can measure how often it triggers across realistic prompts rather than checking one at a time". Source: [Extend Claude with skills](https://code.claude.com/docs/en/skills).
- **ks-so-five-tag-cap**: Stack Overflow caps each question at 5 tags. Quote: "Each question may only contain 5 tags at a maximum". Source: [Stack Overflow tagging help](https://stackoverflow.com/help/tagging).
- **ks-so-favor-existing-tags**: Use existing tags, and create a new one only when there is a strong case for it. Quote: "You should always favor existing tags; only create new tags when you feel you can make a strong case". Source: [Create new tags](https://stackoverflow.com/help/privileges/create-tags).
- **ks-so-tag-synonyms-auto-retag**: Tag synonyms retag items automatically. Quote: "The goal is to avoid manually editing the tags on every post by making the retagging automatic for common tag mistakes." Source: [Create tag synonyms](https://stackoverflow.com/help/privileges/suggest-tag-synonyms).

## Platform guidelines

*Platform guidelines: what do the platform owners' own guidelines say, for each platform the topic touches (Apple, Android, Windows, web, the databases and runtimes concerned)?*

Apple, Android and Windows have no bearing on this topic. The platforms it touches are the agent hosts, git and GitHub, and the vocabulary standards.

- **pg-agent-skills-progressive-disclosure**: Agent Skills load information in stages. Quote: "Claude loads information in stages as needed, rather than consuming context upfront." Source: [Agent Skills](https://docs.claude.com/en/docs/agents-and-tools/agent-skills/overview).
- **pg-skills-metadata-only-until-triggered**: Only a skill's name and description sit in context until the skill triggers. Quote: "until a Skill is triggered, only its name and description occupy context." Source: [Agent Skills](https://docs.claude.com/en/docs/agents-and-tools/agent-skills/overview).
- **pg-skills-description-key-terms**: The selection text should name key terms and say when to use the skill. Quote: "Include both what the Skill does and specific triggers/contexts for when to use it." Source: [Skill authoring best practices](https://docs.claude.com/en/docs/agents-and-tools/agent-skills/best-practices).
- **pg-skills-evaluations-first**: Build evaluations before writing extensive content. Quote: "Create evaluations BEFORE writing extensive documentation." Source: [Skill authoring best practices](https://docs.claude.com/en/docs/agents-and-tools/agent-skills/best-practices).
- **pg-skills-evaluations-source-of-truth**: Evaluations are the source of truth for whether a skill works. Quote: "Evaluations are your source of truth for measuring Skill effectiveness." Source: [Skill authoring best practices](https://docs.claude.com/en/docs/agents-and-tools/agent-skills/best-practices).
- **pg-claude-md-size-adherence**: Keep the always-loaded file under 200 lines and move part-specific instructions into scoped rules. Quote: "Longer files consume more context and reduce adherence." Source: [Manage Claude's memory](https://code.claude.com/docs/en/memory).
- **pg-instructions-loaded-hook**: A hook logs which instruction files load, when and why. Quote: "log which `CLAUDE.md` and rules files are loaded, when they load, and why." Source: [Manage Claude's memory](https://code.claude.com/docs/en/memory).
- **pg-bad-frontmatter-loads-always**: A rule whose frontmatter does not parse loads as if it had no scope, and no error is raised. Quote: "Claude Code ignores the frontmatter and loads the rule as if it had no `paths`." Source: [Manage Claude's memory](https://code.claude.com/docs/en/memory).
- **pg-unknown-fields-ignored-silently**: The host silently ignores frontmatter fields it does not know. Quote: "any other field is ignored without an error." Source: [Manage Claude's memory](https://code.claude.com/docs/en/memory).
- **pg-cursor-rules-focused**: Cursor's guidance is for focused rules under 500 lines. Quote: "Good rules are focused, actionable, and scoped. Keep rules under 500 lines". Source: [Cursor Rules](https://cursor.com/docs/context/rules).
- **pg-skos-one-preflabel**: A concept has at most one preferred label per language. Quote: "S14 A resource has no more than one value of skos:prefLabel per language tag." Source: [SKOS Reference](https://www.w3.org/TR/skos-reference/).
- **pg-skos-scope-note**: A scope note says how a concept's use is limited. Quote: "especially as an indication of how the use of a concept is limited in indexing practice." Source: [SKOS Primer](https://www.w3.org/TR/skos-primer/).
- **pg-skos-definition**: A definition gives the complete meaning. Quote: "skos:definition supplies a complete explanation of the intended meaning of a concept." Source: [SKOS Primer](https://www.w3.org/TR/skos-primer/).
- **pg-skos-example**: An example note shows a concept in use. Quote: "skos:example supplies an example of the use of a concept". Source: [SKOS Primer](https://www.w3.org/TR/skos-primer/).
- **pg-skos-history-note**: A history note records significant changes. Quote: "skos:historyNote describes significant changes to the meaning or the form of a concept". Source: [SKOS Primer](https://www.w3.org/TR/skos-primer/).
- **pg-skos-change-note**: A change note records fine-grained administrative changes. Quote: "skos:changeNote documents fine-grained changes to a concept, for the purposes of administration and maintenance". Source: [SKOS Primer](https://www.w3.org/TR/skos-primer/).
- **pg-skos-altlabel-synonyms**: Alternative labels hold synonyms and old forms beside the preferred label. Quote: "The skos:altLabel property makes it possible to assign an alternative lexical label to a concept." Source: [SKOS Primer](https://www.w3.org/TR/skos-primer/).
- **pg-skos-hidden-label**: Hidden labels match in search without being shown. Quote: "would like that character string to be accessible to applications performing text-based indexing and search operations, but would not like that label to be visible otherwise." Source: [SKOS Primer](https://www.w3.org/TR/skos-primer/).
- **pg-skos-open-boundary**: SKOS cannot close a vocabulary, so the application has to enforce closure. Quote: "note that there is no way to close the boundary of a concept scheme." Source: [SKOS Reference](https://www.w3.org/TR/skos-reference/).
- **pg-iso25964-maintenance**: ISO 25964-1 covers how thesauri are developed and maintained. Quote: "This part of ISO 25964 gives recommendations for the development and maintenance of thesauri intended for information retrieval applications". Source: [NISO: ISO 25964](https://www.niso.org/schemas/iso25964).
- **pg-iso25964-skos-compatible**: ISO 25964 was written to stay compatible with SKOS. Quote: "Care has similarly been taken to maintain compatibility with the W3C standard SKOS". Source: [NISO: ISO 25964](https://www.niso.org/schemas/iso25964).
- **pg-githooks-pre-commit-bypass**: Anyone can bypass the git pre-commit hook. Quote: "pre-commit This hook is invoked by git-commit[1] , and can be bypassed with the --no-verify option." Source: [githooks](https://git-scm.com/docs/githooks).
- **pg-githooks-pre-push**: pre-push is a later checkpoint that can block a push. Quote: "pre-push This hook is called by git-push[1] and can be used to prevent a push from taking place." Source: [githooks](https://git-scm.com/docs/githooks).
- **pg-github-required-status-checks**: GitHub can require named checks to pass before changes reach a protected branch. Quote: "Required status checks must have a `successful`, `skipped`, or `neutral` status before collaborators can make changes to a protected branch." Source: [About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).

## The expert's view

*The expert's view: if we hired an expert consultant in this topic, what would they tell us: what to do, what to avoid, and what people usually get wrong?*

- **ev-lost-in-middle-position**: Models do not make robust use of long contexts. The study used 2,655 NaturalQuestions queries with 10-30 documents per context and measured accuracy. Quote: "performance can degrade significantly when changing the position of relevant information". Source: [Lost in the Middle](https://arxiv.org/abs/2307.03172).
- **ev-lost-in-middle-below-closed-book**: Extra documents can leave a model worse off than having none. Quote: "GPT-3.5-Turbo's performance on the multi- document question task is lower than its performance when predicting without any documents (i.e., the closed-book setting; 56.1%)." Source: [Lost in the Middle](https://arxiv.org/abs/2307.03172).
- **ev-more-docs-marginal**: Going from 20 to 50 documents bought only about 1-1.5 points of accuracy. Quote: "using 50 documents instead of 20 retrieved documents only marginally improves performance". Source: [Lost in the Middle](https://arxiv.org/abs/2307.03172).
- **ev-ifscale-instruction-density**: Accuracy falls as the number of instructions given at once rises. The benchmark has 500 keyword-inclusion instructions and tested 20 models; the best reached 68% at the highest density. Quote: "We introduce IFScale, a simple benchmark of 500 keyword-inclusion instructions". Source: [How Many Instructions Can LLMs Follow at Once?](https://arxiv.org/abs/2507.11538).
- **ev-chroma-context-rot**: Across 18 models, performance grows less reliable as input grows. Quote: "their performance grows increasingly unreliable as input length grows." Source: [Context Rot](https://research.trychroma.com/context-rot).
- **ev-rag-mcp-selection-accuracy**: Retrieving a small subset of tools first tripled selection accuracy, from 13.62% to 43.13%, and cut prompt tokens by more than half. Quote: "more than triples tool selection accuracy (43.13% vs 13.62% baseline)". Source: [RAG-MCP](https://arxiv.org/abs/2505.03275).
- **ev-rag-mcp-degrades-at-scale**: Retrieval-based selection also loses precision as the registry grows into the thousands. Quote: "its retrieval precision and overall throughput degrade as the tool registry scales to thousands of MCPs." Source: [RAG-MCP](https://arxiv.org/abs/2505.03275).
- **ev-anthropic-tool-search-internal**: Anthropic reports accuracy gains from on-demand tool loading, from internal testing with no disclosed sample. Quote: "Opus 4 improved from 49% to 74%". Source: [Introducing advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use).
- **ev-tool-search-token-reduction**: Anthropic reports an 85% token reduction from deferring tool definitions, from its own example. Quote: "This represents an 85% reduction in token usage". Source: [Introducing advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use).
- **ev-contextual-retrieval-failure-rate**: Measure selection by the share of relevant items that are not retrieved (1 minus recall@k). Quote: "We use 1 minus recall@20 as our evaluation metric". Source: [Introducing Contextual Retrieval](https://www.anthropic.com/news/contextual-retrieval).
- **ev-contextual-retrieval-small-kb-in-prompt**: When the whole corpus is under about 200,000 tokens, load it all instead of filtering. This pulls against the context-rot findings. Quote: "If your knowledge base is smaller than 200,000 tokens (about 500 pages of material), you can just include the entire knowledge base in the prompt". Source: [Introducing Contextual Retrieval](https://www.anthropic.com/news/contextual-retrieval).
- **ev-test-collection-three-parts**: An evaluation needs a document collection, a set of information needs, and relevance judgments. For triggers, those are the guidelines, a set of tasks, and the guidelines each task needs. Quote: "we need a test collection consisting of three things". Source: [IIR ch. 8](https://wiki.eecs.yorku.ca/course_archive/2013-14/W/6339/_media/08eval.pdf).
- **ev-fifty-information-needs**: The rule of thumb is a minimum of 50 information needs. Quote: "As a rule of thumb, 50 information needs has usually been found to be a sufficient minimum." Source: [IIR ch. 8](https://wiki.eecs.yorku.ca/course_archive/2013-14/W/6339/_media/08eval.pdf).
- **ev-relevance-to-need-not-query**: Relevance is judged against the task, not against the trigger word. Quote: "Relevance is assessed relative to an information need, not a query." Source: [IIR ch. 8](https://wiki.eecs.yorku.ca/course_archive/2013-14/W/6339/_media/08eval.pdf).
- **ev-measure-by-recall-precision**: Retrieval is traditionally measured by recall and precision. Quote: "Information retrieval effectiveness is traditionally measured by two parameters: recall and precision." Source: [ANSI/NISO Z39.19](https://groups.niso.org/higherlogic/ws/public/download/6484/Guidelines%20for%20the%20Construction,%20Format,%20and%20Management%20of%20Monolingual%20Controlled%20Vocabularies.pdf).
- **ev-recall-defined**: Recall measures whether all the relevant items are retrieved. Quote: "A measure of a search system's ability to retrieve all relevant content objects." Source: [ANSI/NISO Z39.19](https://groups.niso.org/higherlogic/ws/public/download/6484/Guidelines%20for%20the%20Construction,%20Format,%20and%20Management%20of%20Monolingual%20Controlled%20Vocabularies.pdf).
- **ev-precision-defined**: Precision measures whether only relevant items are retrieved. Quote: "A measure of a search system's ability to retrieve only relevant content objects." Source: [ANSI/NISO Z39.19](https://groups.niso.org/higherlogic/ws/public/download/6484/Guidelines%20for%20the%20Construction,%20Format,%20and%20Management%20of%20Monolingual%20Controlled%20Vocabularies.pdf).
- **ev-recall-precision-inverse**: Recall and precision usually trade off against each other. Quote: "Recall and precision tend to be inverse ratios. When one goes up, the other usually goes down." Source: [ANSI/NISO Z39.19](https://groups.niso.org/higherlogic/ws/public/download/6484/Guidelines%20for%20the%20Construction,%20Format,%20and%20Management%20of%20Monolingual%20Controlled%20Vocabularies.pdf).
- **ev-start-with-recall**: Tune recall first, then precision. Anthropic says this about compaction; it is applied here by analogy. Quote: "Start by maximizing recall to ensure your compaction prompt captures every relevant piece of information from the trace, then iterate to improve precision". Source: [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents).
- **ev-human-cant-pick-tool**: Options that overlap defeat selection. The same holds for triggers whose scopes overlap. Quote: "If a human engineer can't definitively say which tool should be used in a given situation, an AI agent can't be expected to do better." Source: [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents).
- **ev-little-research-vocab-evaluation**: There is little published work on testing vocabularies, so the cookbook has to build its own evaluation. Quote: "There is surprisingly little research or literature dealing specifically with the testing and evaluation of controlled vocabularies". Source: [ANSI/NISO Z39.19](https://groups.niso.org/higherlogic/ws/public/download/6484/Guidelines%20for%20the%20Construction,%20Format,%20and%20Management%20of%20Monolingual%20Controlled%20Vocabularies.pdf).
- **ev-indexer-consistency-low**: People tagging from a controlled vocabulary agree with each other only 27.5-39.5% of the time. The study used Hooper's measure on three articles, with student and professional indexers. So tags alone will miss items. Quote: "The tool with the best results is the list of descriptors (39.5% consistency)". Source: [Evaluation of controlled vocabularies by inter-indexer consistency](https://informationr.net/ir/16-4/paper502.html).
