
- `should-express-every-decision-as-a-token`: each UI design decision is a named token in the single source, or the work says why not
- `must-reference-semantic-tokens-not-raw-values`: components and application code hold no raw design values
- `must-keep-one-shared-source`: one shared token source exists, with no per-platform duplicate
- `should-use-the-dtcg-format`: the source is DTCG JSON, or the work says why not
- `should-pin-a-dated-dtcg-revision`: the source pins a dated DTCG revision, or the work says why not
- `must-give-each-token-a-type-and-value`: every token has an explicit `$type` and `$value`
- `should-generate-platform-outputs`: every platform output is generated by a build step, or the work says why not
- `should-use-three-layers`: tokens are layered as primitive, semantic and component, or the work says why not
- `must-not-reference-primitives-from-code`: no component or application code references a primitive
- `must-alias-semantic-and-component-tokens`: every semantic and component token is a `{token.path}` alias
- `should-keep-three-tiers-at-most`: there are at most three tiers and any component tier has a second consumer, or the work says why not
- `should-model-variants-by-swapping-semantic-references`: each variant swaps the semantic layer's references and leaves component tokens untouched, or the work says why not
- `should-resolve-modes-as-sets-or-themes`: mode-specific values resolve as sets/themes with one component contract, or the work says why not
- `must-use-platform-neutral-names`: every token name is consistent and platform-neutral
- `should-check-contrast-in-the-pipeline`: the token pipeline checks WCAG 2.2 contrast (4.5:1 body, 3:1 large/UI) and fails the build on violation, or the work says why not
- `should-schema-validate-the-token-file`: CI schema-validates the token file, or the work says why not
