
- **should-group-protocol-with-primary-implementation**: If a file defines a protocol and a second file is its primary concrete implementation, they **SHOULD** be in the same scope group unless the implementation is independently large enough to warrant separation (50+ files) — protocol/interface + implementors form one unit.
- **should-treat-barrel-reexports-as-one-candidate**: If a barrel re-exports from five subdirectories, those subdirectories share an interface and **SHOULD** be treated as candidates for a single scope group — unless they are large enough to warrant separate groups that share a common API layer — barrel files define the interface boundary.
- **should-place-shared-types-with-primary-consumer**: A shared type **SHOULD** be placed with its primary consumer, not its definition file: a `UserProfile` struct defined in `Models/` but used only by the `Auth` module belongs in the `Auth` scope group — shared types follow their primary consumer, not their definition file.
- **should-note-fragmented-interfaces**: If the same logical interface is declared across three files with no organizing barrel, the analysis **SHOULD** note this as a cohesion anomaly — fragmented interfaces are a smell.
- **should-not-count-internal-helpers-as-interface**: Private/internal/file-private symbols **SHOULD NOT** be counted toward interface cohesion; they contribute to implementation cohesion analyzed by `dependency-clusters` — internal helpers are not interface.
- **should-attend-to-protocol-extension-pairs**: For Swift `public` / `open` declarations, the analysis **SHOULD** pay special attention to protocol + extension pairs.
- **should-treat-java-interface-triads-as-one-unit**: Java `interface` + `abstract class` + primary implementation triads **SHOULD** be treated as one unit.
