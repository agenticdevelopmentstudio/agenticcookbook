
- **should-research-open-source-before-building**: When no native solution exists, SHOULD research battle-tested open-source libraries and present options to the user before building a custom solution.
- **should-make-custom-a-deliberate-decision**: A custom implementation MAY always be chosen instead, but it SHOULD be a deliberate decision, not a default.
- **should-check-what-you-already-have**: Before reaching outward, SHOULD check what you already have: the platform's standard library and the dependencies already in the project often solve the problem — SHOULD prefer those before adding anything new.
- **should-evaluate-candidates-before-recommending**: SHOULD evaluate candidates by maintenance activity, license compatibility, and community adoption before recommending.
- **should-verify-candidate-is-real**: SHOULD verify a candidate is real before adopting it: confirm the package actually exists, is actively maintained, and is widely used.
- **must-not-install-unverified-ai-suggested-packages**: MUST NOT install a package name an AI suggested without verifying it — hallucinated and typosquatted names are a live supply-chain risk.
- **should-present-at-least-two-options**: SHOULD present at least two options with trade-offs rather than silently picking one.
- **should-document-why-open-source-was-rejected**: If building custom, SHOULD document why the available open-source options were rejected.
