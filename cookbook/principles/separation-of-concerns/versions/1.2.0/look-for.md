
- `should-have-one-reason-to-change`: a function, module, service, or team that changes for more than one reason
- `should-split-when-description-needs-and`: a module whose responsibility cannot be described in one sentence without "and"
- `should-separate-ui-logic-and-data`: UI rendering, business logic, and data access mixed in one layer
- `should-treat-cross-feature-edits-as-coupling`: a change to one feature that forces edits in an unrelated feature
- `should-co-locate-by-reason-to-read`: one feature's behavior scattered across many files so a reader must hop between them to follow it
