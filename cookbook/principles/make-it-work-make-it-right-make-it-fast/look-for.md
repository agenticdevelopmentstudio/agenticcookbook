
- `should-separate-into-sequential-phases`: correctness, design cleanup and optimization mixed into one pass
- `should-first-make-it-work`: design or performance work started before the common case works
- `should-then-make-it-right`: a working solution left unrefactored, with edge cases unhandled or design left messy
- `should-optimize-only-measured-slowness`: an optimization with no measurement showing the code was slow
- `must-not-skip-make-it-right`: optimization applied to code that was never refactored, its edge cases unhandled
- `must-walk-each-claimed-behavior-to-its-effect`: does this change actually work, in every way it will be run?
  - For each behavior the changeset claims to deliver (from its commit messages, new/renamed public names, and the shape of the diff):
  - (1) State the claim in one sentence — what a user of this change is supposed to be able to do or observe.
  - (2) Walk the primary path entry-to-effect in the code AS WRITTEN — from the entry point (CLI verb, API route, event handler, config flag) through every call it makes to the observed effect — using the repo tools to read past the diff, including into submodule and vendored paths; a wall the call path crosses is a wall the trace must cross.
- `must-not-silently-remove-old-behavior`: (3) Compare against the base: when `read_base_file` is among your tools, use it to read what the code did BEFORE the change; when it is not (some providers and degraded runs cannot open the base commit), read the before-code from the diff's removed and context lines instead, and say in your summary that the comparison reached only as far as the hunks show. Either way, say what a user of the old behavior experiences after the change — a behavior the change silently removed or broke is a finding even when every new line is individually correct.
- `must-order-every-step-on-a-path-correctly`: (4) Then look past the claims, at what the code does that nobody claimed. Ask of every path you walked: (a) What else runs on this path, and in what order? Name each step that fires on the first run, on a repeat run, after the user declines or cancels, and when a background or scheduled job reaches the same code — a step that runs when it should not, runs twice, or runs before the thing it depends on is a finding.
- `must-treat-paired-operations-alike`: (b) Do paired operations treat the same input the same way? Install and uninstall, write and read, register and unregister, encode and decode, add and remove: put the two sides next to each other and compare how each normalizes, trims, quotes, matches and looks up the same value — one side that does and one that does not is a finding.
- `must-close-every-route-to-a-fixed-failure`: (c) Does a fix close every route to the failure it targets? When the change says it fixes or prevents something, list every path that can reach that failure (other callers, other entry points, the upgrade path, the already-broken state on disk) and check each one — a fix that closes one route and leaves another open is a finding.
- `should-not-ask-for-more-than-the-use-needs`: (d) Does each low-level call ask for more than it needs? A file or lock opened read-write when it is only read, a wider permission, mode, scope or flag than the use requires, an exclusive hold where a shared one would do — each is a finding.
- `must-not-ship-a-path-that-cannot-work`: (5) File every real defect you find on the way — a path that never reaches its effect, a claim with no path at all, a regression the diff hides, and anything (a)-(d) turned up — whether or not the changeset made a claim about it. A condition tested twice, a check that can never be true, a wrong index or off-by-one are bugs and are yours. Purely cosmetic style is not a bug; leave it to the specialists that own it.
